FS7 — Build y entrega: qué hace realmente tu bundler

FS7.0 Por qué este módulo

En el M09 configuraste Vite, instalaste dependencias con npm y pusiste ESLint. Eso alcanza para trabajar. Deja de alcanzar exactamente el día en que alguien te manda un mensaje que dice: "el bundle inicial pesa 940 KB, ¿por qué?". Ahí no sirve saber qué archivo de configuración tocar: hay que saber qué construyó el bundler y con qué criterio.

💡 La tesis del módulo. Un bundler no es una caja negra que "empaqueta": es un programa que construye un grafo dirigido de módulos a partir de un punto de entrada, y después decide cómo cortar ese grafo en archivos. Todo lo demás —tree shaking, code splitting, por qué una dependencia CommonJS arruina la optimización, por qué el vendor chunk gigante te invalida la caché— son consecuencias de esas dos operaciones. Entendé el grafo y el resto se deduce.

Y hay una razón de coyuntura para estudiarlo ahora. Entre 2024 y 2026 el ecosistema se reescribió en Rust y Go. En marzo de 2026, Vite 8 reemplazó sus dos bundlers históricos —esbuild en desarrollo, Rollup en producción— por uno solo escrito en Rust, Rolldown, sin opción de opt-out. En Next.js 16, Turbopack pasó a ser el bundler estable y por defecto tanto en dev como en build. Los tiempos de build cayeron un orden de magnitud, los mensajes de error cambiaron y algunas suposiciones que tenías dejaron de valer. Este módulo es el mapa de ese terreno.

📌 Lo que separa configurar de decidir. Configurar es copiar un vite.config.js de un blog. Decidir es poder responder, con un número, estas cuatro preguntas: ¿cuánto JavaScript descarga y ejecuta un usuario nuevo en la ruta más importante? ¿Qué porcentaje de eso se usa en los primeros 5 segundos? ¿Qué se invalida de la caché en cada deploy? ¿Cuánto de todo eso lo puse yo y cuánto vino de arrastre?

FS7.1 El grafo de módulos: las cuatro etapas de un build

Todo bundler moderno hace lo mismo, en el mismo orden. Cambian los lenguajes de implementación y las heurísticas, no las etapas:

1. Entry. Arranca de uno o varios puntos de entrada (src/main.tsx, o el <script type="module"> del HTML). Cada entry es la raíz de un grafo.
2. Resolución. Por cada import, traduce el especificador a un archivo real en disco. "./boton" → ./boton.tsx. "react" → node_modules/react/index.js, o lo que digan los campos exports / module / main del package.json. Es una operación de I/O intensiva y en proyectos grandes es donde se va muchísimo tiempo.
3. Transformación. Cada archivo pasa por los loaders/plugins: TypeScript se despoja de tipos, JSX se convierte en llamadas a función, el CSS se procesa, los assets se convierten en URLs o en data URIs. El resultado es JavaScript que el navegador entiende, más un registro de qué importa y qué exporta cada módulo.
4. Chunking y emisión. Con el grafo completo se decide en cuántos archivos se corta: se aplica tree shaking, se agrupan módulos en chunks, se minifica, se calculan los hashes de contenido para el nombre de archivo y se escribe todo a dist/.
# El grafo, dibujado a mano
#
#   main.tsx  (entry)
#     ├─ App.tsx
#     │    ├─ Header.tsx ──── logo.svg
#     │    ├─ Tabla.tsx ───── date-fns/format
#     │    └─ Grafico.tsx ─── recharts  (350 KB)
#     └─ estilos.css
#
# El bundler visita cada nodo UNA vez, lo cachea, y después
# decide qué nodos van juntos en cada archivo de salida.

Dónde se va el tiempo del build

EtapaPeso típicoQué la hace lentaCómo se acelera
Resolución10–25%Miles de stat() al filesystem; node_modules profundoCaché en disco; resolución paralela (Rust/Go)
Transformación40–60%Parsear y regenerar AST por archivo — el cuello clásico de BabelParsers nativos (Oxc, SWC, esbuild), paralelismo real por core
Tree shaking + chunking10–20%Análisis global: no se puede paralelizar del todoGrafos incrementales; menos módulos
Minificación15–30%Terser en JS puro era lo más caro de todoMinificadores nativos (Oxc, esbuild)
Por eso la migración a Rust/Go dio saltos tan grandes: las dos etapas que más pesan —transformar y minificar— son vergonzosamente paralelas (cada archivo es independiente) y Node.js, con un solo hilo por proceso, no podía aprovecharlas. No fue magia: fue usar los ocho cores que ya tenías.

FS7.2 ESM vs CommonJS: por qué el análisis estático lo habilita todo

La diferencia entre los dos sistemas de módulos no es de sintaxis. Es que uno se puede analizar sin ejecutarlo y el otro no.

// ESM — la estructura es ESTÁTICA.
// Los import van arriba, no pueden estar dentro de un if,
// y los nombres son literales. El bundler sabe todo sin ejecutar nada.
import { format } from "date-fns";
export function fecha(d) { return format(d, "yyyy-MM-dd"); }
// CommonJS — la estructura es DINÁMICA.
// require() es una función normal: puede recibir cualquier expresión.
const nombre = process.env.MODO === "rapido" ? "./rapido" : "./lento";
const mod = require(nombre);          // ¿qué módulo es? Se sabe en runtime.

module.exports.util = mod.util;
if (features.beta) module.exports.beta = require("./beta");   // exports condicionales
📌 La consecuencia. Con ESM, el bundler puede afirmar "del módulo date-fns solo se usa format" y descartar el resto con certeza matemática. Con CommonJS, la única respuesta honesta es "no sé qué se usa, incluyo todo". Tree shaking, code splitting automático y import() analizable son todos corolarios del análisis estático de ESM.

Una sola dependencia CJS puede arruinarlo

El problema no es tener una dependencia CommonJS: es dónde está. Si un paquete CJS está en el camino de tus imports, todo lo que pase por él pierde el análisis:

// tu-app importa un wrapper que es CJS,
// y ese wrapper importa la librería grande.
//
//   app.tsx (ESM)  →  @empresa/ui-kit (CJS)  →  recharts (ESM, 350 KB)
//
// El bundler NO puede saber qué re-exporta ui-kit, así que
// arrastra recharts entero, aunque vos uses un solo componente.
# Cómo detectar dependencias CJS en tu grafo
npx are-the-types-wrong@latest @empresa/ui-kit   # verifica exports/tipos ESM
npx publint @empresa/ui-kit                      # audita el package.json publicado

# Y en Vite: qué tuvo que convertir de CJS a ESM en el pre-bundle
npx vite build --debug 2>&1 | grep -i "commonjs"
El error de diagnóstico más común: ver un paquete inflado en el treemap y culpar al bundler por "no sacudirlo". En nueve de cada diez casos la causa está una capa más arriba: un barrel file (index.js que re-exporta 300 módulos), un package.json sin campo exports, o un intermediario CommonJS. El bundler hizo exactamente lo que podía hacer con la información que le diste.

Cómo se ve un paquete que se deja optimizar

{
  "name": "mi-lib",
  "type": "module",
  "sideEffects": false,
  "exports": {
    ".":        { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
    "./boton":  { "types": "./dist/boton.d.ts", "import": "./dist/boton.js" },
    "./estilos.css": "./dist/estilos.css"
  },
  "files": ["dist"]
}
Tres señales de que una dependencia va a jugar limpio con tu bundle: (1) "type": "module", (2) campo exports con subpaths reales en vez de un único barrel, (3) sideEffects declarado. Si un paquete tiene las tres, tree shaking va a funcionar. Si no tiene ninguna, asumí que vas a cargar el paquete entero y decidí sabiendo eso.

FS7.3 Tree shaking de verdad y sus límites

La definición de folleto es "elimina el código que no usás". La definición honesta es: elimina las exportaciones que puede demostrar que nadie referencia y cuya eliminación puede demostrar que no cambia el comportamiento observable. Las dos demostraciones fallan más seguido de lo que la gente cree.

Por qué sideEffects: false importa tanto

Considerá este módulo:

// analytics.js
export function trackear(evento) { /* ... */ }

// ⚠️ esto corre en el momento en que el módulo se IMPORTA
window.__analytics_listo = true;
document.addEventListener("click", registrarClick);

Si nadie usa trackear, ¿el bundler puede borrar el módulo entero? No: tiene efectos de nivel superior que alguien podría estar esperando. Ante la duda, el bundler conserva. Multiplicá esa duda por 800 módulos de node_modules y ahí está tu bundle inflado.

// package.json — la declaración que resuelve la duda
{
  "sideEffects": false
}

// O, lo correcto en el 90% de los casos reales: declarar las excepciones.
{
  "sideEffects": ["*.css", "*.scss", "./src/polyfills.js"]
}
⚠️ El error que se paga en producción. Poner "sideEffects": false en un paquete que importa CSS es la forma más rápida de que los estilos desaparezcan del build de producción y solo del de producción. En desarrollo no hay tree shaking, así que todo se ve bien; el bug aparece recién en el deploy. Un import "./boton.css" no exporta nada, así que el bundler lo considera código muerto y lo borra. La declaración correcta es "sideEffects": ["*.css"].

Los cuatro límites reales

LímiteQué pasaQué hacer
Barrel filesUn index.ts que re-exporta 300 módulos obliga a evaluarlos todos para resolver unoImportar por subpath: from "lib/boton", no from "lib"
CommonJS en el caminoSin análisis estático, entra el paquete completoBuscar la versión ESM, o aislar la dependencia en un chunk perezoso
Clases con métodosSe sacuden mucho peor que las funciones sueltas: el bundler no puede saber qué método se llamaPreferir funciones exportadas por separado en código de librería
Efectos que el compilador no veUn Object.defineProperty, un decorador, un polyfill, un import por su efectoAnotar con /*#__PURE__*/ lo que sí es puro
 
// La anotación que le da permiso al bundler para borrar
// Sin ella, el bundler asume que crear el cliente puede tener efectos.
export const cliente = /*#__PURE__*/ crearCliente({ url: API });

// Barrel vs subpath: el mismo componente, muy distinto costo
import { Boton } from "@empresa/ui";          // ❌ evalúa el índice completo
import { Boton } from "@empresa/ui/boton";    // ✅ solo ese módulo

Cómo comprobar qué quedó adentro (no adivinar)

Hay dos preguntas distintas y se responden con herramientas distintas:

# 1. "¿QUÉ hay en mi bundle?" — análisis estático del build
npx vite-bundle-analyzer                    # treemap interactivo
grep -c "nombreDeLaFuncion" dist/assets/*.js   # la comprobación bruta y honesta

# 2. "¿Qué se EJECUTA de lo que hay?" — Coverage, en el navegador
#    DevTools → Ctrl+Shift+P → "Show Coverage" → recargar
#    Te da el % de bytes no usados por archivo. Es la métrica que importa.
Coverage no es una lista de código para borrar. Un 70% de "código no usado" en la carga inicial puede ser perfectamente correcto: es el manejador del formulario que el usuario todavía no abrió. Coverage responde "¿esto tenía que descargarse AHORA?", no "¿esto sirve?". Lo que señala un porcentaje alto no es código muerto: es una oportunidad de code splitting.

FS7.4 Code splitting: menos requests contra mejor caché

Cortar el grafo en varios archivos tiene tres criterios útiles, y se combinan:

1. Por ruta

// El import() dinámico es la única instrucción que necesitás saber:
// crea un punto de corte en el grafo y devuelve una promesa.
const Dashboard = lazy(() => import("./rutas/Dashboard"));
const Reportes  = lazy(() => import("./rutas/Reportes"));

// Todo lo que Dashboard importe —y nada más— va a su propio chunk.

2. Por interacción

// El caso de mayor retorno: una librería pesada detrás de un click.
// El editor de texto enriquecido pesa 280 KB y lo usa el 4% de las sesiones.
async function abrirEditor() {
  const { montarEditor } = await import("./editor-pesado");
  montarEditor(contenedor);
}

// 🎯 Precarga en hover: el usuario no percibe la espera
boton.addEventListener("mouseenter", () => import("./editor-pesado"), { once: true });
El mouseenter compra entre 150 y 400 ms de ventaja: es el tiempo promedio entre que el puntero entra en un botón y el click efectivo. En móvil el equivalente es touchstart, que adelanta unos 80–100 ms respecto del click. Es la optimización de mejor relación esfuerzo/resultado de todo este módulo.

3. Vendor chunks — y por qué el gigante es una trampa

La idea intuitiva es: "las dependencias cambian poco, van a un archivo aparte que el usuario cachea para siempre". La idea es correcta. La implementación ingenua no:

// ❌ El vendor monolítico
// Un solo archivo de 420 KB con react, react-dom, lodash, recharts,
// date-fns y 40 paquetes más.
manualChunks(id) {
  if (id.includes("node_modules")) return "vendor";
}
Por qué esto se rompe. Los nombres de archivo llevan un hash del contenido: vendor.a3f9c1.js. Si actualizás una sola dependencia —un patch de date-fns— el contenido cambia, el hash cambia, y los 420 KB completos se vuelven a descargar para todos tus usuarios. Un chunk de vendor gigante convierte cada actualización menor en una invalidación total de caché. 
// ✅ Vendor segmentado por frecuencia de cambio
manualChunks(id) {
  if (!id.includes("node_modules")) return;
  // Núcleo: cambia dos veces por año
  if (/[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/.test(id)) return "core";
  // Librerías pesadas de un solo uso: que vivan en su propio chunk
  if (id.includes("recharts") || id.includes("d3-")) return "charts";
  // El resto
  return "vendor";
}

El trade-off, con números

EstrategiaRequestsReutilización de cachéCuándo conviene
1 solo bundle10% tras cualquier cambioLanding estática, app < 150 KB
App + 1 vendor grande2Alta… hasta que actualizás algoCasi nunca. Es el default que hay que revisar
Por ruta + vendor segmentado4–8 en la rutaAlta y estableEl default sano de una SPA real
Granularidad extrema (> 30 chunks)30+Máxima en teoríaContraproducente: cadena de requests, overhead por archivo
Con HTTP/2 y HTTP/3 el costo de un request extra bajó muchísimo (multiplexado sobre una conexión), pero no llegó a cero: cada chunk paga su compresión por separado —comprimir 10 archivos de 20 KB da más bytes que uno de 200 KB— y, sobre todo, los chunks anidados crean cadenas de descubrimiento: el navegador no sabe que necesita C hasta que descargó y parseó B. Esa latencia en serie es lo que arruina el LCP, no la cantidad de archivos en sí. Con conexión móvil de 150 ms de RTT, tres niveles de anidamiento son casi medio segundo de nada. 
// Romper la cadena: declarar en el HTML lo que se sabe que hace falta
// <link rel="modulepreload" href="/assets/core.a3f9.js">
//
// modulepreload descarga Y parsea el módulo en paralelo, sin ejecutarlo.
// Es la diferencia entre descubrir el chunk en el paso 3 o en el paso 1.

FS7.5 Analizar el bundle: cómo se lee un treemap

Un treemap muestra el bundle como rectángulos anidados donde el área es proporcional al tamaño. Es la herramienta con la que se responde "¿por qué pesa 940 KB?" en cinco minutos en vez de en dos días.

# Opción A — treemap interactivo, funciona con Vite/Rollup/Rolldown
npx vite-bundle-analyzer

# Opción B — plugin en el config, se genera con cada build
npm i -D rollup-plugin-visualizer

# Opción C — reporte JSON del propio Rolldown, ideal para CI
#   bundleAnalyzerPlugin() emite chunks, módulos, dependencias y alcanzabilidad

# Opción D — la clásica, parte del source map en vez del grafo
npx source-map-explorer 'dist/assets/*.js'
📌 Leé el treemap en este orden. (1) Los 3 rectángulos más grandes: ahí está el 60% del problema. (2) Buscá el mismo nombre dos veces: son versiones duplicadas. (3) Mirá qué hay en el chunk de entrada que no debería estar ahí. (4) Recién después, el resto. La tentación de empezar por lo chico y "prolijo" es fuerte y es una pérdida de tiempo.

Las tres sorpresas de siempre

1. La librería de fechas con todos los idiomas. El caso arquetípico es moment, que empaqueta ~160 locales por defecto y suma unos 230 KB minificados cuando tu app está solo en español. Está deprecado desde 2020 y sigue apareciendo, casi siempre como dependencia transitiva de otra cosa. El reemplazo moderno es date-fns (modular, ESM, tree-shakeable) o directamente Intl.DateTimeFormat, que ya está en el navegador y pesa 0 KB.
2. El pack de iconos entero. import { IconoUsuario } from "@paquete/icons" con un barrel de 4.000 iconos puede meter 180–200 KB para dibujar tres flechitas. Se detecta al instante en el treemap: un rectángulo enorme, uniforme, con cientos de módulos diminutos adentro.
3. La misma librería en dos versiones. Tu app usa date-fns@4 y una dependencia trae date-fns@2. npm las anida en distintos node_modules, el bundler las trata como paquetes distintos y las incluye a las dos. Es peso puro, sin ningún beneficio.
# Detectar duplicados ANTES de mirar el treemap
npm ls date-fns          # muestra el árbol y todas las versiones instaladas
npx npm-why date-fns     # explica QUIÉN pidió cada versión

# Forzar una sola versión (npm 8.3+)
#   package.json:
#   "overrides": { "date-fns": "^4.1.0" }
#
# En pnpm: "pnpm": { "overrides": { ... } }   ·   En yarn: "resolutions"
Un override es una promesa que hacés vos. Le estás diciendo al gestor de paquetes "usá esta versión aunque la dependencia haya pedido otra". Si hubo cambios incompatibles entre v2 y v4, rompés en runtime y no en el build. Antes de forzar, leé el changelog de las APIs que la dependencia realmente usa, y dejá un test que ejercite ese camino.

FS7.6 La generación en Rust y Go: qué cambió de verdad

Entre 2020 y 2026 toda la cadena de herramientas se reescribió en lenguajes compilados. No fue moda: fue que las dos etapas más caras del build eran paralelizables y Node.js no podía paralelizarlas.

HerramientaLenguajeQué esEstado en 2026
esbuildGoBundler + transformador + minificador. El que abrió la puerta en 2020Vivo y sólido, pero fuera del core de Vite desde la v8
SWCRustTransformador (reemplazo de Babel). No es un bundlerEstable; es la base de compilación de Next.js
OxcRustParser, linter, transformador y minificadorTransformador estable; minificador todavía alpha pero ya supera a esbuild en tamaño de salida. Es el compilador de Vite 8
RolldownRustBundler, drop-in de la API de Rollup1.0 estable (mayo 2026). Bundler único de Vite 8
RspackRustBundler compatible con la config y los loaders de webpackEstable. La ruta de migración para monolitos webpack
TurbopackRustBundler incremental (cachea a nivel de función, no de archivo)Estable y por defecto en Next.js 16, en dev y en build

Vite 8: el cambio que ya te afecta

💡 Qué pasó exactamente. Vite tenía una arquitectura de dos bundlers: esbuild para el dev server (velocidad) y Rollup para producción (calidad de salida y ecosistema de plugins). Eso significaba que dev y prod nunca eran idénticos. Vite 8, publicado el 12 de marzo de 2026, reemplazó a los dos por Rolldown — un bundler en Rust construido como reemplazo directo de la API de Rollup — y usa Oxc para transformar y minificar. Un solo motor para dev y prod, por primera vez. No es opcional: es el comportamiento por defecto y único. 
# Requisitos de Vite 8 — los mismos que Vite 7
node -v          # se necesita Node 20.19+ o 22.12+

npm create vite@latest mi-app
npm i vite@latest        # a septiembre de 2026, la línea 8.2.x

# Migración desde Vite 7 en dos pasos, si el proyecto es complejo:
#   1. npm i -D rolldown-vite   → Vite 7 con el bundler nuevo, para detectar roturas
#   2. después sí, subir a Vite 8

Los números, y lo que cuestan

Caso medidoAntesDespués
Benchmark del equipo de Vite (19.000 módulos)40,10 s (Rollup)1,61 s (Rolldown) ≈ 25×
Linear46 s6 s
Beehiiv—−64% de tiempo de build
Ramp—−57%
Mercedes-Benz.io—−38%
⚠️ Qué se resigna. Esto no aparece en los anuncios. (1) El puente JS↔Rust cuesta. Un plugin escrito en JavaScript obliga a serializar datos en cada hook: si tenés un plugin que toca los 3.000 módulos, buena parte de la ganancia se evapora ahí. (2) Los plugins que manipulaban el AST de Rollup son los que más probabilidades tienen de romper. (3) El minificador de Oxc sigue en alpha: comprime mejor que esbuild, pero un caso raro puede darte una salida distinta de la que esperabas — hay que probar el build de producción, no solo confiar. (4) Los mensajes de error cambiaron, y depurar el bundler mismo es más opaco cuando el stack trace muere en Rust.
Regla práctica para 2026. Proyecto nuevo con Vite: no pensás en nada, ya tenés Rolldown. Proyecto Next.js: no pensás en nada, ya tenés Turbopack. Monolito con webpack y 60 loaders: la migración barata es Rspack, que lee tu configuración casi sin cambios, no reescribir todo a Vite. Y si tu build ya tarda 20 segundos, migrar por velocidad es optimizar donde no duele.

FS7.7 El dev server: por qué arranca instantáneo y el build no

La pregunta que casi nadie se hace: si npm run build tarda 40 segundos, ¿por qué npm run dev levanta en 300 ms? Porque en desarrollo no se bundlea.

La analogía. El build de producción es cocinar el banquete entero antes de que llegue el primer invitado: todo tiene que estar listo, optimizado y emplatado. El dev server es un restaurante à la carte: no cocina nada hasta que alguien lo pide. Por eso abre en un minuto y por eso el primer plato de cada mesa tarda un poquito más. 
# Lo que realmente pasa cuando abrís localhost:5173
#
# 1. El navegador pide index.html
# 2. Ve  <script type="module" src="/src/main.tsx">  y lo pide
# 3. El servidor transforma SOLO ese archivo (TS → JS) y lo devuelve
# 4. El navegador ve sus import y pide cada uno
# 5. Repetir
#
# Nunca se construye el grafo completo. Solo se transforma lo que
# la ruta que estás mirando efectivamente necesita.

El pre-bundling de dependencias, y por qué existe

Si el dev server no bundlea nada, ¿por qué la primera vez tarda unos segundos "optimizando dependencias"? Porque hay una excepción, y tiene una razón concreta:

// lodash-es publica cada función como un módulo aparte.
// Sin pre-bundle, esta línea genera ~600 peticiones HTTP al dev server.
import { debounce } from "lodash-es";

// Vite lo convierte UNA vez a un solo módulo ESM cacheado en
// node_modules/.vite/deps/  →  1 petición en vez de 600.
# Cuándo tenés que forzar el re-optimizado
rm -rf node_modules/.vite      # el martillo
npm run dev -- --force         # el bisturí

# Síntoma típico de caché rancia: "Failed to resolve import" en una
# dependencia que existe perfectamente, justo después de un npm install.

HMR: por qué no perdés el estado

El Hot Module Replacement no recarga la página: reemplaza el módulo que cambiaste y propaga la invalidación hacia arriba en el grafo hasta encontrar un límite HMR — un módulo que sabe re-aplicarse a sí mismo. En React ese límite lo pone Fast Refresh en cada componente. Por eso editás un botón y el formulario a medio llenar sigue ahí.

Por qué a veces "el HMR no anda" y recarga toda la página. Porque el módulo que tocaste no tiene límite: exportás un componente y además una constante desde el mismo archivo, o exportás algo con export default anónimo, o el archivo es un store global que nadie sabe cómo re-aplicar. La invalidación sube hasta la raíz y no queda otra que recargar. La solución es aburrida y funciona: un componente por archivo, y las constantes en un módulo aparte.
⚠️ Dev y prod ejecutan código distinto — este es el bug de "solo pasa en producción". En el dev server no hay tree shaking, no hay minificación, el orden de evaluación puede diferir y las variables de entorno se reemplazan de otra forma. Un componente que funciona diez horas en dev puede romper en el primer deploy. La disciplina que ahorra tardes enteras es correr npm run build && npm run preview localmente antes de cada merge a main, y tener al menos un smoke test E2E que corra contra el build de producción, no contra el dev server.

FS7.8 Source maps: cómo depurar producción sin regalar el código

Un source map es un archivo JSON que traduce "línea 1, columna 48.312 de index.a3f9.js" a "línea 27 de CarritoDeCompras.tsx". Sin él, un stack trace de producción es ruido. Con él —mal servido— es tu código fuente completo, público.

El sourcemaps inject del ejemplo no es decorativo: inserta un Debug ID único en el bundle y en el mapa, para que el servicio de errores los aparee por identificador y no por nombre de archivo. Sin eso, cualquier cambio de hash o de ruta de CDN te deja stack traces sin desminificar, que es exactamente el escenario en el que no querés estar a las 3 de la mañana.

En su segunda oleada afectó decenas de miles de repositorios. En mayo de 2026 volvió una variante que comprometió más de 170 paquetes de npm y, por primera vez, cruzó a PyPI en la misma operación. Ninguna de estas víctimas hizo nada mal: solo tenían la dependencia instalada.

Cómo evaluar una dependencia en 3 minutos

1. Pesala primero. Pegá el import en bundlejs.com y mirá el tamaño tree-shaken y comprimido con Brotli — no el número de "unpacked size" de npm, que incluye tests y docs y no significa nada para tu bundle.
2. Miralas todas. npm ls --all <paquete> antes de instalar (o npx howfat <paquete>). Un helper de 3 KB que arrastra 40 transitivas es un helper de 40 transitivas.
3. ¿Es ESM con exports y sideEffects? Si no, asumí que entra entero al bundle y decidí con ese número, no con el optimista.
4. ¿Está viva? Fecha del último publish, issues abiertos sin respuesta, y —la métrica que más importa y menos se mira— cuántas personas pueden publicar. Un solo mantenedor es un solo phishing.
5. ¿Ya está en la plataforma? Intl para fechas y números, structuredClone para clonar hondo, crypto.randomUUID(), URLSearchParams, Array.prototype.at, fetch. Media docena de dependencias clásicas hoy pesan 0 KB porque el navegador ya las trae.

Cuándo escribir las 40 líneas vos mismo

// Esto es una dependencia entera de muchos proyectos.
// Son 9 líneas y no tiene casos borde ocultos.
export function debounce(fn, ms = 300) {
  let t;
  return function (...args) {
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), ms);
  };
}

// Y esto reemplaza a una librería de 12 KB:
export const clases = (...xs) => xs.filter(Boolean).join(" ");
📌 El criterio, en una línea. Escribilo vos si el problema es pequeño, cerrado y lo entendés completo: debounce, un formateador de clases, un slug simple. Usá la librería si el problema tiene casos borde que no ves desde acá: fechas con zonas horarias y DST, i18n y pluralización, criptografía, parsing de cualquier cosa, accesibilidad de widgets complejos (combobox, date picker, modal con foco atrapado). Reimplementar un date picker accesible no es ahorrar 30 KB: es firmar un contrato de mantenimiento de por vida con vos mismo.

Ningún bundle pasa de 180 KB a 940 KB en un commit. Pasa en cuarenta commits de 19 KB cada uno, todos razonables, revisados y aprobados. Un presupuesto es simplemente hacer visible ese crecimiento en el momento en que ocurre, que es el único momento en que sale barato arreglarlo.

FS7.11 Cuándo NO tenés que optimizar el build

La mitad del contenido de este módulo no aplica a la mayoría de los proyectos, y decirlo es parte de saberlo.

1. El bundle ya es chico. Si el JS inicial pesa menos de 150 KB comprimido, code splitting agresivo te va a dar menos de lo que te va a costar en complejidad y en cadenas de requests. Un solo archivo bien cacheado le gana a seis chunks bien pensados.
2. El problema está en el servidor. Abrí la pestaña Network y mirá el waterfall. Si el HTML tarda 1,4 s en el TTFB y el JS descarga en 80 ms, tu bundle no es el problema: es una query N+1, un cold start, o un origen sin CDN. Optimizar el bundle ahí es pulir el volante de un auto sin motor.
3. El build tarda 20 segundos. Migrar de herramienta para bajarlo a 6 no cambia la vida de nadie. Vale la pena cuando el build tarda minutos, cuando bloquea el CI, o cuando el HMR se siente lento en el día a día — eso último sí se paga cincuenta veces por día.
4. La audiencia es interna y conocida. Un panel de administración que usan 30 personas por LAN, con máquinas de escritorio y conexión estable, no necesita el mismo presupuesto de bytes que un e-commerce en 4G. El costo del peso extra es real pero chico; el costo de la complejidad que agregás es el mismo que en cualquier lado.
📌 El orden correcto siempre. Medir → encontrar el cuello de botella → arreglar ese → volver a medir. Optimizar el build sin haber mirado un waterfall y un treemap no es ingeniería: es superstición con buena reputación.

Checkpoint — ¿lo tenés claro?

Tenés una dependencia ESM, con sideEffects: false, y aun así entra entera en el bundle. ¿Qué revisás?

Primero, cómo la importás: si es un barrel (from "lib" en vez de from "lib/boton"), el bundler tiene que evaluar el índice completo para resolver un solo símbolo, y basta con que un módulo de ese índice tenga efectos para que la cadena entera se conserve. Segundo, si hay un intermediario CommonJS: un wrapper propio o un paquete de la empresa que sea CJS corta el análisis estático y todo lo que pase por él entra completo, sin importar lo prolija que sea la dependencia final. Tercero, si la declaración es honesta: sideEffects: false en un paquete que en realidad registra cosas en window o importa CSS es una promesa falsa, y algunos bundlers detectan efectos reales y conservan igual. Lo comprobás en el treemap, no razonando: si el rectángulo sigue ahí después de cambiar el import a subpath, el problema estaba una capa más arriba.

¿Por qué un vendor chunk único de 400 KB puede ser peor que tres chunks de 130 KB?

Por la invalidación de caché. El nombre del archivo lleva un hash del contenido, así que actualizar una sola dependencia cambia el hash y obliga a todos tus usuarios a redescargar los 400 KB completos. Con tres chunks segmentados por frecuencia de cambio —el núcleo React que se toca dos veces al año, las librerías pesadas de uso puntual, y el resto— una actualización menor invalida solo el chunk que cambió, y los otros dos siguen sirviéndose desde la caché del navegador. El costo de la segmentación son dos requests más, que con HTTP/2 son baratos, y una compresión levemente peor por tener menos contexto compartido. Con deploys frecuentes, ese intercambio conviene casi siempre. Donde no conviene es en granularidad extrema: pasando los ~30 chunks empiezan a pesar el overhead por archivo y, sobre todo, las cadenas de descubrimiento en serie.

El build de producción rompe y el dev server anda perfecto. ¿Cuáles son las tres causas más probables?

(1) Tree shaking: algo se eliminó porque parecía código muerto — el caso clásico es el CSS borrado por un sideEffects: false mal declarado, o un módulo que solo se importaba por su efecto lateral. En dev no hay tree shaking, por eso no se ve. (2) Minificación: código que depende de Function.prototype.name, de nombres de clase en runtime, o de comparar constructor.name se rompe cuando el minificador renombra todo a una letra. (3) Variables de entorno y modo: import.meta.env se reemplaza literalmente en el build, y una variable que existía en tu .env local pero no en el CI queda como undefined incrustado en el bundle — el fallo aparece lejos de la causa. La disciplina que las previene a las tres es correr npm run build && npm run preview localmente antes del merge, y tener un smoke test E2E que corra contra el build de producción y no contra el dev server.

Resumen ejecutivo

  • Un bundler construye un grafo de módulos (entry → resolución → transformación → chunks) y después lo corta. Todo lo demás se deduce de esas dos operaciones.
  • El análisis estático de ESM es lo que habilita tree shaking, splitting automático e import() analizable. Un solo intermediario CommonJS en el camino desactiva todo eso para lo que pase por él.
  • Tree shaking elimina lo que puede demostrar que no se usa y que no tiene efectos. Sus enemigos son los barrel files, CommonJS y los efectos de nivel superior. sideEffects: false en un paquete con CSS borra tus estilos solo en producción.
  • Code splitting: por ruta, por interacción (con precarga en mouseenter) y vendor segmentado por frecuencia de cambio. Un vendor monolítico convierte cada patch en una invalidación total de caché.
  • El treemap responde "¿por qué pesa tanto?" en minutos. Las tres sorpresas de siempre: fechas con todos los locales, un icon pack entero por un barrel, y la misma librería en dos versiones.
  • 2026: Vite 8 (marzo) usa Rolldown como bundler único —esbuild y Rollup salieron del core— con Oxc de compilador; Rolldown 1.0 es estable desde mayo. Next.js 16 tiene Turbopack estable y por defecto en dev y build. El costo: el puente JS↔Rust se paga por hook, algunos plugins de AST rompen, y el minificador de Oxc todavía es alpha.
  • El dev server no bundlea: transforma bajo demanda. Por eso arranca instantáneo y por eso dev ≠ prod. Corré build && preview antes de mergear.
  • Source maps en producción: hidden, subidos al servicio de errores con Debug ID y borrados del artefacto público. Verificá con un curl que el .map dé 404.
  • Una dependencia cuesta peso, transitivas, mantenimiento, acoplamiento y superficie de supply chain. Lockfile commiteado, npm ci --ignore-scripts y cuarentena por antigüedad son mitigaciones baratas frente a ataques que en 2025-2026 dejaron de ser hipotéticos.
  • Los presupuestos funcionan cuando informan el delta contra main y tienen dueño; se vuelven ruido cuando se fijan al número exacto de hoy.
  • No optimices si el bundle ya es chico, si el cuello está en el servidor, o si el build tarda 20 segundos. Medí primero: waterfall y treemap antes que cualquier cambio.

🧠 Autoevaluación

1. Publicás una librería de componentes, ponés "sideEffects": false en el package.json y de golpe las apps que la consumen pierden todos los estilos solo en producción. ¿Qué pasó?

Un import de CSS existe solo por su efecto lateral — no exporta ningún símbolo que alguien referencie. Al declarar sideEffects: false le prometiste al bundler que ningún módulo tiene efectos, así que eliminó esos imports con toda razón. Aparece solo en producción porque el dev server no hace tree shaking. La declaración correcta es la lista de excepciones: "sideEffects": ["*.css"].

2. Tu build de producción con Vite 8 tarda 4 segundos y el bundle inicial pesa 610 KB comprimido. El equipo propone migrar a otra herramienta "porque es más rápida". ¿Cuál es la objeción correcta?

Son dos métricas distintas y se confunden todo el tiempo. Un bundler más rápido mejora tu ciclo de desarrollo y el tiempo de CI; no cambia cuántos bytes descarga el usuario, porque eso lo determinan tus imports y tus dependencias. Con 4 segundos de build no hay dolor que justifique una migración, y con 610 KB sí hay un problema real que se ataca con treemap, code splitting y deduplicación. Optimizar la métrica equivocada es el error más caro de este módulo.

3. Necesitás desminificar los stack traces de producción sin publicar tu código fuente. ¿Cuál es la configuración correcta?

'hidden' es exactamente el modo que existe para este caso: produce el mapa pero omite el comentario //# sourceMappingURL, así que ningún navegador lo pide. Se sube al servicio de errores —idealmente con Debug ID inyectado, para que el apareo no dependa del nombre de archivo— y se borra de dist/ antes de publicar. 'inline' es lo opuesto de lo que se pide: incrusta el código fuente completo en el archivo que servís, y encima multiplica su tamaño. Y false te deja sin ninguna forma de leer un error en producción.
