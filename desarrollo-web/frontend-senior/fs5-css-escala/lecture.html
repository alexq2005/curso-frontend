FS5 — CSS a escala: arquitectura y la plataforma moderna

FS5.0 Por qué este módulo

El CSS de un proyecto viejo casi nunca se rompe. Se pudre. Nadie borra una regla, porque nadie puede probar que no la usa nadie; entonces el archivo solo crece. Cada sprint agrega selectores y ninguno saca. A los dos años tenés 240 KB de hoja de estilos donde el 60% no se aplica a nada, hay tres escalas de espaciado conviviendo, y para cambiar el color de un botón hace falta un !important porque en algún lado alguien escribió #app .sidebar ul li a.btn.

💡 La tesis del módulo. El problema del CSS a escala no es la sintaxis: la sintaxis la aprendiste en M03. El problema es que el CSS, por diseño, es global y sin límites. Cualquier regla puede afectar a cualquier elemento del documento, y nada en el lenguaje te avisa cuándo cruzaste una frontera que no existía. Todo lo que vas a ver acá —capas, scoping, contenedores, convenciones de nombres, herramientas de build— es una respuesta a la misma pregunta: ¿cómo le pongo límites a algo que nació sin ellos?

La buena noticia es que la plataforma cambió mucho entre 2023 y 2026. Cosas que antes requerían una herramienta —ordenar la cascada, hacer que un componente responda a su contenedor y no a la ventana, tipar una variable para poder animarla— ahora son CSS nativo y con soporte real. La mala noticia es que cada una de esas herramientas tiene un costo, y la mayoría de los artículos que las presentan solo cuentan la mitad linda.

Qué NO es este módulo. Los fundamentos de CSS (M03) y el layout con Flexbox y Grid (M04) se dan por sabidos. Acá no explicamos qué es display: grid: explicamos por qué tu grilla de tarjetas no se puede reutilizar en el sidebar, y qué mecanismo de 2023 resuelve exactamente eso.

FS5.1 La cascada de verdad

Casi todo el mundo cree que la cascada es "gana el más específico, y si empata gana el último". Eso es el final del algoritmo, no el algoritmo. El orden real de desempate que aplica el navegador, de mayor a menor prioridad, es este:

#CriterioQué significa en la práctica
1Origen e importanciaTransiciones activas → !important del navegador → !important del usuario → !important del autor → animaciones activas → normal del autor → normal del usuario → normal del navegador
2ContextoLos estilos del árbol de luz le ganan a los del Shadow DOM (y al revés con !important)
3Atributo styleEl estilo inline le gana a cualquier hoja del mismo origen
4Capas en cascadaLa capa declarada después gana. Lo no encapado gana sobre todas las capas
5EspecificidadLa terna (ids, clases, tipos)
6Proximidad de scopeCon @scope: gana la regla cuyo scope raíz está más cerca del elemento
7Orden de apariciónLa última declaración que llegó

Fijate dónde está la especificidad: quinta. Cuatro criterios se resuelven antes. Eso es lo que hace que @layer sea tan potente y también tan peligroso si no lo entendés: mueve la pelea del criterio 5 al criterio 4, donde vos controlás el orden con una sola línea.

Especificidad: la aritmética que sí importa

La especificidad es una terna (a, b, c) que se compara de izquierda a derecha, sin acarreo: 11 clases nunca le ganan a un id.

/* (a=ids, b=clases/atributos/pseudo-clases, c=tipos/pseudo-elementos) */

a                        /* (0,0,1) */
.btn                     /* (0,1,0) */
a.btn                    /* (0,1,1) */
#app .btn                /* (1,1,0) */
.card > .title           /* (0,2,0) — el combinador no suma nada */
li:nth-child(2)          /* (0,1,1) */
::before                 /* (0,0,1) */

/* Las tres pseudo-clases funcionales que cambian la aritmética */
:where(.a, #b, .c)       /* (0,0,0) — SIEMPRE cero, pase lo que pase adentro */
:is(.a, #b, .c)          /* (1,0,0) — el MÁXIMO de la lista */
:not(.a, #b)             /* (1,0,0) — el MÁXIMO de la lista */
h2:has(> img)            /* (0,0,1) + el máximo de adentro → acá (0,0,2) */
📌 :where() es la herramienta más subvalorada del CSS moderno. Te deja escribir selectores complejos que no pesan nada en la cascada. Un reset o una librería de componentes escrita con :where() se puede sobreescribir con una sola clase, sin !important y sin importar el orden de los archivos. Si publicás CSS que otros van a consumir, envolvé tus selectores base en :where() y les regalás la vida. 
/* Reset agresivo, especificidad CERO: cualquiera lo pisa con una clase */
:where(h1, h2, h3, h4, p, ul, ol, figure, blockquote) {
  margin-block: 0;
}

/* El consumidor hace esto y funciona, sin importar el orden de carga */
.prosa p { margin-block: 1rem; }   /* (0,2,0) vs (0,0,0) → gana siempre */

Por qué !important es un síntoma

!important no es "prioridad alta". Es cambiar de banda de origen: la declaración se muda a la banda 4 de la tabla de arriba, donde compite con otros !important de autor. Por eso la escalada es inevitable: si el único mecanismo para ganar es mudarse de banda, y ya estás todos en la misma banda, la única salida que queda es la especificidad… dentro de la banda de los importantes. Y ahí volvés al punto de partida, pero con más ruido.

El diagnóstico correcto. Cada !important en tu código responde a una de estas tres causas, y cada una tiene una cura distinta que no es !important:
  • Estoy peleando contra una librería de terceros → cura: @layer, meterla en una capa baja.
  • Estoy peleando contra código mío de otro archivo → cura: @layer o bajar la especificidad del origen con :where().
  • Estoy peleando contra un estilo inline que pone JavaScript → cura: que el JS toque una clase o una custom property, no element.style. Este es el único caso donde !important a veces es la respuesta honesta.
Métrica de salud, no de estilo. Contá los !important de tu proyecto y ponelo en el CI como un número que no puede subir. No hace falta que baje a cero: hace falta que agregar uno nuevo sea una decisión consciente y no un reflejo. Un grep -c '!important' en el bundle final es el chequeo de arquitectura CSS más barato que existe.

FS5.2 @layer: ordenar la cascada sin pelear especificidad

Las capas en cascada (@layer) son, de todo lo que llegó en los últimos años, lo que más cambia la arquitectura de un proyecto grande. Son Baseline widely available desde septiembre de 2024 (Chrome/Edge 99, Firefox 97, Safari 15.4, todas de principios de 2022), con más del 96% de cobertura global.

La idea es simple: vos declarás un orden de prioridad entre grupos de estilos, y ese orden gana antes que la especificidad. Un selector de un solo carácter en una capa alta le gana a un monstruo de cinco ids en una capa baja.

/* Una sola línea, arriba de todo del archivo de entrada.
   Define el orden de prioridad: de MENOR a MAYOR. */
@layer reset, vendor, base, layout, components, utilities;

@layer vendor {
  /* Bootstrap, un date picker, lo que sea */
  #app .navbar .nav-link.active { color: #0d6efd; }   /* (1,3,0) */
}

@layer components {
  .nav-link { color: var(--brand); }                   /* (0,1,0) */
}

/* La regla de `components` GANA, aunque su especificidad sea 30 veces menor,
   porque `components` se declaró después de `vendor`. */

Las cuatro reglas que tenés que saber de memoria

1. El orden se define en la primera declaración de cada nombre. Por eso conviene declarar todas las capas vacías, en una línea, arriba de todo. Si no lo hacés, el orden lo determina el orden de aparición de los bloques, que depende del orden de tu bundler — es decir, el azar.
2. Lo no encapado le gana a TODAS las capas. Cualquier regla que esté fuera de un @layer se comporta como si estuviera en una capa implícita al final del stack. No es un bug: es la propiedad que hace posible migrar sin big bang.
3. !important invierte el orden de las capas. Entre declaraciones importantes, la capa declarada primero gana, y lo no encapado importante pierde contra todo lo encapado importante. Es coherente (el reset importante debería ser el más fuerte) y es profundamente contraintuitivo la primera vez.
4. Las capas anidan. @layer components.card { } crea la subcapa card dentro de components, y su orden solo compite con sus hermanas. Sirve para que cada equipo maneje su propio orden interno sin tocar el global.
⚠️ El error que te va a morder. Migrás medio proyecto a capas, todo funciona, y una semana después alguien agrega un archivo nuevo sin envolverlo en @layer. Ese archivo pisa todo tu sistema, incluidas las utilidades, y el bug se reporta como "el margen del botón está mal en una sola página". La defensa es un lint que exija que todo archivo de la carpeta styles/ empiece con @layer, o —más simple— que el archivo de entrada importe todo con layer() y ningún módulo se importe suelto.

Cómo se migra un proyecto que ya existe (sin big bang)

Esta es la parte que casi nunca se cuenta, y es la razón principal para adoptar capas. La regla 2 —lo no encapado gana— convierte la migración en algo incremental y reversible:

/* PASO 1 — main.css. No cambia NADA visualmente.
   Todo tu CSS actual sigue sin encapar, y por lo tanto sigue ganando. */
@layer reset, vendor, base, components, utilities;

@import url("./legacy/todo-lo-viejo.css");   /* sin layer(): sigue arriba de todo */
/* PASO 2 — Meté los terceros en la capa más baja.
   Acá empiezan a sobrar los !important que existían solo para ganarle a Bootstrap. */
@import url("bootstrap/dist/css/bootstrap.css") layer(vendor);
@import url("flatpickr/dist/flatpickr.css")     layer(vendor);
/* PASO 3 — Migrá componente por componente, a medida que los tocás.
   Cada componente que entra a una capa puede perder sus !important. */
@layer components {
  @import url("./components/card.css");
  @import url("./components/button.css");
}
El truco de oro de la migración: mové primero lo que no controlás (vendor) y último lo que más se toca (utilities). Cada paso es un PR chico, con un solo criterio de aceptación —"ninguna captura visual cambió"— y con revert de una línea. Nunca vas a tener el proyecto "a medio migrar y roto", porque en cada estado intermedio lo no encapado sigue mandando.
El costo real de las capas. Tres, y ninguno es de rendimiento:
  • Un @import crudo en el navegador cuesta un round-trip serializado (el navegador no descubre el archivo importado hasta que parseó el que lo importa). En build está perfecto porque el bundler lo aplana; en producción, jamás sirvas un CSS con @import sin aplanar.
  • Un <link rel="stylesheet"> no se puede encapar. Si cargás la librería con un tag, no hay forma de meterla en una capa: hay que pasarla por @import ... layer() o por el bundler.
  • Debuggear un orden mal declarado es horrible. El síntoma es "esta regla se ve tachada en DevTools y no entiendo por qué": DevTools ya muestra el nombre de la capa junto al origen, pero hay que saber mirarlo.

FS5.3 :has(): el selector padre y lo que cuesta

:has() es la pseudo-clase que rompió una limitación de veinte años: seleccionar un elemento por lo que contiene. Llegó a Baseline newly available en diciembre de 2023 y pasó a Baseline widely available en junio de 2026, así que a esta altura no hay razón para tratarlo como experimental.

Lo que cambia no es "escribir menos JavaScript": es que una clase entera de estado deja de necesitar JavaScript. Antes, para que una tarjeta se viera distinta si tenía imagen, alguien tenía que agregar .card--con-imagen desde el servidor o desde el cliente. Ahora el estado ya está en el DOM y el CSS lo puede leer.

/* 1 — Layout según el contenido: la tarjeta se acomoda sola */
.card:has(> img) { grid-template-columns: 120px 1fr; }
.card:not(:has(> img)) { grid-template-columns: 1fr; }

/* 2 — Validación sin JS: el error se muestra solo si el campo es inválido
       Y el usuario ya lo tocó (nadie quiere ver "error" en un campo vacío) */
.field:has(input:user-invalid) { --borde: var(--danger); }
.field:has(input:user-invalid) .mensaje-error { display: block; }

/* 3 — Combinador de hermano ANTERIOR, que nunca existió */
label:has(+ input:required)::after { content: " *"; color: var(--danger); }

/* 4 — Estado de página desde un elemento cualquiera */
body:has(dialog[open]) { overflow: hidden; }          /* bloquear scroll de fondo */
.layout:has(.sidebar:empty) { grid-template-columns: 1fr; }

/* 5 — Cantidad de hijos, que tampoco existía como selector */
.grid:has(> :nth-child(4)) { --columnas: 2; }         /* 4 hijos o más → 2 columnas */
Especificidad de :has(): aporta la del argumento más específico de su lista, igual que :is(). .card:has(#hero) pesa (1,1,0), no (0,1,0). Si querés el poder de :has() sin el peso, envolvé el argumento: .card:has(:where(#hero)) → (0,1,0).

El costo: no es hacer match, es invalidar

Acá está la parte que los tutoriales saltean. El costo de :has() no está en encontrar los elementos que matchean —eso el navegador lo hace rápido—; está en que :has() invierte la dirección de la invalidación. Normalmente, cuando cambia un elemento, el navegador sabe que solo puede haber afectado a ese elemento y a sus descendientes. Con :has(), cambiar un nodo hoja puede afectar el estilo de cualquier ancestro, así que el motor tiene que subir el árbol comprobando.

/* ⚠️ Caro: cualquier cambio en cualquier parte del documento obliga a
   reevaluar si `body` sigue matcheando. Si esto se togglea en cada scroll,
   se paga un recálculo de estilo sobre TODO el árbol. */
body:has(.panel .item.activo) { --tema: oscuro; }

/* ✅ Barato: el ámbito de invalidación es el propio .panel y sus hijos */
.panel:has(> .item.activo) { --tema: oscuro; }
📌 Tres reglas prácticas para :has().
  1. Acotá el ancestro. Preferí el ancestro más chico que sirva; body:has() y html:has() son la versión cara.
  2. Preferí el combinador hijo (:has(> .x)) al descendiente (:has(.x)): limita el subárbol que hay que vigilar.
  3. Medilo antes de defenderlo. En DevTools → Performance, mirá Recalculate Style durante la interacción sospechosa, y activá Selector Stats en la solapa de experimentos: te da tiempo transcurrido e intentos de match por selector. Un :has() problemático aparece primero en esa lista, no hay que adivinarlo.
El anti-patrón clásico. Alguien reemplaza una clase que ponía JavaScript (document.body.classList.toggle('modal-abierto')) por body:has(dialog[open]) y se siente muy moderno. En este caso puntual está bien, porque dialog[open] cambia dos veces por sesión. Pero si el estado cambia en cada frame —un drag, un scroll, un input— la clase explícita puesta por JS es más barata y más predecible que hacer que el motor de estilos infiera el estado subiendo el árbol.

FS5.4 Container queries: el componente que se puede mover

Una media query pregunta por el viewport. Eso significa que un componente con media queries adentro tiene una dependencia oculta con la página completa. Podés ponerlo en el contenido principal y funciona; lo movés a un sidebar de 320 px y se rompe, aunque la ventana siga midiendo 1440 px. Un componente que responde al viewport no es un componente: es un fragmento de página.

💡 La idea. Las container queries invierten la pregunta: en lugar de "¿cuánto mide la ventana?", el componente pregunta "¿cuánto mido yo?". Con eso, la misma tarjeta se ve en una columna cuando está en un sidebar angosto y en dos columnas cuando está en el contenido ancho, sin que nadie le pase una prop, una clase ni un breakpoint. Son Baseline widely available desde febrero de 2023 en su forma de tamaño (Chrome/Edge 105, Safari 16, Firefox 110). 
/* 1 — El contenedor se declara. Sin esto, no hay a quién preguntarle. */
.card-slot {
  container-type: inline-size;   /* solo mide el ancho: lo normal */
  container-name: tarjeta;       /* opcional pero muy recomendable */
}

/* Atajo equivalente */
.card-slot { container: tarjeta / inline-size; }

/* 2 — El componente pregunta por SU contenedor, no por la ventana */
@container tarjeta (inline-size >= 420px) {
  .card { grid-template-columns: 160px 1fr; }
  .card__resumen { display: block; }
}

@container tarjeta (inline-size < 260px) {
  .card__meta { display: none; }
}

El markup obliga a una separación que no es opcional: el contenedor y el componente tienen que ser elementos distintos, porque un contenedor no puede consultarse a sí mismo. Ese wrapper es el costo estructural de las container queries, y conviene asumirlo desde el diseño del componente en vez de descubrirlo al tercer bug:

<!-- El slot mide; la tarjeta reacciona. Son dos elementos, siempre. -->
<div class="card-slot">
  <article class="card">
    <img class="card__img" src="/p/123.avif" width="320" height="240" alt="">
    <h3 class="card__titulo">Teclado mecánico 65%</h3>
    <p class="card__resumen">Switches lineales, hot-swap, USB-C.</p>
    <p class="card__meta">Envío en 24 h</p>
  </article>
</div>

<!-- La MISMA tarjeta, sin una sola prop distinta, en un sidebar de 280px
     y en una grilla de 900px. Eso es lo que compran las container queries. -->

Las unidades cq*: tipografía relativa al contenedor

Junto con @container llegaron unidades que se resuelven contra el contenedor de consulta más cercano, igual que vw/vh se resuelven contra el viewport:

/* Título que escala con el ancho del contenedor, con techo y piso.
   Reemplaza tres breakpoints por una línea. */
.card__titulo {
  font-size: clamp(1rem, 4cqi, 2rem);
}

⚠️ La trampa número uno: container-type: size te colapsa la altura. Para que el navegador pueda responder una consulta de tamaño antes de haber dispuesto el contenido, el contenedor tiene que tener containment en esa dimensión: su tamaño no puede depender de lo que tiene adentro. Con inline-size eso solo aplica al ancho, que en flujo normal ya viene del padre — no se nota. Con size aplica también al alto, y como el alto normalmente sí depende del contenido, el contenedor colapsa a 0 px. Regla: usá inline-size salvo que tengas una altura explícita y sepas exactamente por qué necesitás cqb.
Los otros tres costos.
  • Un contenedor no se puede consultar a sí mismo. El elemento que declara container-type queda fuera del alcance de su propia @container. Casi siempre hace falta un wrapper, y eso es un div extra en el markup por cada componente responsivo.
  • container-type aplica containment de layout y estilo, lo que puede cambiar comportamientos sutiles: position: fixed de un descendiente pasa a posicionarse contra el contenedor, y los márgenes dejan de colapsar hacia afuera.
  • El nombre es un contrato global. Si no usás container-name, @container se resuelve contra el contenedor más cercano, y anidar dos componentes responsivos produce bugs que se ven como magia negra. Nombrá siempre.

FS5.5 Custom properties a fondo

Las custom properties no son "las variables de Sass pero en CSS". La diferencia es de naturaleza y es la que explica todo lo demás: una variable de Sass se resuelve en build; una custom property se resuelve en el navegador, en tiempo de valor computado, y hereda. Eso las convierte en un canal de comunicación entre padres e hijos que atraviesa componentes, medios, temas y estados.

/* El patrón fundamental: el componente declara SU API pública en variables,
   y el consumidor la configura desde afuera sin tocar los selectores internos. */
.btn {
  --btn-bg: var(--color-brand, #4f46e5);
  --btn-fg: white;
  --btn-pad: 0.6rem 1.1rem;

  background: var(--btn-bg);
  color: var(--btn-fg);
  padding: var(--btn-pad);
}

/* El consumidor NO reescribe .btn: le pasa parámetros por herencia */
.barra-peligro { --btn-bg: var(--color-danger); }
.toolbar-compacta { --btn-pad: 0.3rem 0.6rem; }
📌 La regla de diseño. Un componente bien hecho expone pocas custom properties con nombres estables y mantiene todo lo demás privado. Esas variables son tu API: cambiarles el nombre es un breaking change, igual que renombrar una prop. Documentalas como documentarías una función.

@property: variables tipadas y animables

Una custom property común es, para el motor, una cadena de texto. No sabe que --angulo: 45deg es un ángulo, así que no lo puede interpolar: animarla produce un salto, no una transición. @property registra la variable con un tipo, y con eso desbloquea tres cosas.

@property --angulo {
  syntax: "<angle>";      /* 1. Tipo: ahora el motor sabe interpolarlo */
  inherits: false;         /* 2. Control explícito de la herencia */
  initial-value: 0deg;     /* 3. Valor inicial garantizado */
}

.tarjeta-borde {
  --angulo: 0deg;
  background: linear-gradient(var(--angulo), var(--c1), var(--c2));
  transition: --angulo 400ms ease;   /* ⬅ esto NO funciona sin @property */
}
.tarjeta-borde:hover { --angulo: 180deg; }
Lo que desbloqueaDetalle
Animación e interpolaciónUn <angle>, <color>, <length> o <number> registrado se puede poner en transition y @keyframes
ValidaciónUn valor que no cumple el syntax se descarta y se usa el initial-value, en vez de propagar basura hacia abajo
Control de herenciainherits: false corta la herencia: ideal para variables internas de un componente que no deben filtrarse a los hijos
Estado de @property en 2026 (esto suele contarse mal). Es Baseline newly available desde el 9 de julio de 2024 —Chrome/Edge 85, Safari 16.4, Firefox 128—, y su paso a widely available está proyectado recién para enero de 2027. Traducción práctica: es seguro para mejoras progresivas (una animación más linda), y todavía no para algo de lo que dependa la legibilidad o el layout. Si un usuario con un navegador viejo no ve tu gradiente animado, no pasa nada; si no ve el texto, sí.

Theming sin una línea de JavaScript

El patrón completo son cuatro piezas: color-scheme para que el navegador pinte los controles nativos y la barra de scroll acordes, light-dark() para escribir los dos valores en una sola declaración, un @media (prefers-color-scheme) para respetar el sistema, y un atributo en la raíz para la elección explícita del usuario.

:root {
  /* "El usuario elige, y si no eligió, seguimos al sistema" */
  color-scheme: light dark;

  --fondo:  light-dark(#ffffff, #0f172a);
  --texto:  light-dark(#0f172a, #f1f5f9);
  --borde:  light-dark(#e2e8f0, #334155);
}

/* Elección explícita: un atributo en <html> y listo */
:root[data-tema="light"] { color-scheme: light; }
:root[data-tema="dark"]  { color-scheme: dark; }

body { background: var(--fondo); color: var(--texto); }
Con esto, el único JavaScript que queda es el que lee la preferencia guardada y escribe data-tema en <html> — tres líneas, en un script bloqueante en el <head> para evitar el flash de tema equivocado. Todo el resto del sistema de temas es CSS y no crece cuando agregás componentes: si el componente usa las variables, ya está tematizado.
El costo escondido: el radio de invalidación. Cambiar una custom property en :root invalida el estilo computado de todos los elementos que la heredan — es decir, del documento entero. Para un cambio de tema, eso es correcto y ocurre una vez. Para un valor que cambia en cada frame (la posición del mouse, el progreso de un scroll), es carísimo: declará esa variable en el elemento más bajo posible, o registrala con inherits: false para que el motor sepa que no tiene que bajar por el árbol.

FS5.6 Arquitectura: las cuatro familias y su costo real

Toda metodología de CSS resuelve el mismo problema —el alcance global— y las diferencias están en a quién le pasa el costo. Esta es la comparación honesta:

FS5.7 Por qué el CSS-in-JS con runtime cayó en desgracia

Entre 2018 y 2022, CSS-in-JS con runtime fue el default de facto del ecosistema React. En 2026 es una tecnología en retirada. Los números lo muestran sin ambigüedad:

PaqueteDescargas semanales 20232026Variación
styled-components~8,5 M~6,8 M−20% · proyecto en modo mantenimiento
tailwindcss~6 M~12 M×2
@pandacss/dev~80 K~200 K+150% (desde una base chica)

La causa no fue una moda: fue una incompatibilidad arquitectónica. El runtime de CSS-in-JS inyecta estilos durante el render, coordinándose a través del contexto de React. Los React Server Components no corren en un contexto de cliente que pueda recolectar e inyectar esos estilos, y el streaming SSR rompe la premisa de "junto todos los estilos y los emito en el <head>", porque el HTML se empieza a mandar antes de que existan. A eso se le sumó el costo por render, que en listas largas aparece directamente en el INP.

Lo que lo reemplazó. No fue una cosa, fueron dos: utility-first (Tailwind, que duplicó su adopción) para equipos que quieren velocidad y un sistema cerrado, y zero-runtime CSS-in-JS (vanilla-extract, Panda CSS, StyleX) para equipos que quieren conservar la DX de tipos en TypeScript. Ambos comparten la misma idea: la extracción ocurre en build, y lo que llega al navegador es CSS estático, cacheable y sin librería.

Qué hacer si ya tenés uno (probablemente: casi nada)

1. Medí antes de decidir. Abrí un perfil de Performance en la vista más pesada y buscá cuánto tiempo se va en la serialización de estilos. Si es el 2% del render, no tenés un problema de estilos, tenés una moda. Migrar por moda es cómo se pierden tres sprints sin un solo cambio visible para el usuario.
2. Congelá la frontera. Regla de equipo: ningún componente nuevo usa la librería vieja. Esto no cuesta nada y hace que el problema deje de crecer, que es el 80% del valor.
3. Sacá los tokens primero. Mové colores, espaciados y tipografía del objeto de tema de JS a custom properties en CSS. Con eso, la mayoría de los componentes dejan de necesitar el runtime: ya no necesitan JS para saber qué color usar, lo heredan. Este paso solo ya suele eliminar la mitad de las razones para tener la librería.
4. Migrá desde las hojas hacia la raíz. Los componentes hoja (un botón, un badge) no tienen hijos cuyos estilos dependan de ellos: se pueden convertir de a uno, con un cambio de import y una revisión visual. Los layouts van último.
5. Si el bloqueante son los RSC, la migración deja de ser opcional — pero incluso ahí el camino es el mismo, solo que con fecha. Marcá los componentes que tienen que ser de servidor y migrá esos primero; el resto puede convivir indefinidamente en el lado cliente.
La regla que evita el desastre. Una migración de la capa de estilos es el proyecto arquetípico que consume meses y produce cero cambio visible. Si no podés escribir el beneficio como un número —"−18 KB de JS", "−40 ms de INP en la lista de pedidos", "desbloquea RSC en el checkout"— entonces todavía no tenés una justificación: tenés una preferencia estética. Escribí el número primero.

En CSS eso es indecidible en el caso general, y no por falta de herramientas: por la naturaleza del lenguaje. Un selector no se "llama": espera. Y la lista de razones por las que puede estar esperando algo legítimo es larga:

Coverage de DevTools y su límite exacto

Chrome tiene un panel de Coverage que te dice qué bytes de cada hoja no se usaron. Es útil y es la primera parada, pero su límite hay que entenderlo con precisión: te dice qué no se usó en esta página, en este estado, durante esta grabación. No te dice que algo esté muerto. Un botón que nadie pasó por encima aparece como no usado.

La versión seria es automatizar la recolección sobre un recorrido real y unir los resultados:

// Coverage sobre un JOURNEY, no sobre una carga. Playwright / Puppeteer.
import { chromium } from "playwright";

const RUTAS = ["/", "/productos", "/producto/123", "/carrito", "/checkout", "/cuenta"];

const navegador = await chromium.launch();
const pagina = await navegador.newPage();
const usados = new Map();   // url de la hoja -> Set de rangos usados

for (const ruta of RUTAS) {
  await pagina.coverage.startCSSCoverage();
  await pagina.goto("http://localhost:3000" + ruta);

  // Ejercitá LOS ESTADOS, que es lo que una carga simple nunca toca
  for (const el of await pagina.$$("[data-abrir], .btn, summary")) {
    await el.hover().catch(() => {});
    await el.click({ trial: true }).catch(() => {});
  }
  await pagina.emulateMedia({ media: "print" });
  await pagina.emulateMedia({ media: "screen" });

  for (const entrada of await pagina.coverage.stopCSSCoverage()) {
    const set = usados.get(entrada.url) ?? new Set();
    entrada.ranges.forEach(r => set.add(`${r.start}-${r.end}`));
    usados.set(entrada.url, set);
  }
}
await navegador.close();
// El resultado NO es una lista para borrar: es una lista de CANDIDATOS a revisar.
⚠️ Nunca borres CSS a partir de un reporte de coverage. Es la forma más rápida conocida de romper la página de error 500, el flujo de recuperación de contraseña o la vista de impresión de la factura — todo eso que nadie visita en el happy path y que alguien va a necesitar el peor día posible. El reporte genera candidatos; la decisión la toma una persona que sabe qué es cada bloque.
📌 La única cura estructural es una frontera, no una herramienta. El CSS muerto es difícil de detectar porque nada lo ata a nada. Si el estilo vive adentro del componente —CSS Modules, un archivo .css importado por el componente, utilidades en el markup—, entonces borrar el componente borra su estilo, automáticamente y sin análisis. Eso es lo que realmente comprás cuando elegís una arquitectura con alcance: no "clases más lindas", sino la capacidad de borrar.

FS5.9 Layout moderno: subgrid, aspect-ratio y view transitions

Subgrid: alinear a través de componentes

subgrid resuelve el problema clásico de una grilla de tarjetas: querés que los títulos, los cuerpos y los botones queden alineados entre tarjetas distintas, aunque el texto de cada una tenga largo diferente. Antes se hacía con alturas fijas y mentiras. Es Baseline widely available desde marzo de 2026 (Firefox lo tiene desde 2019, Safari desde 16, Chrome/Edge desde 117 en septiembre de 2023).

.grilla {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(260px, 1fr));
  gap: 1.5rem;
}

.tarjeta {
  display: grid;
  /* Las 3 filas propias de la tarjeta pasan a ser filas de la grilla PADRE */
  grid-row: span 3;
  grid-template-rows: subgrid;
  gap: 0;
}
/* Resultado: todos los títulos alineados, todos los botones al mismo nivel,
   sin alturas fijas y sin JavaScript midiendo nada. */

aspect-ratio: reservar espacio es una decisión de CLS

Esto conecta directo con FS4. aspect-ratio le permite al navegador reservar la caja antes de conocer el contenido, que es exactamente lo que evita el salto de layout:

.hero-media { aspect-ratio: 16 / 9; width: 100%; }
.avatar     { aspect-ratio: 1; object-fit: cover; }

/* Para <img>, seguí poniendo width y height en el HTML:
   el navegador deriva el aspect-ratio de esos atributos y reserva
   el espacio ANTES de que el CSS termine de cargar. */

View transitions: animar entre estados y entre páginas

La API de view transitions toma una captura del estado anterior, aplica tu cambio de DOM, toma una captura del nuevo, y anima entre las dos. Hay dos variantes con estados de soporte muy distintos, y confundirlas es el error más común:

// A — MISMO documento (SPA). Soporte amplio: Chrome 111+, Safari 18+, Firefox 133+.
// El navegador que no la tenga simplemente aplica el cambio sin animar.
function actualizarVista(nuevoHTML) {
  if (!document.startViewTransition) {   // degradación explícita
    contenedor.innerHTML = nuevoHTML;
    return;
  }
  document.startViewTransition(() => {
    contenedor.innerHTML = nuevoHTML;
  });
}
/* B — CROSS-document (MPA), sin una línea de JS. Va en AMBAS páginas. */
@view-transition { navigation: auto; }

/* Nombrar un elemento lo convierte en un actor de la transición:
   el navegador lo interpola entre las dos páginas en vez de hacer cross-fade. */
.producto__foto { view-transition-name: foto-destacada; }

::view-transition-old(foto-destacada),
::view-transition-new(foto-destacada) {
  animation-duration: 260ms;
}

/* Obligatorio: respetar la preferencia del usuario */
@media (prefers-reduced-motion: reduce) {
  ::view-transition-group(*),
  ::view-transition-old(*),
  ::view-transition-new(*) { animation: none !important; }
}
Estado real en septiembre de 2026 — corregí esto si lo leíste en otro lado. Las transiciones de mismo documento están en todos los motores (Chrome 111+, Safari 18+, Firefox 133+), y :active-view-transition llegó a Baseline newly available en enero de 2026. Las cross-document (@view-transition) son otra historia: Chrome 126+ y Safari 18.2+ las tienen, pero Firefox sigue detrás de un flag, y MDN clasifica la at-rule como limited availability, explícitamente no Baseline. No es "ya está lista": es una mejora progresiva con un motor entero afuera.
Tres trampas de view transitions.
  • Los view-transition-name tienen que ser únicos en el documento en el momento de la transición. Dos elementos con el mismo nombre —típico al renderizar una lista— abortan la transición entera, sin error en consola. Generá el nombre a partir del id del ítem.
  • Durante la transición, la página está congelada: lo que ves es una captura. Una animación de 600 ms son 600 ms en los que el usuario no puede interactuar. Quedate en 200–300 ms.
  • No las uses para ocultar latencia. Una transición larga no hace que la navegación sea más rápida; hace que el usuario espere igual, pero mirando algo lindo. Si el destino tarda, el problema es el destino (FS4).

FS5.10 Rendimiento del CSS: el mito y la realidad

Durante años se enseñó que los selectores descendentes eran caros y que había que escribir de derecha a izquierda pensando en el motor. Eso viene de mediciones de los años 2000 y hoy es, para casi todo el mundo, ruido. Los motores modernos indexan las reglas por el compound más a la derecha, matchean de derecha a izquierda con filtros de Bloom para descartar ancestros imposibles, y el matcheo de selectores suele ser una fracción menor del recálculo de estilo.

💡 El orden real de los costos del CSS, de mayor a menor impacto en un proyecto típico:
  1. Bytes. El CSS bloquea el render: hasta que no se descargó y parseó, no hay primer pintado. Este es, casi siempre, el costo dominante.
  2. Radio de invalidación. Cambiar una clase en <html> o una variable en :root obliga a recalcular el documento entero.
  3. Cantidad de elementos × reglas a considerar. El recálculo escala con el producto, no con la longitud de tus selectores.
  4. Qué propiedad animás. transform y opacity se resuelven en el compositor; width, top o box-shadow disparan layout o paint en cada frame.
  5. Complejidad del selector. Último. Con dos excepciones reales: :has() mal acotado y selectores universales combinados, que son problemas de invalidación, no de matcheo.

content-visibility y contain: pagar solo por lo que se ve

La optimización de rendering con más impacto por línea escrita es content-visibility: auto: le dice al navegador que puede saltear layout, paint y estilo del subárbol mientras está fuera de la pantalla. En páginas muy largas (un feed, una documentación, una tabla de miles de filas) el ahorro en el render inicial es grande, porque el trabajo se difiere hasta que el contenido se acerca al viewport.

.seccion-larga {
  content-visibility: auto;
  /* CRÍTICO: sin esto, cada sección oculta mide 0 y la barra de scroll salta */
  contain-intrinsic-size: auto 800px;
}

/* `contain` es el mecanismo de bajo nivel: promete que lo de adentro
   no afecta a lo de afuera, y el navegador aprovecha esa promesa. */
.widget-aislado { contain: layout paint; }
Lo que content-visibility te cobra.
  • El scroll se vuelve una estimación. contain-intrinsic-size es una promesa sobre el alto; si le errás mucho, la barra de scroll salta cuando el contenido real se materializa. La forma auto <valor> hace que el navegador recuerde el tamaño real una vez medido, y mitiga bastante el problema.
  • Anclaje y saltos a anclas pueden comportarse raro si el destino todavía no se renderizó.
  • No lo pongas en todo. Aplicado a elementos chicos, el costo de administrar el saltado supera al ahorro. Es una herramienta para secciones grandes y repetidas.

FS5.11 Cuándo NO usar lo nuevo

Todo lo anterior es adoptable. Nada de lo anterior es obligatorio. Estos son los cuatro criterios para frenar:

1. Distinguí cosmético de funcional. Es la distinción más útil que existe. Si la ausencia de la feature produce una página menos linda, adoptala hoy sin fallback: las view transitions degradan a un cambio instantáneo, que es exactamente lo que había antes. Si su ausencia produce una página rota o ilegible —un layout que depende de container queries, un color que depende de @property—, necesitás fallback o un piso de soporte declarado. Nadie se queja de una animación que no vio; todos se quejan de un texto que no se lee.
2. Mirá TU analytics, no el porcentaje global. "97% de soporte global" no significa nada para tu producto. Si el 6% de tu tráfico es un navegador embebido de una app corporativa que quedó en una versión de 2021, ese 6% son personas concretas. El número que importa es el de tu panel, segmentado por el flujo donde vas a usar la feature.
3. Usá @supports, y sabé cómo se pregunta por un selector. La consulta de propiedades es la conocida; para pseudo-clases hace falta la forma selector(), que mucha gente no conoce.
/* Base: funciona en todos lados */
.layout { display: block; }

@supports (container-type: inline-size) {
  .layout { display: grid; }
}

/* Para selectores, la forma correcta es selector() */
@supports selector(:has(a)) {
  .card:has(> img) { grid-template-columns: 120px 1fr; }
}

/* Y se pueden combinar */
@supports (view-transition-name: none) and (not (contain-intrinsic-size: 1px)) {
  /* … */
}
4. Preguntate si el equipo lo va a poder mantener. Este es el criterio que más proyectos hunde y el que menos se menciona. Si sos la única persona que puede explicar por qué el orden de capas es reset, vendor, base, components, utilities y qué pasa si alguien agrega un archivo suelto, entonces ese orden va a estar mal en tres meses — y no por incompetencia ajena, sino porque el conocimiento vivía en una sola cabeza. La prueba concreta: ¿puede alguien que entró la semana pasada agregar un componente nuevo sin leer un wiki ni preguntarte? Si la respuesta es no, la arquitectura tiene un bug, aunque el CSS esté impecable.
⚠️ El costo que nunca se presupuesta. Cada capa de indirección que agregás —un sistema de tokens, un stack de capas, una convención de nombres de contenedores— es algo que hay que enseñar, documentar y hacer cumplir, para siempre. Ese costo es recurrente y lo paga el equipo entero; el beneficio suele ser puntual y lo cobra quien la introdujo. Antes de agregar una abstracción, escribí en una línea quién la va a mantener cuando vos estés en otro proyecto.

Paso 2 — El diagnóstico, que no es el que parece.

📌 El problema no es que sean 241 KB. Es que nadie puede borrar nada. Los 214 !important y la especificidad de (3,7,2) no son descuido: son la evidencia fósil de que la única forma de ganar una discusión con la cascada, en este proyecto, era escalar. Y las tres escalas de espaciado conviven porque cada rediseño agregó la suya sin poder sacar la anterior — sacar la anterior habría requerido saber quién la usa, y eso nadie lo sabe. El tamaño es la consecuencia; la causa es la falta de límites.

Paso 3 — El plan incremental. Cinco PRs, cada uno mergeable y reversible.

PR 1 — Declarar el orden. Cero cambios visuales. Una línea arriba del archivo de entrada: @layer reset, vendor, base, layout, components, utilities;. Como todo el CSS actual está sin encapar, sigue ganando sobre todas las capas y no cambia absolutamente nada. Es un PR de una línea que se puede mergear un viernes. Se agrega el chequeo de capturas visuales al CI acá, no después.
PR 2 — Meter los terceros en layer(vendor). Bootstrap y el date picker pasan a @import ... layer(vendor). En este momento, los !important que existían solo para ganarle a Bootstrap dejan de hacer falta. Se sacan con un grep guiado: de 214 bajan a 96 en un solo PR, y las capturas no cambian.
PR 3 — El reset a layer(reset), reescrito con :where(). Baja la especificidad base a cero y saca otros 20 !important. Bajo riesgo, alto rédito.
PR 4..N — Componente por componente, a medida que se tocan. Regla de equipo: todo ticket que toca un componente lo mueve a @layer components y le saca los !important que ya no necesita. No hay un sprint de migración: la migración viaja de polizón en el trabajo normal. Se le pone un tablero con el porcentaje encapado para que se vea el avance.
PR final — Unificar el espaciado. Recién acá, con las capas puestas, se define una escala en custom properties y se aliasan las dos viejas a la nueva (--space-15: var(--space-4)) para que nada cambie visualmente. Después se van eliminando los alias a medida que el uso llega a cero. Este orden importa: intentar unificar tokens antes de tener capas es pelear en dos frentes.

Checkpoint — ¿lo tenés claro?

¿Por qué el CSS sin encapar le gana a todas las capas, y qué te permite hacer eso?

Porque la especificación define que las declaraciones no encapadas se comportan como si estuvieran en una capa implícita al final del orden — es decir, la de mayor prioridad. La consecuencia práctica es enorme: podés declarar tu orden de capas en un proyecto legacy y no cambia nada, porque todo el CSS existente sigue sin encapar y sigue ganando. Eso convierte la adopción de @layer en una migración incremental y reversible en vez de un big bang. El precio es el reverso: cualquier archivo nuevo que alguien olvide encapar pisa el sistema entero, así que hace falta un lint o un único punto de entrada que importe todo con layer(). Y ojo con la asimetría: entre declaraciones con !important el orden se invierte, y ahí lo no encapado pierde contra todo lo encapado.

Pusiste container-type en un wrapper y el componente colapsó a cero de alto. ¿Qué pasó?

Usaste container-type: size en vez de inline-size. Para poder responder una consulta de tamaño antes de disponer el contenido, el navegador necesita que el tamaño del contenedor no dependa de lo que tiene adentro: eso es containment de tamaño. Con inline-size solo aplica al ancho, que en flujo normal ya viene dado por el padre, así que no se nota. Con size aplica también al alto, y como el alto normalmente sí sale del contenido, el contenedor se computa como si estuviera vacío: 0 px. La regla es usar inline-size siempre, salvo que tengas una altura explícita y necesites específicamente consultar block-size o usar unidades cqb.

Un reporte dice que el 60% de tu CSS no se usa. ¿Lo borrás?

No, y esta es la trampa clásica. El coverage te dice qué no se ejercitó en esa grabación, no qué está muerto: los estados (:hover, .is-open, input:invalid), las clases construidas dinámicamente en JS, el markup que inyectan widgets de terceros, el HTML que escriben editores en un CMS, @media print y las rutas que no visitaste aparecen todos como "no usados". Lo correcto es correr el coverage sobre un journey automatizado que ejercite estados y rutas, unir los rangos, y tratar el resultado como una lista de candidatos que revisa una persona. Y sobre todo entender que la herramienta no arregla la causa: mientras el CSS no tenga una frontera que lo ate a un componente, va a seguir siendo indeciblemente difícil de borrar.

Resumen ejecutivo

  • El CSS a escala no falla por sintaxis: falla porque es global y sin límites. Toda la arquitectura consiste en fabricar fronteras que el lenguaje no trae.
  • La especificidad es el quinto criterio de la cascada, no el primero. @layer mueve la pelea a un criterio anterior que vos controlás en una línea, y :where() te deja escribir selectores complejos que pesan cero.
  • !important es un síntoma, y cada uno delata una de tres causas con curas distintas. Contalos en el CI y no dejes que el número suba.
  • @layer es widely available desde 2024 y su superpoder es la migración incremental: lo no encapado gana, así que declarar el orden no rompe nada. Cuidado con la inversión bajo !important.
  • :has() pasó a widely available en junio de 2026. Su costo no es el matcheo sino la invalidación hacia arriba: acotá el ancestro y preferí el combinador hijo.
  • Container queries (widely available desde 2023) son lo que hace que un componente se pueda mover. No reemplazan las media queries del shell ni las de preferencias. Usá inline-size, no size.
  • @property es Baseline newly available (widely proyectado para enero de 2027): úsalo para mejoras progresivas, todavía no para lo funcional.
  • El CSS-in-JS con runtime retrocede por una razón técnica —incompatibilidad con RSC y streaming SSR—, no por moda. Lo reemplazaron utility-first y la extracción en build. Si ya tenés uno: congelá la frontera, sacá los tokens a custom properties, migrá desde las hojas, y justificá con un número.
  • El dead code CSS es indecidible en general; el coverage da candidatos, no sentencias. La única cura estructural es que el estilo viva adentro del componente, para que borrar el componente borre el estilo.
  • En rendimiento, el orden es bytes → invalidación → elementos×reglas → propiedad animada → complejidad del selector. La complejidad del selector va última, con la excepción de un :has() mal acotado.
  • Cross-document view transitions siguen sin ser Baseline en septiembre de 2026: Firefox detrás de un flag. Tratalas como cosmético progresivo, nunca como funcional.

🧠 Autoevaluación

1. Declarás @layer reset, vendor, components; en un proyecto legacy de 200 KB donde ningún archivo está encapado. ¿Qué pasa con los estilos al desplegar?

Esta es exactamente la propiedad que hace viable la migración incremental. Las declaraciones fuera de todo @layer compiten como si estuvieran en una capa implícita al final del orden, es decir con la máxima prioridad. Podés declarar el stack completo en un PR de una línea y desplegarlo sin riesgo, y recién después ir moviendo archivos hacia adentro de a uno. La contracara: un archivo nuevo que alguien olvide encapar pisa todo el sistema, así que hace falta un lint o un único punto de entrada. Y bajo !important el orden se invierte, con lo no encapado perdiendo contra todo lo encapado.

2. Estás por usar @view-transition { navigation: auto; } para animar la navegación entre páginas de un sitio MPA. ¿Cuál es la lectura correcta de su soporte en septiembre de 2026?

Hay que separar las dos variantes. Las transiciones de mismo documento (document.startViewTransition()) están en los tres motores: Chrome 111+, Safari 18+, Firefox 133+. Las cross-document con la at-rule @view-transition están en Chromium 126+ y Safari 18.2+, pero Firefox las mantiene detrás de un flag, y MDN clasifica la at-rule como limited availability, explícitamente no Baseline. La consecuencia práctica es buena: donde no está soportada, la navegación simplemente ocurre sin animar, que es lo que pasaba antes. Por eso califica como cosmético progresivo — y por eso nunca hay que colgar de ella nada funcional.

3. Tu hoja pesa 241 KB, tiene selectores descendentes largos y 6.800 reglas. ¿Dónde está, casi con certeza, la mayor parte del costo para el usuario?

El costo dominante en un proyecto típico es el tamaño, porque el CSS es render-blocking: no hay primer pintado hasta que se descargó y parseó. Lo de los selectores descendentes es un mito heredado de mediciones de los 2000: los motores modernos indexan por el compound más a la derecha y usan filtros de Bloom para descartar ancestros imposibles, así que el matcheo suele ser una fracción menor del recálculo de estilo. Y no, el navegador no evalúa las 6.800 reglas contra cada elemento — están agrupadas en buckets. El orden real de los costos es: bytes, radio de invalidación, elementos × reglas consideradas, qué propiedad animás, y último la complejidad del selector, con la excepción de un :has() mal acotado, que es un problema de invalidación disfrazado de selector.
