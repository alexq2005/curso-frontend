CF2 — Arquitectura de firmware: código que corre 5 años sin reiniciarse

CF2.0 Por qué este módulo

En E03 y E04 aprendiste a hacer que un microcontrolador haga cosas: leer un pin, mover un servo, hablar por I²C. Este módulo no trata de eso. Trata de la pregunta que aparece después, cuando ese código deja tu escritorio y se mete adentro de una caja atornillada a una pared: ¿va a seguir funcionando dentro de tres años, sin que nadie lo mire?

💡 La tesis del módulo. El software que escribís para un servidor vive en un mundo donde el error es barato: si algo se rompe, reiniciás el proceso; si hay un bug, desplegás en veinte minutos; si te queda una fuga de memoria chica, el reinicio nocturno la limpia. El firmware no tiene nada de eso. No hay quien reinicie, no hay F5, no hay kubectl rollout restart, y la memoria que fragmentaste el martes sigue fragmentada el martes del año que viene. Toda la arquitectura de firmware que vas a ver acá es una consecuencia lógica de esas tres ausencias.

La diferencia se ve en un solo número. Un servicio web con un uptime de 99,9% pierde 8,7 horas por año y nadie se entera demasiado. Un equipo embebido con ese mismo 99,9% se reinicia solo unas 525 veces por año si cada caída dura un minuto — y si es un caudalímetro que factura, o una bomba de infusión, o el controlador de una barrera de peaje, esas 525 veces son 525 incidentes. El objetivo del firmware de campo no es "casi siempre". Es que el contador de uptime no se resetee nunca, y que cuando se resetee, sepas exactamente por qué.

📌 La regla que ordena todo el módulo. En firmware, cualquier recurso cuyo consumo dependa del historial de ejecución es una bomba de tiempo. Memoria del heap, entradas de una tabla que crece, handles que se piden y no se devuelven, contadores que no saturan. Si no podés calcular el peor caso en papel, no lo podés poner en campo.

Un aviso de alcance: CF2 es sobre estructura y confiabilidad. El timing —prioridades, jitter, análisis de planificabilidad— lo cubrió CF1, y voy a apoyarme en eso sin repetirlo. La criptografía del arranque seguro y la firma de imágenes se ve en CF6: acá tratamos la integridad del update (que no quede a medias) y ahí se trata la autenticidad (que sea tuyo).

CF2.1 Las cuatro capas: HAL, drivers, servicios, aplicación

La arquitectura por capas en firmware no es una moda de arquitectos. Es la respuesta a un problema muy concreto: el silicio se te muere debajo del producto. Un STM32 que elegiste en 2023 puede entrar en Not Recommended for New Designs en 2027, y tu producto todavía se fabrica. La escasez de semiconductores de 2021–2022 le enseñó eso a la industria entera de la peor manera: equipos que tuvieron que migrar de familia de MCU en semanas.

El driver del sensor no sabe qué hace la aplicación con la lectura. En C esto se implementa con estructuras de punteros a función — el equivalente pobre pero perfectamente funcional de una interfaz:

CF2.2 Máquinas de estados: la columna vertebral

Abrí cualquier firmware viejo que haya sobrevivido a tres programadores y vas a encontrar lo mismo: un while(1) con un if anidado seis niveles, banderas booleanas con nombres como flag_ok2, y un comentario que dice /* no tocar */. Ese es el olor característico del firmware sin arquitectura, y siempre nace igual: alguien modeló un proceso secuencial con condicionales en vez de con estados.

Un equipo embebido casi nunca es secuencial. Es reactivo: llega un evento (un timeout, un byte, un botón, una lectura fuera de rango) y el sistema tiene que responder distinto según en qué situación esté. Eso es literalmente la definición de una máquina de estados finitos, y modelarla como tal no es elegancia: es la única forma de poder enumerar todas las combinaciones y demostrar que ninguna quedó sin manejar.

Las tres implementaciones, con su costo

/* OPCIÓN 1 — switch. La que se escribe primero, y la correcta el 80% de las veces. */
typedef enum { ST_INIT, ST_IDLE, ST_MIDIENDO, ST_ENVIANDO, ST_FALLA, ST_COUNT } estado_t;
typedef enum { EV_TICK, EV_DATO_LISTO, EV_TX_OK, EV_TIMEOUT, EV_ERROR, EV_COUNT } evento_t;

static estado_t st = ST_INIT;

void fsm_paso(evento_t ev)
{
    switch (st) {
    case ST_IDLE:
        if (ev == EV_TICK) { sensor_disparar(); st = ST_MIDIENDO; }
        break;

    case ST_MIDIENDO:
        if      (ev == EV_DATO_LISTO) { radio_enviar(); st = ST_ENVIANDO; }
        else if (ev == EV_TIMEOUT)    { st = ST_FALLA; }
        break;

    case ST_ENVIANDO:
        if      (ev == EV_TX_OK)   { st = ST_IDLE; }
        else if (ev == EV_TIMEOUT) { st = ST_FALLA; }
        break;

    default:
        /* Nunca dejes un default vacío: un estado imposible es un bug, no un no-evento */
        log_err("estado invalido %d con evento %d", (int)st, (int)ev);
        st = ST_FALLA;
        break;
    }
}
/* OPCIÓN 2 — tabla de transición. Los estados dejan de ser código y pasan a ser datos. */
typedef struct {
    estado_t destino;
    void   (*accion)(void);
} transicion_t;

/* [estado][evento] -> a dónde voy y qué hago. La tabla vive en flash: 0 bytes de RAM. */

/* ST_IDLE   */ {{ST_MIDIENDO, sensor_disparar}, {ST_IDLE, NULL},       {ST_IDLE, NULL},        {ST_IDLE, NULL},       {ST_FALLA, NULL}},

/* ST_FALLA  */ {{ST_FALLA,    NULL       }, {ST_FALLA, NULL},          {ST_FALLA, NULL},       {ST_FALLA, NULL},      {ST_FALLA, NULL}},
};

void fsm_paso(evento_t ev)
{
    if (st >= ST_COUNT || ev >= EV_COUNT) { st = ST_FALLA; return; }
    const transicion_t *t = &TABLA[st][ev];
    if (t->accion) t->accion();
    st = t->destino;
}
📌 Lo que gana la tabla no es velocidad: es completitud. Si tenés 5 estados y 5 eventos, hay 25 casillas, y el compilador te obliga a llenarlas todas o a declarar explícitamente el default. Con un switch podés escribir 9 casos y nunca enterarte de los 16 que faltan hasta que uno aparece en campo. Esa es toda la diferencia, y en un producto que corre años es enorme. 
/* OPCIÓN 3 — punteros a función por estado (state pattern). Para jerarquías y estados con
   entry/exit propios. Es la más flexible y también la más difícil de seguir leyendo. */
typedef struct estado_s {
    const char *nombre;
    void (*on_entry)(void);
    const struct estado_s *(*on_event)(evento_t ev);
    void (*on_exit)(void);
} estado_desc_t;

static const estado_desc_t *actual = &ST_DESC_INIT;

void fsm_paso(evento_t ev)
{
    const estado_desc_t *siguiente = actual->on_event(ev);
    if (siguiente != NULL && siguiente != actual) {
        if (actual->on_exit)     actual->on_exit();
        actual = siguiente;
        if (actual->on_entry)    actual->on_entry();
        log_info("estado -> %s", actual->nombre);
    }
}

El error clásico: estados implícitos en variables sueltas. Tres booleanos (conectado, midiendo, enviando) son 2³ = 8 combinaciones, de las cuales quizás 4 son válidas. Las otras 4 son estados imposibles que van a ocurrir igual, porque una interrupción cambió uno de los flags entre dos líneas. Un enum de 4 valores hace que los estados imposibles no se puedan representar. Es la misma idea que "make illegal states unrepresentable" del mundo de los tipos, aplicada con un enum de C.

CF2.3 Memoria dinámica: por qué no

Este es probablemente el punto donde más se separa el firmware amateur del profesional, y el que más resistencia genera, porque en cualquier otro lenguaje pedir memoria es tan normal como respirar.

⚠️ El escenario que hay que entender. Tu equipo tiene 64 KB de RAM y usa malloc para un buffer que crece y se achica según el tamaño de los mensajes que llegan. Funciona perfecto en el banco de pruebas. En campo, después de siete meses y unos 30 millones de ciclos de alocación, un malloc(2048) devuelve NULL: hay 18 KB libres, pero repartidos en 140 huecos de los cuales el más grande es de 1.900 bytes. No hay fuga de memoria. Hay fragmentación externa, y no se cura sola. Un equipo que reinicia todos los días nunca la habría visto.

Los tres problemas son independientes entre sí y cada uno alcanza para descartar el heap en un sistema serio:

1. Fragmentación externa. Alocaciones de tamaños distintos dejan huecos que no se pueden reusar. Es acumulativa, depende del historial, y no se puede acotar analíticamente para un patrón de uso arbitrario. En un servidor no importa porque el proceso se recicla; acá no se recicla nada.
2. No determinismo temporal. malloc recorre listas libres. Su tiempo depende del estado del heap, y ese estado depende del pasado. Un malloc que tarda 3 µs en el minuto 1 puede tardar 90 µs en el mes 6. Si eso pasa adentro de una tarea con deadline (ver CF1), rompiste el análisis de planificabilidad sin escribir una línea nueva.
3. El fallo no tiene salida. ¿Qué hacés cuando malloc devuelve NULL? En un servidor, tirás una excepción y que el supervisor reinicie. En un controlador de riego a 40 km, ¿reiniciás? ¿Seguís con menos funcionalidad? La mayoría del código embebido con heap simplemente no chequea el retorno, y ahí el NULL se convierte en un HardFault por desreferenciar dirección 0.
Esto no es una opinión de nicho: MISRA C:2012, reglas 21.3 y 21.4, prohíben directamente malloc, calloc, realloc y free, y esa prohibición es obligatoria en desarrollos bajo ISO 26262 (automotriz) e IEC 61508 (seguridad funcional industrial). Si alguna vez tu producto tiene que certificar, el heap ya está descartado por norma, no por gusto.

   El linker te dice en tiempo de compilación si no entra: el mejor momento para enterarse. */

{

    sensores[n_sensores++] = sensor_crear(cfg);
    return true;
}

Alternativa 2 — Pool de bloques de tamaño fijo

Cuando de verdad necesitás alocar y liberar en tiempo de ejecución —paquetes de red que llegan y se procesan, por ejemplo— la solución es un pool: todos los bloques del mismo tamaño. Si todos los bloques son iguales, la fragmentación externa es imposible por construcción, y alocar/liberar es O(1) determinista.

/* pool.h — pool de bloques fijos con free-list intrusiva.
   Costo total de RAM: N * TAM + sizeof(pool_t). Nada más, y calculable en papel. */
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

typedef struct bloque_s { struct bloque_s *sig; } bloque_t;

typedef struct {
    bloque_t *libres;
    uint8_t  *arena;
    size_t    tam_bloque;
    uint16_t  n_bloques;
    uint16_t  en_uso;
    uint16_t  pico;          /* HIGH WATER MARK: el dato que te salva la vida */
} pool_t;

void pool_init(pool_t *p, void *arena, size_t tam_bloque, uint16_t n)
{
    p->arena = (uint8_t *)arena;
    p->tam_bloque = tam_bloque;
    p->n_bloques = n;
    p->en_uso = 0;
    p->pico = 0;
    p->libres = NULL;

    /* Encadeno todos los bloques en la free-list, hacia atrás */
    for (uint16_t i = n; i > 0; i--) {
        bloque_t *b = (bloque_t *)(p->arena + (size_t)(i - 1) * tam_bloque);
        b->sig = p->libres;
        p->libres = b;
    }
}

void *pool_alloc(pool_t *p)          /* O(1), siempre, para toda la vida del equipo */
{
    if (p->libres == NULL) return NULL;
    bloque_t *b = p->libres;
    p->libres = b->sig;
    p->en_uso++;
    if (p->en_uso > p->pico) p->pico = p->en_uso;
    return (void *)b;
}

void pool_free(pool_t *p, void *ptr)
{
    if (ptr == NULL) return;
    /* Chequeo de cordura barato: ¿este puntero es realmente mío y está alineado? */
    uint8_t *q = (uint8_t *)ptr;
    ptrdiff_t off = q - p->arena;
    if (off < 0 || (size_t)off >= (size_t)p->n_bloques * p->tam_bloque
                || ((size_t)off % p->tam_bloque) != 0) {
        fault_registrar(FAULT_POOL_FREE_INVALIDO);   /* corrupción: no lo escondas */
        return;
    }
    bloque_t *b = (bloque_t *)ptr;
    b->sig = p->libres;
    p->libres = b;
    p->en_uso--;
}
/* Uso: la arena es estática, y el tamaño total queda escrito en el binario. */
#define PKT_TAM   128
#define PKT_N      12                 /* 12 * 128 = 1536 bytes. Fijo. Para siempre. */

static uint8_t pkt_arena[PKT_N * PKT_TAM] __attribute__((aligned(8)));
static pool_t  pkt_pool;

void red_init(void) { pool_init(&pkt_pool, pkt_arena, PKT_TAM, PKT_N); }
Ese campo pico es el más importante de la estructura. Publicalo por el canal de telemetría o mostralo en el log de arranque: te dice cuánto margen real te queda. Si un equipo lleva un año con pico = 4 de 12, sabés que podés recortar el pool y liberar 1 KB. Si pico = 12 de 12, estuviste a un paquete de perder datos y no te enteraste.

Alternativa 3 — Arena / bump allocator

Para cosas que se alocan una vez y se liberan todas juntas (parsear un mensaje, construir un reporte), una arena es imbatible: un puntero que avanza, y un reset que lo pone en cero.

typedef struct { uint8_t *base; size_t cap, usado, pico; } arena_t;

void *arena_alloc(arena_t *a, size_t n, size_t align)
{
    size_t p = (a->usado + (align - 1)) & ~(align - 1);   /* alineo hacia arriba */
    if (p + n > a->cap) return NULL;                       /* no entra: falla explícita */
    a->usado = p + n;
    if (a->usado > a->pico) a->pico = a->usado;
    return a->base + p;
}

void arena_reset(arena_t *a) { a->usado = 0; }   /* libera TODO en 1 instrucción */

/* C) Patrón centinela (stack painting). Lo que hace FreeRTOS con uxTaskGetStackHighWaterMark.

{

        *p = PATRON;

{
    uint32_t *p = &_sstack;
    while (p < &_estack && *p == PATRON) p++;

}

⚠️ La detección real se hace con la MPU, no con el centinela. El patrón centinela te dice después que estuviste cerca; no impide nada, y si el desborde salta por arriba de la zona pintada (una función que reserva 512 bytes de una) no lo detecta. La Memory Protection Unit de cualquier Cortex-M con MPU te deja poner una región de "guarda" sin permisos justo debajo del stack: cualquier escritura ahí dispara un MemManage_Handler en el instante exacto del desborde, con el PC apuntando a la función culpable. Costo: una región de MPU (de 8 o 16 disponibles) y ~32 bytes de RAM desperdiciados por el alineamiento. Es la mejor relación costo/beneficio de todo este módulo.

CF2.5 Watchdog: el que se patea en un timer no sirve

El watchdog es un contador en hardware que resetea el chip si no lo refrescás a tiempo. Es la última red de seguridad del equipo: si el firmware se cuelga, el watchdog lo revive. Y es, de lejos, el mecanismo peor implementado de la industria.

El antipatrón. Alguien pone el kick del watchdog en una interrupción de timer, o en el while(1) del main. A partir de ese momento el watchdog ya no vigila que el sistema funcione: vigila que el timer siga corriendo. Y el timer va a seguir corriendo aunque la tarea de red esté trabada en un semáforo desde hace cuarenta minutos, aunque la máquina de estados haya quedado en un estado inválido, aunque el sensor no responda desde ayer. Un watchdog que se patea solo es un watchdog apagado con pasos extra.

El patrón correcto invierte la responsabilidad: cada tarea reporta su propia salud, y el watchdog se patea únicamente si todas reportaron. La tarea de menor prioridad —la idle o una tarea supervisora— es la que hace la verificación, porque si el sistema está saturado esa tarea no corre, y entonces el reset ocurre: exactamente lo que querés.

/* wdt_super.c — watchdog supervisado por tareas. Patrón de bitmask, sin locks. */
#include <stdint.h>
#include <stdatomic.h>

typedef enum {
    WDT_TAREA_SENSOR   = (1u << 0),
    WDT_TAREA_RED      = (1u << 1),
    WDT_TAREA_CONTROL  = (1u << 2),
    WDT_TAREA_UI       = (1u << 3),
    WDT_TODAS          = 0x0Fu,
} wdt_tarea_t;

static atomic_uint checkin;      /* bits reportados desde la última ronda */

/* Cada tarea llama a esto al COMPLETAR una iteración útil, no al empezar. */
void wdt_checkin(wdt_tarea_t quien)
{
    atomic_fetch_or(&checkin, (unsigned)quien);
}

/* Corre en la tarea de menor prioridad, cada 500 ms. */
void wdt_supervisor_paso(void)
{
    unsigned vistos = atomic_exchange(&checkin, 0u);

    if (vistos == WDT_TODAS) {
        hal_iwdg_kick();                    /* SOLO acá se patea el perro */
        return;
    }

    /* Alguien no reportó. Antes de morir, dejo escrito QUIÉN, en RAM no inicializada
       para que sobreviva al reset (ver CF2.7). */
    fault_ctx.faltantes = WDT_TODAS & ~vistos;
    fault_ctx.magia     = FAULT_MAGIA;
    fault_ctx.causa     = CAUSA_WDT_TAREA;
    /* No pateo: dejo que el hardware me resetee en el próximo vencimiento. */
}
📌 El punto sutil que casi nadie implementa. No basta con "la tarea sigue viva": la tarea tiene que haber hecho trabajo útil. Una tarea de red trabada reintentando la misma conexión fallida en un lazo cerrado está viva, corre, y reporta felizmente. Por eso el wdt_checkin() va después del trabajo real —dato publicado, comando procesado— y no arriba del lazo. Una variante más estricta agrega un plazo por tarea: cada una declara cada cuánto debería reportar, y el supervisor exige que ninguna exceda su plazo.

El dato que casi nadie guarda: por qué se reinició

Todo MCU moderno tiene un registro que dice la causa del último reset y sobrevive al reinicio. Leerlo en el arranque y registrarlo cuesta diez líneas y es la diferencia entre "se cuelga cada tanto" y un diagnóstico:

typedef enum {
    RST_POR,        /* power-on: se cortó la luz */
    RST_PIN,        /* alguien apretó reset */
    RST_WDT,        /* el watchdog nos mató  <-- este es el interesante */
    RST_SOFT,       /* NVIC_SystemReset() nuestro */
    RST_BROWNOUT,   /* la tensión cayó por debajo del umbral (ver CF3) */
    RST_DESCONOCIDO,
} reset_causa_t;

reset_causa_t reset_causa_leer(void)   /* STM32: registro RCC->CSR */
{
    uint32_t csr = RCC->CSR;
    RCC->CSR |= RCC_CSR_RMVF;          /* limpiar flags para el próximo arranque */

    if (csr & RCC_CSR_IWDGRSTF) return RST_WDT;
    if (csr & RCC_CSR_BORRSTF)  return RST_BROWNOUT;
    if (csr & RCC_CSR_PINRSTF)  return RST_PIN;
    if (csr & RCC_CSR_SFTRSTF)  return RST_SOFT;
    if (csr & RCC_CSR_PORRSTF)  return RST_POR;
    return RST_DESCONOCIDO;
}

CF2.6 Manejo de errores sin excepciones

En C no hay excepciones, y en firmware tampoco querrías tenerlas: el desenrollado de pila no es determinista y el binario crece. Lo que sí necesitás es una disciplina uniforme, porque el problema real no es la falta de try/catch: es que cada módulo inventa su propia convención (uno devuelve 0 en éxito, otro 1, otro -1, otro pone errno) y el código que los combina se vuelve ilegible.

/* UNA convención para todo el proyecto. 0 = éxito, negativos = error. Y se respeta. */
typedef int32_t err_t;

#define ERR_OK             0
#define ERR_ARG          (-1)
#define ERR_TIMEOUT      (-2)
#define ERR_NO_MEM       (-3)
#define ERR_CRC          (-4)
#define ERR_NO_DISPOSITIVO (-5)
#define ERR_ESTADO       (-6)

/* El macro que hace que el código de arriba sea legible. Sin él, todo es un if anidado. */
#define TRY(expr)  do { err_t _e = (expr); if (_e != ERR_OK) return _e; } while (0)
/* El patrón goto cleanup. En C ES la construcción correcta: es el único
   mecanismo del lenguaje para un único punto de salida con liberación ordenada. */
err_t medicion_ciclo(medicion_t *out)
{
    err_t st = ERR_OK;
    bool  bus_tomado = false;
    bool  sensor_on  = false;

    st = bus_lock(&i2c1, 100);
    if (st != ERR_OK) goto cleanup;
    bus_tomado = true;

    st = sensor_power(true);
    if (st != ERR_OK) goto cleanup;
    sensor_on = true;

    st = sensor_leer(out);
    if (st != ERR_OK) goto cleanup;

    st = validar_rango(out);
    if (st != ERR_OK) goto cleanup;

cleanup:
    /* Se deshace en orden inverso, y solo lo que llegó a hacerse */
    if (sensor_on)  sensor_power(false);
    if (bus_tomado) bus_unlock(&i2c1);
    if (st != ERR_OK) stats_err_inc(st);
    return st;
}
El goto tiene mala fama por el artículo de Dijkstra de 1968, que hablaba de saltos arbitrarios en lenguajes sin bloques estructurados. El salto hacia adelante a una única etiqueta de limpieza es otra cosa: es el idioma estándar del kernel de Linux, de OpenSSL y de prácticamente todo el firmware serio en C. La alternativa —anidar seis if y repetir la liberación en cada rama— es medible y objetivamente peor: más caminos, más código, más chances de olvidarte un unlock.

📌 La línea que separa assert de error. ASSERT es para invariantes internos: cosas que si son falsas, tu código tiene un bug. Un return ERR_x es para condiciones del mundo: un bus que no responde, un frame corrupto, un usuario que mandó basura. Meter un assert en un dato que viene de afuera es convertir un paquete malformado en un reinicio del equipo — y le acabás de dar a cualquiera un ataque de denegación de servicio de un solo paquete.

⚠️ Nunca while(1); en un fallo de producción. Un equipo trabado en un lazo infinito es un equipo muerto que además no reporta que está muerto y que no vuelve solo. Reiniciar es casi siempre mejor: el equipo tiene una chance de volver a operar, el registro de causa de reset queda escrito, y el contador de reinicios te avisa que hay un problema. La única excepción es cuando reiniciar es físicamente peligroso (un actuador que vuelve a energizarse en medio de un ciclo); ahí el estado seguro se mantiene en hardware, no en un while(1) del firmware.

CF2.7 Logging en un sistema sin consola

El equipo está adentro de un tablero. No hay terminal, no hay pantalla, y cuando falla te lo devuelven en una caja con la nota "no anda". Todo lo que vas a tener para diagnosticar es lo que el firmware haya guardado antes de morir.

⚠️ printf bloqueante es la forma más elegante de arruinar el timing. Un printf("%.2f\n", v) por un UART a 115.200 baudios manda ~10 bytes = ~870 µs bloqueando. Adentro de una ISR, eso son 870 µs de latencia agregada a todas las interrupciones de igual o menor prioridad — el problema de jitter que CF1 analiza en detalle. Y encima el %f arrastra _printf_float de newlib: entre 4 y 10 KB de flash y unos 200–400 bytes de stack, en un chip donde peleás por cada KB. El printf de debug que dejaste "temporalmente" en la ISR de captura es la causa raíz de una cantidad no menor de bugs de timing.

La arquitectura correcta separa producir el log de transmitirlo. El productor solo copia bytes a un buffer circular en RAM y vuelve; una tarea de baja prioridad vacía ese buffer cuando el sistema tiene tiempo.

/* log_ring.c — buffer circular lock-free para un productor y un consumidor.
   Con potencia de 2 no hace falta módulo, y el wrap de los índices es automático. */
#include <stdint.h>
#include <string.h>
#include <stdatomic.h>

#define LOG_CAP   2048u                 /* 2 KB. Potencia de 2 obligatoria. */
#define LOG_MASK  (LOG_CAP - 1u)

static uint8_t             buf[LOG_CAP];
static atomic_uint_least32_t w = 0, r = 0;
static atomic_uint_least32_t perdidos = 0;

/* Llamable desde una ISR: no toma locks, no bloquea, tiempo acotado. */
void log_push(const uint8_t *datos, uint32_t n)
{
    uint32_t wi = atomic_load_explicit(&w, memory_order_relaxed);
    uint32_t ri = atomic_load_explicit(&r, memory_order_acquire);

    if ((LOG_CAP - (wi - ri)) < n) {     /* no entra */
        atomic_fetch_add(&perdidos, 1);  /* CUENTO lo que tiro. Nunca lo escondo. */
        return;
    }
    for (uint32_t i = 0; i < n; i++)
        buf[(wi + i) & LOG_MASK] = datos[i];

    atomic_store_explicit(&w, wi + n, memory_order_release);
}

/* Corre en la tarea de menor prioridad. Puede bloquear todo lo que quiera. */
void log_drenar(void)
{
    uint32_t ri = atomic_load_explicit(&r, memory_order_relaxed);
    uint32_t wi = atomic_load_explicit(&w, memory_order_acquire);

    while (ri != wi) {
        uint32_t chunk = wi - ri;
        if (chunk > 64u) chunk = 64u;
        uint8_t tmp[64];
        for (uint32_t i = 0; i < chunk; i++) tmp[i] = buf[(ri + i) & LOG_MASK];
        uart_tx_dma(tmp, chunk);         /* DMA: la CPU queda libre */
        ri += chunk;
    }
    atomic_store_explicit(&r, ri, memory_order_release);
}

CF2.8 Bootloader y actualización de firmware (OTA)

Si tu producto va a estar cinco años en campo, va a necesitar actualizarse. No es opcional ni una feature de lujo: es un requisito regulatorio. El Cyber Resilience Act de la Unión Europea obliga a proveer actualizaciones de seguridad por un mínimo de cinco años o la vida del producto, y su calendario ya está corriendo — la obligación de reportar vulnerabilidades explotadas activamente en 24 horas entra en vigor el 11 de septiembre de 2026, y el resto de las obligaciones (diseño seguro, evaluación de conformidad, SBOM) el 11 de diciembre de 2027, con multas de hasta 15 millones de euros o el 2,5% de la facturación global. Un producto sin OTA no va a poder llevar marcado CE.

💡 El invariante no negociable del OTA. Un update interrumpido —se cortó la luz, se cayó el enlace, la imagen llegó corrupta— no puede dejar el equipo muerto. Si un corte de energía en el peor instante posible convierte tu producto en un ladrillo que hay que ir a buscar con una camioneta, no tenés un sistema de actualización: tenés una ruleta rusa con 2.000 equipos instalados. Todo el diseño de esta sección existe para garantizar ese único invariante.

En un chip de 512 KB, A/B directamente no entra, y esa es una decisión de selección de componente, no de software. La alternativa —descargar a una flash SPI externa de 2 MB por USD 0,30 y copiar sobre el slot único al reiniciar— cambia el costo de silicio por una ventana de vulnerabilidad durante la copia, que se cubre con un modo de recuperación en el bootloader.

La secuencia completa, con el punto de no retorno

1. Descarga. La imagen nueva se escribe en el slot secundario. El equipo sigue corriendo normalmente con el primario. Si se corta acá, no pasó nada: el secundario queda a medias y se descarta.
2. Verificación. Antes de tocar nada, se valida la imagen completa: tamaño, CRC/hash, magic, versión, e ID de producto (que un firmware de otro modelo no entre nunca — es la causa más común de bricking masivo). La firma criptográfica que verifica que la imagen es realmente tuya se ve en CF6; acá nos ocupa la integridad.
3. Marcado y reinicio. Se escribe un flag "hay imagen candidata" y se reinicia. Este es el punto de no retorno, y por eso ese flag tiene que escribirse de forma atómica (CF2.9).
4. El bootloader decide. Verifica de nuevo la imagen candidata —no confía en la verificación que hizo la app— y hace el swap. Si algo falla, arranca la vieja.
5. Confirmación. La imagen nueva arranca en modo de prueba. Si llega a un estado sano —conectó a la red, leyó los sensores, pasó sus autotests— llama a image_confirm(). Si no confirma y el watchdog la mata, el bootloader revierte automáticamente a la anterior.
/* El paso 5 es el que separa un OTA que funciona de uno que te deja 2.000 ladrillos.
   La confirmación NO va al final del arranque: va después del PRIMER trabajo útil. */
void app_main(void)
{
    sistema_init();

    if (ota_estado() == OTA_EN_PRUEBA) {
        log_warn("imagen en prueba, version %s: hay que confirmarla", VERSION);
        /* NO confirmo todavía. Si me cuelgo antes del check, el bootloader revierte. */
    }

    for (;;) {
        ciclo_principal();

        if (ota_estado() == OTA_EN_PRUEBA && autotest_completo_ok()) {
            ota_confirmar();                 /* recién ACÁ. Punto de no retorno #2 */
            log_info("imagen %s confirmada", VERSION);
        }
    }
}

/* autotest_completo_ok() tiene que probar lo que ROMPE un update malo:
   - ¿el enlace de red se estableció? (si no, no vas a poder mandar el próximo update)
   - ¿los sensores responden?
   - ¿la configuración persistente se leyó y validó?
   - ¿pasaron N minutos sin resets?  <-- el criterio más útil y el más olvidado */
📌 Un rollback automático que no cubre "el equipo arranca pero no se puede volver a actualizar" no sirve. El peor escenario del OTA no es la imagen que no bootea —esa se revierte sola—: es la imagen que bootea perfecto, confirma, y tiene roto el cliente de actualización. Ahí perdiste el único canal para arreglarlo. Por eso el autotest tiene que incluir la capacidad de recibir el próximo update, y por eso se despliega en oleadas: 1% de la flota, 24 horas de observación, 10%, 50%, resto.
Estado de la herramienta en 2026. MCUboot, bajo el paraguas de Trusted Firmware, es el bootloader seguro de referencia para MCUs de 32 bits: firma y validación de imágenes, anti-rollback, estrategias de swap y de overwrite, y una capa de abstracción de flash. Es el bootloader por defecto de Zephyr y está integrado en el SDK de NXP MCUXpresso, en ESP-IDF y en Microchip Harmony. Para Linux embebido el equivalente es U-Boot con esquemas A/B (SWUpdate, RAUC, Mender). El consenso de la industria en 2026 es explícito: escribir tu propio bootloader casi nunca es la decisión correcta. El costo de mantener y auditar código que, si tiene un bug, deja la flota entera inalcanzable, supera cualquier ahorro.

CF2.9 Configuración persistente sin corromperse

Tu equipo guarda una dirección de servidor, unos coeficientes de calibración, un umbral. Esos datos tienen que sobrevivir al corte de energía. Y ahí aparece un problema que la mayoría descubre en campo: si se corta la luz en el medio de la escritura, la config queda a medias, y en el próximo arranque el equipo lee basura.

Tres particularidades de la flash embebida hacen esto difícil:

RestricciónConsecuencia práctica
Solo se puede pasar de 1 a 0 escribiendo; para volver a 1 hay que borrar un sector enteroNo podés "actualizar un campo": tenés que borrar y reescribir todo el bloque
El borrado tarda de decenas de ms a ~2 s según el tamaño del sectorLa ventana de vulnerabilidad a un corte es enorme comparada con una escritura

Escritura atómica: dos copias más un secuencial

/* El patrón ping-pong. Nunca se borra el bloque que contiene la config válida. */
typedef struct {
    uint32_t magia;        /* CFG_MAGIA */
    uint32_t version;      /* del esquema: permite migrar formatos viejos */
    uint32_t secuencia;    /* el MÁS ALTO gana. Así se sabe cuál es la última */
    /* ---- payload ---- */
    char     servidor[64];
    uint32_t intervalo_s;
    float    cal_offset;
    float    cal_ganancia;
    /* ---- fin payload ---- */
    uint32_t crc;          /* CRC32 de todo lo anterior. SIEMPRE el último campo */
} cfg_t;

#define CFG_SLOT_A  ((const cfg_t *)0x080F0000)
#define CFG_SLOT_B  ((const cfg_t *)0x080F8000)

static bool cfg_valida(const cfg_t *c)
{
    return c->magia == CFG_MAGIA
        && c->crc == crc32((const uint8_t *)c, offsetof(cfg_t, crc));
}

err_t cfg_cargar(cfg_t *out)
{
    bool a_ok = cfg_valida(CFG_SLOT_A);
    bool b_ok = cfg_valida(CFG_SLOT_B);

    if (a_ok && b_ok) {
        /* Resta con wraparound: sobrevive al desborde del contador de secuencia */
        *out = ((int32_t)(CFG_SLOT_A->secuencia - CFG_SLOT_B->secuencia) > 0)
             ? *CFG_SLOT_A : *CFG_SLOT_B;
        return ERR_OK;
    }
    if (a_ok) { *out = *CFG_SLOT_A; return ERR_OK; }
    if (b_ok) { *out = *CFG_SLOT_B; return ERR_OK; }

    *out = CFG_POR_DEFECTO;        /* ambos corruptos: arranco igual, degradado */
    log_err("config corrupta en ambos slots, usando defaults");
    return ERR_CRC;
}

err_t cfg_guardar(const cfg_t *nueva)
{
    /* Escribo SIEMPRE en el slot que NO está vigente. Si se corta la luz
       en cualquier punto de esta función, el slot vigente sigue intacto. */
    bool usar_a = !(cfg_valida(CFG_SLOT_A)
                    && (!cfg_valida(CFG_SLOT_B)
                        || (int32_t)(CFG_SLOT_A->secuencia - CFG_SLOT_B->secuencia) > 0));

    cfg_t tmp = *nueva;
    tmp.magia     = CFG_MAGIA;
    tmp.version   = CFG_VERSION;
    tmp.secuencia = cfg_secuencia_actual() + 1u;
    tmp.crc       = crc32((const uint8_t *)&tmp, offsetof(cfg_t, crc));

    const cfg_t *destino = usar_a ? CFG_SLOT_A : CFG_SLOT_B;
    TRY(flash_borrar_sector((uint32_t)destino));
    TRY(flash_escribir((uint32_t)destino, (const uint8_t *)&tmp, sizeof tmp));

    /* Verificación de lectura: la flash puede aceptar la escritura y guardar mal */
    if (!cfg_valida(destino)) return ERR_CRC;
    return ERR_OK;
}
📌 El CRC va último y se calcula sobre todo lo anterior, por una razón física. La flash se escribe en orden ascendente de direcciones. Si el corte ocurre a mitad de la escritura, el CRC —que está al final— nunca llegó a escribirse, y el registro queda inválido por construcción. Poner el CRC primero rompe esta garantía: podrías tener un CRC correcto sobre datos que se escribieron a medias.

Wear leveling: cuando escribís seguido

El ping-pong resuelve la atomicidad pero no el desgaste: alterna entre dos sectores, así que duplica la vida útil y nada más. Si escribís cada minuto, 10.000 ciclos por sector × 2 sectores = 13 días. La solución es un log circular de registros dentro de un sector: escribís registros nuevos consecutivamente sin borrar, y solo cuando el sector se llena borrás y arrancás de nuevo.

/* Sector de 2 KB, registros de 32 bytes = 64 registros por borrado.
   Escribiendo 1 vez por minuto: 64 min por ciclo de borrado.
   10.000 ciclos * 64 min = 640.000 min = 1,2 AÑOS.  Sigue sin alcanzar.
   Con 2 sectores alternados: 2,4 años. Con 8 sectores: casi 10 años. */

/* El registro válido es el ÚLTIMO cuyo CRC cierra. Buscar desde el final es O(n)
   con n = 64; a 3 µs por lectura son 200 µs en el arranque. Aceptable. */
static const registro_t *ultimo_valido(const uint8_t *sector, size_t n_regs)
{
    for (size_t i = n_regs; i > 0; i--) {
        const registro_t *r = (const registro_t *)(sector + (i - 1) * sizeof(registro_t));
        if (r->magia == REG_MAGIA && reg_crc_ok(r)) return r;
    }
    return NULL;
}
El error de diseño de fondo: guardar en flash algo que no lo necesita. Antes de pelear con el wear leveling, preguntate qué estás escribiendo tan seguido. Un contador de horas de funcionamiento no necesita persistirse cada minuto: mantenelo en RAM y escribilo cada hora, o —mucho mejor— aprovechá la detección de brownout (ver CF3) para escribirlo cuando se está yendo la energía, con el capacitor de la fuente como reserva. Pasás de 525.600 escrituras por año a 4, y el problema desaparece en vez de administrarse.

CF2.11 Cuándo NO sobre-arquitecturar

Todo lo anterior tiene un costo, y aplicarlo sin criterio produce un desastre distinto pero igual de real: 200 líneas de lógica repartidas en 14 archivos con tres niveles de indirección, donde entender qué pasa cuando se aprieta un botón lleva media hora.

📌 La arquitectura se paga con complejidad, y la complejidad también es un modo de falla. Un sistema que nadie entiende completo es un sistema donde nadie puede razonar sobre sus estados. Cada capa, cada indirección y cada abstracción tiene que estar comprada por un beneficio concreto que puedas nombrar.

Sensor que lee y prende un LED. 200 líneas. Una persona, un año de vida útilUn archivo, superloop, sin capasHAL + drivers + servicios + FSM en tabla
Datalogger con 3 sensores y SD. 2.000 líneas. Se actualiza a manoDrivers separados de la app, FSM con switch, memoria estática, watchdog simpleOTA A/B, pools, logging binario

Las tres preguntas que deciden. (1) ¿Alguien va a poder llegar físicamente al equipo? Si sí, el costo de un fallo baja un orden de magnitud y podés simplificar. (2) ¿Cuánto tiempo va a correr entre reinicios? Un equipo que se apaga cada noche perdona la fragmentación; uno que corre tres años no. (3) ¿Cuánta gente va a tocar este código y por cuánto tiempo? La arquitectura es, sobre todo, comunicación con el que venga después — incluido vos mismo dentro de dos años.
El error simétrico, y el más caro de los dos. Arrancar con el superloop de 200 líneas "porque es un prototipo", y que ese prototipo se convierta en el producto sin que nadie tome la decisión de reescribirlo. Retrofitear capas, pools y OTA sobre 8.000 líneas de firmware acoplado cuesta entre tres y diez veces más que haberlo diseñado así desde el principio. El punto de decisión no es "cuando el código crezca": es el día que alguien dice "esto lo vamos a vender".

🧑‍🎓 Worked Example — "se cuelga cada tres semanas"

Un controlador de riego industrial, 140 unidades instaladas, firmware en un STM32F411 con 128 KB de RAM. El cliente reporta que "algunos equipos se cuelgan cada dos o tres semanas". No hay patrón por sitio, ni por hora, ni por clima. En el banco de pruebas nunca pasó. Nadie tiene un log de nada.

Paso 0 — Lo que NO se hace. No se empieza a leer código buscando el bug, ni se agrega un printf "por las dudas", ni se sube el timeout del watchdog. Con un fallo de tres semanas de período, cada iteración de prueba a ciegas cuesta tres semanas.

Paso 1 — Instrumentar antes de diagnosticar. Se despliega una versión con lo mínimo para que el equipo se explique solo: causa de reset desde RCC->CSR, contexto de fallo en .noinit, contador de reinicios, y publicación de pico de cada pool y del high water mark de stack en la telemetría de cada hora. Son unas 120 líneas y no cambia ninguna lógica.

📌 La instrumentación no es un paso previo al diagnóstico: es el diagnóstico. Un bug que aparece cada tres semanas en 140 equipos no se caza mirando código; se caza haciendo que los 140 equipos cuenten qué les pasó. Con 140 unidades y un período de 3 semanas, tenés unos 6 eventos por día a nivel flota: de "irreproducible" pasás a tener muestras diarias.

Paso 2 — La primera revelación, a las 48 horas. Nueve equipos reportaron reinicio con causa = RST_WDT. Los equipos nunca se "colgaban": el watchdog los reiniciaba y volvían a operar en dos segundos. El operador solo veía un hueco en los datos y lo reportaba como "se colgó". El problema real no era un cuelgue: era un reinicio silencioso que nadie estaba registrando.

Paso 3 — Quién no reportaba. El bitmask faltantes del watchdog por tareas apuntaba siempre al mismo bit: WDT_TAREA_RED. La tarea de red se quedaba sin llegar a completar su ciclo. Y en la telemetría de la hora previa aparecía el dato que cerraba el caso:

Paso 4 — La causa raíz. El cliente de red hacía realloc del buffer de recepción según el tamaño anunciado en cada mensaje: de 512 bytes para un ACK a 4.096 para un bloque de configuración. Cada realloc que no podía crecer en el lugar dejaba un hueco del tamaño viejo. Tras ~3 semanas de tráfico variable, el bloque contiguo más grande caía por debajo de 4.096 bytes, el realloc devolvía NULL, y el código —que no chequeaba el retorno— desreferenciaba NULL. El HardFault_Handler por defecto era un while(1);, así que la tarea de red quedaba muerta y el watchdog reiniciaba el equipo. Nunca hubo una fuga de memoria: hubo fragmentación, que es otra cosa y no se cura sola.

Checkpoint — ¿lo tenés claro?

Tu malloc nunca falló en dos meses de pruebas en el banco. ¿Por qué no alcanza como evidencia?

Porque la fragmentación es acumulativa y depende del historial completo de alocaciones y liberaciones, no del tiempo transcurrido. Un banco de pruebas casi siempre ejercita un patrón de tráfico uniforme —el mismo mensaje, el mismo tamaño, el mismo ritmo— que no produce huecos de tamaños variados. En campo el patrón es irregular por naturaleza: mensajes de 40 bytes mezclados con bloques de 4 KB, ráfagas y silencios. Además, dos meses de banco pueden ser dos órdenes de magnitud menos ciclos de alocación que dos meses de campo. La única evidencia que sirve no es "no falló": es poder acotar el peor caso en papel, y con malloc de propósito general eso es imposible. Con un pool de bloques fijos el peor caso es N × TAM y se conoce en tiempo de compilación.

¿Por qué un watchdog pateado desde una interrupción de timer es peor que no tener watchdog?

Porque te da una falsa sensación de seguridad, que es peor que la ausencia declarada de una protección. El timer del sistema es lo último que deja de funcionar: sigue corriendo aunque todas las tareas estén trabadas en un semáforo, aunque la máquina de estados haya caído en un estado inválido, aunque el sensor no responda desde hace un día. El watchdog termina vigilando su propio mecanismo de pateo en vez del sistema. El patrón correcto invierte la responsabilidad: cada tarea reporta que completó trabajo útil (no que "está viva"), un supervisor de baja prioridad verifica que todas reportaron, y solo entonces patea. Que el supervisor sea de baja prioridad es parte del diseño: si el sistema está saturado no llega a correr, y el reset ocurre — que es exactamente lo que querés.

Un update OTA se interrumpe justo cuando el bootloader está copiando la imagen nueva sobre el slot primario. ¿Por qué el equipo no queda muerto?

Porque la copia no es el punto de no retorno: el estado del proceso vive en metadatos persistentes, fuera de la imagen. Al reiniciar, el bootloader —que es inmutable y nunca se actualiza por OTA— vuelve a leer esos metadatos, ve que había un swap en curso y lo reanuda desde donde quedó, usando el área de scratch como memoria intermedia. Si en cambio la imagen candidata no valida (hash, versión, ID de producto), la descarta y arranca la anterior, que sigue íntegra en el otro slot. Y si la nueva imagen sí arranca pero no confirma dentro de su ventana de prueba, el watchdog la mata y el bootloader revierte solo. Son tres redes independientes, y la clave de todas es la misma: siempre existe una imagen íntegra y arrancable en el dispositivo, en todo instante del proceso.

Resumen ejecutivo

  • Las cuatro capas (HAL / drivers / servicios / app) se pagan con 2–5 ciclos por llamada indirecta y compran dos cosas caras: poder testear en el host y poder cambiar de MCU cuando el chip se discontinúe — que pasa siempre.
  • Máquinas de estados explícitas. El switch alcanza hasta ~6 estados; la tabla de transición cuesta N×M×8 bytes de flash y compra exhaustividad. Tres booleanos son ocho estados, de los cuales la mitad son imposibles y van a ocurrir igual.
  • No hay malloc después del arranque. Fragmentación acumulativa, tiempo no determinista y un fallo sin salida. MISRA C:2012 21.3/21.4 lo prohíbe, y es obligatorio bajo ISO 26262 e IEC 61508. Alternativas: estático, pool O(1), arena. Y siempre registrá el high water mark.
  • El "33% de RAM usada" del build es .data + .bss: no incluye el stack. Acotalo con -fstack-usage, con patrón centinela para la tendencia, y detectá el desborde de verdad con una región de guarda en la MPU — la mejor relación costo/beneficio del módulo.
  • Watchdog por tareas, nunca por timer. Cada tarea reporta trabajo completado; un supervisor de baja prioridad patea solo si reportaron todas. Y leé siempre el registro de causa de reset.
  • Errores: una convención única en todo el proyecto, goto cleanup (que en C es lo correcto), ASSERT solo para invariantes internos y return ERR_x para datos del mundo. Ante un fallo fatal: estado seguro primero, rastro después, y NVIC_SystemReset() — nunca while(1).
  • Logging diferido. Ring buffer en RAM más una tarea de baja prioridad; contexto de fallo en .noinit para que sobreviva al reset. Un printf bloqueante en una ISR son ~870 µs de jitter a 115.200 baudios y hasta 10 KB de flash por el %f.
  • OTA A/B con rollback automático. El invariante: siempre hay una imagen íntegra y arrancable. Confirmá recién después del primer trabajo útil, y que el autotest incluya la capacidad de recibir el próximo update. Usá MCUboot; escribir tu propio bootloader casi nunca es la decisión correcta. El CRA lo vuelve obligatorio: reporte de vulnerabilidades explotadas desde el 11-sep-2026, resto de obligaciones el 11-dic-2027.
  • Config persistente: dos slots, número de secuencia, CRC al final (porque la flash se escribe en orden ascendente), y verificación por lectura. Y antes de pelear con el wear leveling, preguntate por qué escribís tan seguido.
  • Testing: unitarios en el host con HAL falsa (con ASan y UBSan, que en el target no tenés), simulación con Renode en cada PR, HIL antes de cada release.
  • No sobre-arquitecturés. Un sensor de 200 líneas no necesita cinco capas. Pero el error simétrico —dejar que el prototipo se convierta en producto sin rediseñarlo— cuesta entre 3 y 10 veces más.

  2. Implementá el pool de bloques fijos de CF2.3 completo, incluyendo el high water mark, y escribí tests en el host que verifiquen: agotamiento (el bloque N+1 devuelve NULL), doble free del mismo puntero, y free de un puntero ajeno al pool. Corrélos bajo AddressSanitizer.
  3. Convertí una máquina de estados escrita con if anidados (buscá una en cualquier ejemplo de Arduino) a tabla de transición. Contá cuántas casillas de la tabla quedaron sin cubrir en la versión original: esos son los bugs latentes que tenía.
  4. Implementá el watchdog supervisado por tareas de CF2.5 con al menos tres tareas. Después provocá deliberadamente que una se trabe y verificá que (a) el equipo se reinicia, y (b) el bitmask en .noinit identifica correctamente cuál falló.
  5. Medí el costo real de printf: compilá el mismo programa con y sin una llamada que use %f y compará el tamaño del .text. Después medí con un osciloscopio (o con un GPIO y un contador de ciclos) cuánto bloquea un printf de 10 caracteres por UART a 115.200 baudios.
  6. Implementá el esquema de configuración de doble slot de CF2.9. Después escribí un test que simule un corte de energía interrumpiendo la escritura en 10 puntos distintos del proceso, y verificá que en los 10 casos el sistema arranca con una configuración válida.
  7. Diseñá en papel el mapa de flash para un producto con OTA A/B en un MCU de 512 KB, con una aplicación de 200 KB. ¿Entra? ¿Qué tenés que sacrificar? Compará el costo contra agregar una flash SPI externa y justificá la decisión con números.
  8. Tomá un driver de sensor que ya tengas escrito y refactorizalo para que reciba la interfaz de bus por parámetro en vez de llamar directamente a la HAL del fabricante. Escribí cuatro tests en el host: camino feliz, ID de chip incorrecto, timeout del bus, y punteros nulos.
  9. Instalá Renode y corré el binario real de un proyecto tuyo en la plataforma simulada. Guioná una falla —que un sensor I²C deje de responder a partir del segundo 30— y verificá que tu firmware la maneja como esperabas en vez de trabarse.

🧠 Autoevaluación

1. Un equipo lleva 7 meses en campo. La telemetría muestra que la memoria libre total del heap se mantiene estable en ~21 KB, pero el bloque contiguo más grande bajó de 9 KB a 1,5 KB. ¿Qué está pasando?

La firma de la fragmentación es exactamente esa: total estable, bloque máximo en caída. Si fuera una fuga, el total bajaría. Si fuera el stack invadiendo el heap, ya habría corrupción y HardFaults. La fragmentación externa es acumulativa, depende del historial de alocaciones y no se cura sola: el próximo pedido grande va a devolver NULL aunque "sobre" memoria. Por eso la única solución real no es un heap mejor, sino no tener heap: pool de bloques de tamaño fijo, donde la fragmentación externa es imposible por construcción.

2. Estás por poner en producción un firmware con OTA A/B. ¿En qué momento debería la imagen nueva llamar a ota_confirmar()?

Confirmar al principio del main() anula todo el mecanismo: le estás diciendo al bootloader "esta imagen está bien" antes de tener ninguna evidencia de que lo esté, y perdés el rollback automático justo cuando más lo necesitás. El peor escenario del OTA no es la imagen que no bootea —esa se revierte sola por watchdog—, es la que bootea perfecto pero tiene roto el cliente de actualización: ahí perdiste el único canal para arreglarla y hay que ir físicamente. Por eso el autotest previo a la confirmación tiene que incluir la capacidad de recibir el próximo update.

3. Estás decidiendo dónde llamar a ASSERT() y dónde devolver un código de error. Llega un frame por el puerto serie con un CRC que no cierra. ¿Qué corresponde?

Un CRC que no cierra es ruido eléctrico, un cable flojo, un vecino con un variador de frecuencia: pasa todos los días y el sistema tiene que seguir funcionando. ASSERT es para invariantes internos —cosas que si son falsas, tu código tiene un bug—, y en producción termina en un reset. Meter un assert sobre datos que vienen de afuera convierte un frame corrupto en un reinicio del equipo, y le regala a cualquiera una denegación de servicio de un solo paquete mal formado. La opción de loguear cada frame malo en flash es además un buen camino para quemar el sector de flash en semanas.
