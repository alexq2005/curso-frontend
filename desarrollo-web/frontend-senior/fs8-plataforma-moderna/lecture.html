FS8 — La plataforma web moderna: qué podés hacer hoy sin framework

FS8.0 Por qué este módulo

Durante los siete módulos anteriores desarmaste el navegador, el motor de JavaScript, la red, las métricas, el CSS a escala, la accesibilidad y la cadena de build. En todos ellos apareció, sin decirlo, la misma pregunta de fondo: ¿esto lo resuelve la plataforma o lo tengo que traer de afuera? Este módulo la responde de frente.

💡 La tesis del módulo. Buena parte del trabajo que en 2015 justificaba meter un framework —componentes con estilos encapsulados, transiciones entre vistas, modales accesibles, observar el scroll, guardar datos localmente, funcionar sin red— hoy lo hace el navegador. Eso no significa que los frameworks sobren. Significa que cambió qué dependencias podés justificar, y que la respuesta "usamos React porque necesitamos componentes" ya no es un argumento: es una costumbre.

Nada de lo que sigue es militancia. Cada tema viene con su costo, su punto de quiebre y con qué se mide. Un senior no es el que sabe más APIs: es el que puede defender por qué eligió una y descartó las otras dos.

📌 Leé bien la tercera columna. Es donde vive el argumento honesto a favor de los frameworks, y es la que casi nunca aparece en los posts que dicen "ya no necesitás React". La plataforma te da capacidades. Un framework te da capacidades más un modelo mental compartido, y eso último es lo que hace que ocho personas escriban código parecido.

FS8.1 Web Components: las tres piezas

"Web Components" no es una API: son tres especificaciones que se usan juntas y que se pueden usar por separado.

1. Custom Elements. Registrás una etiqueta HTML propia asociada a una clase que extiende HTMLElement. El navegador te avisa cuando se conecta al documento, cuando se desconecta y cuando cambia un atributo que declaraste observado.
2. Shadow DOM. Un árbol de DOM separado, colgado del elemento, con encapsulación real de estilos en las dos direcciones: tus reglas no salen y las del host no entran (con excepciones importantes que vemos en un minuto).
3. Templates y slots. <template> es markup inerte que no se parsea como contenido activo hasta que lo clonás. <slot> es el agujero por donde entra el contenido que el usuario del componente puso entre las etiquetas.
// Un componente completo, sin dependencias.
const hoja = new CSSStyleSheet();
hoja.replaceSync(`
  :host {
    /* Reset defensivo: las propiedades heredables SÍ cruzan el shadow boundary */
    all: initial;
    display: block;
    font: var(--card-font, 500 14px/1.5 system-ui, sans-serif);
    color: var(--card-color, #111);
    background: var(--card-bg, #fff);
    border: 1px solid var(--card-border, #d4d4d8);
    border-radius: 10px;
    padding: 1rem;
  }
  :host([estado="error"]) { border-color: #dc2626; }
  :host([hidden]) { display: none; }   /* [hidden] NO funciona solo si definís display */
  .titulo { font-weight: 700; margin: 0 0 .35rem; }
  ::slotted(p) { margin: 0; }          /* estilar contenido del light DOM */
`);

class TarjetaEstado extends HTMLElement {
  // Solo estos atributos disparan attributeChangedCallback
  static observedAttributes = ["estado", "titulo"];

  #root;

  constructor() {
    super();
    // delegatesFocus se explica en el Worked Example: cambia dónde cae el foco
    this.#root = this.attachShadow({ mode: "open" });
    this.#root.adoptedStyleSheets = [hoja];   // una sola hoja compartida por N instancias
    this.#root.innerHTML = `
      <p class="titulo"></p>
      <slot>Sin contenido</slot>
    `;
  }

  connectedCallback() {
    // Ojo: puede correr MÁS DE UNA VEZ si el elemento se mueve de lugar en el DOM
    this.#render();
  }

  attributeChangedCallback(nombre, viejo, nuevo) {
    if (viejo !== nuevo) this.#render();
  }

  #render() {
    this.#root.querySelector(".titulo").textContent = this.getAttribute("titulo") ?? "";
  }

  // API de propiedades: los atributos son SIEMPRE strings, las propiedades no
  get estado() { return this.getAttribute("estado"); }
  set estado(v) { this.setAttribute("estado", v); }
}

customElements.define("tarjeta-estado", TarjetaEstado);
<tarjeta-estado titulo="Envío #4412" estado="ok">
  <p>Salió del depósito hace 2 horas.</p>
</tarjeta-estado>
El contrato de estilos de un web component tiene cuatro puertas. :host para el elemento en sí; custom properties (--card-bg) que sí atraviesan el shadow boundary y son tu API de theming; ::part() para exponer partes internas a propósito; y ::slotted() para estilar lo que puso el consumidor. Todo lo demás queda adentro. Diseñar esas cuatro puertas es diseñar el componente.

Declarative Shadow DOM: shadow root sin JavaScript

El pecado original de los web components era que sin JavaScript no había nada. Eso se resolvió: el shadow root se puede escribir en el HTML que manda el servidor.

<tarjeta-estado titulo="Envío #4412">
  <template shadowrootmode="open">
    <style>:host { display:block; border:1px solid #d4d4d8; border-radius:10px; padding:1rem }</style>
    <p class="titulo">Envío #4412</p>
    <slot></slot>
  </template>
  <p>Salió del depósito hace 2 horas.</p>
</tarjeta-estado>
El parser crea el shadow root durante el parseo del HTML, antes de que corra una línea de tu JS. El primer render sale gratis y el contenido es indexable. La hidratación —conectar el markup ya existente con tu clase en vez de volver a pintar todo— sigue siendo trabajo tuyo: en connectedCallback tenés que detectar this.shadowRoot ya presente y no pisarlo con innerHTML.

FS8.2 Dónde brillan los Web Components y dónde no

La pregunta útil no es "¿son buenos?". Es "¿cuál es la propiedad que necesito y que solo ellos me dan?". Esa propiedad es una sola: ser una etiqueta HTML. Todo lo que sabe poner HTML —cualquier framework, cualquier CMS, cualquier email builder, cualquier editor WYSIWYG— sabe usarlos.

Los cuatro límites honestos

1. Formularios. Un custom element no participa de un <form> por defecto: no se envía, no valida, no responde a reset. Se arregla con ElementInternals, y el soporte hoy está en los tres motores, pero es código que escribís vos. 
class InputMoneda extends HTMLElement {
  static formAssociated = true;          // ← sin esto, nada de lo de abajo existe
  #internals;

  constructor() {
    super();
    this.#internals = this.attachInternals();
    this.attachShadow({ mode: "open" }).innerHTML = `<input type="text" inputmode="decimal">`;
    this.shadowRoot.querySelector("input")
      .addEventListener("input", (e) => this.#actualizar(e.target.value));
  }

  #actualizar(texto) {
    const valor = Number(texto.replace(/[^\d.-]/g, ""));
    this.#internals.setFormValue(String(valor));   // así viaja en el submit
    if (Number.isNaN(valor) || valor <= 0) {
      // El tercer argumento (el ancla) es obligatorio: sin él el browser
      // no sabe a qué enfocar cuando el usuario aprieta "Enviar"
      this.#internals.setValidity(
        { customError: true }, "Ingresá un monto mayor a cero",
        this.shadowRoot.querySelector("input"),
      );
    } else {
      this.#internals.setValidity({});
    }
  }

  formResetCallback()   { this.#actualizar(""); }
  formDisabledCallback(deshabilitado) { this.shadowRoot.querySelector("input").disabled = deshabilitado; }
}
customElements.define("input-moneda", InputMoneda);
2. Accesibilidad. Los id no cruzan el shadow boundary. Un aria-labelledby="titulo" adentro del shadow root no puede apuntar a un id del documento, ni al revés. Se mitiga con ElementInternals (que expone role, ariaLabel y compañía sin ensuciar el markup del host), pero las referencias ARIA entre raíces siguen siendo un problema abierto —por eso el tema aparece año tras año en los focus areas de Interop.
3. Nombres globales. customElements.define("mi-boton", …) registra en un registro global del documento. Dos versiones del mismo componente en la misma página se pisan y la segunda tira NotSupportedError. Los scoped custom element registries son justamente un focus area de Interop 2026: o sea, todavía no son interoperables. Mientras tanto: prefijo de proyecto en cada nombre y un if (!customElements.get(nombre)) defensivo.
4. DX. No hay JSX, no hay HMR, los atributos son strings, el tipado es manual y las devtools no te muestran un árbol de componentes con su estado. Librerías como Lit tapan casi todo eso por ~5 KB, y ahí ya volviste a tener una dependencia — que puede ser una decisión perfectamente razonable, pero conviene tomarla con los ojos abiertos.
El error de encuadre más común: comparar "Web Components vs React" como si compitieran por el mismo puesto. React resuelve cómo describo una UI que cambia. Los Web Components resuelven cómo distribuyo un pedazo de UI a consumidores que no controlo. Se pueden usar juntos —y en un design system corporativo grande, casi siempre se usan juntos.

FS8.3 WebAssembly: qué es de verdad

WebAssembly no es "JavaScript rápido". Es un formato binario para una máquina virtual de pila, con tipado estático, que sirve de destino de compilación para C, C++, Rust, Go, Zig, C#, Kotlin y varios más. El navegador lo valida, lo compila a código máquina y lo ejecuta en el mismo hilo y en el mismo sandbox que tu JS.

💡 Los dos hechos que explican todo lo demás. (1) Wasm no tiene acceso al DOM ni a las Web APIs: todo lo que quiera tocar la página pasa por una llamada a JavaScript. (2) Su memoria es un ArrayBuffer plano —memoria lineal— separado del heap de JS: pasar un string o un objeto significa copiarlo. Casi todos los casos donde Wasm decepciona se explican con uno de esos dos.

Dónde está el estándar en 2026

Para dimensionar: Wasm aparece en torno al 5,5% de las cargas de página de Chrome a principios de 2026, contra ~4,5% el año anterior. Crece de manera sostenida y sigue siendo una tecnología de nicho profundo, no de uso general. Que sea nicho no la hace irrelevante: ese 5% incluye Figma, Photoshop Web, AutoCAD Web y prácticamente todo el video en el navegador.

Cuándo gana

Cómputo denso sobre datos contiguos. Códecs de audio y video, criptografía, compresión, físicas, procesamiento de imágenes, inferencia de modelos, parsers binarios. Mucho trabajo por byte, poca interacción con el DOM.
Código portado que sería una locura reescribir. ffmpeg.wasm, sqlite-wasm, motores de PDF, motores de juego. El valor acá no es la velocidad: es no reescribir 300.000 líneas de C probadas durante veinte años.
Cuando querés el mismo algoritmo en cliente y servidor, bit a bit idéntico. Un motor de reglas o un validador compilado una vez y ejecutado en los dos lados elimina toda una clase de bugs de divergencia.

Cuándo pierde

⚠️ El cruce de frontera se come la ganancia. Cada llamada JS↔Wasm tiene overhead, y los strings y objetos hay que serializarlos hacia y desde la memoria lineal. Si tu función hace poco trabajo por llamada, vas a estar más lento que en JS puro. La regla práctica: pocas llamadas que hacen mucho, no muchas llamadas que hacen poco. 
// Antipatrón: 100.000 cruces de frontera para hacer sumas
for (const px of pixeles) resultado.push(wasm.procesarPixel(px));   // ← más lento que JS

// Patrón correcto: UN cruce, el buffer entero, el loop adentro de Wasm
const ptr = wasm.exports.reservar(pixeles.length);
new Uint8Array(wasm.exports.memory.buffer, ptr, pixeles.length).set(pixeles);
wasm.exports.procesarBuffer(ptr, pixeles.length);
const salida = new Uint8Array(wasm.exports.memory.buffer, ptr, pixeles.length).slice();
wasm.exports.liberar(ptr);
⚠️ El costo de arranque es real y se paga siempre. Hay que descargar el .wasm, validarlo y compilarlo antes de la primera llamada. Un runtime con GC puede pesar cientos de kilobytes. Si el usuario típico nunca usa la función que Wasm acelera, le cobraste el arranque a todos para beneficiar a pocos. 
// Compilación en streaming: compila MIENTRAS descarga, no después.
// Exige que el servidor mande Content-Type: application/wasm (si no, cae al camino lento).
const { instance } = await WebAssembly.instantiateStreaming(fetch("/motor.wasm"), imports);

// Y medí las tres fases por separado, porque se optimizan distinto:
performance.mark("wasm:inicio");
const mod = await WebAssembly.instantiateStreaming(fetch("/motor.wasm"), imports);
performance.mark("wasm:listo");
const t = performance.measure("wasm:arranque", "wasm:inicio", "wasm:listo");
console.log(`arranque ${t.duration.toFixed(1)} ms`);   // descarga + compilación
// Después, aparte: tiempo de marshalling vs tiempo de cómputo dentro del módulo.
📌 Wasm es una optimización de cómputo, no una arquitectura de UI. Un "framework en Wasm" que pinta DOM termina haciendo una llamada a JS por cada nodo que toca — y ahí perdiste. Cargá Wasm bajo demanda, adentro de un Worker cuando el trabajo sea largo, y solo después de haber medido que el cuello de botella es cómputo y no red ni layout (FS4).

⚠️ Por qué localStorage es una trampa de rendimiento. Es la única API de almacenamiento sincrónica que queda. Cada getItem y cada setItem bloquea el hilo principal: durante esa operación no hay layout, ni paint, ni respuesta a un click. Serializar un objeto de 500 KB a JSON y escribirlo es una long task perfectamente medible, y en un móvil de gama baja se convierte en INP malo (FS4). Peor todavía: se lee también en el arranque, justo cuando el hilo principal es más escaso.

  for (const entrada of lista.getEntries()) {
    if (entrada.duration < 100) continue;
    for (const s of entrada.scripts) {

OPFS: el sistema de archivos que casi nadie usa

El Origin Private File System es un sistema de archivos real, invisible para el usuario, privado por origen. Está en Baseline Widely available desde marzo de 2023 (Chrome/Edge 86+, Firefox 111+, Safari 15.2+). Su superpoder está en los Workers:

// ── worker.js ── createSyncAccessHandle SOLO existe dentro de un dedicated worker
const raiz    = await navigator.storage.getDirectory();
const archivo = await raiz.getFileHandle("datos.bin", { create: true });
const acceso  = await archivo.createSyncAccessHandle();

// Lecturas y escrituras SINCRÓNICAS, sin await, sin copias intermedias.
// Esto es exactamente lo que permite correr SQLite compilado a Wasm en el navegador.
const buffer = new Uint8Array(1024);
acceso.read(buffer, { at: 0 });
acceso.write(buffer, { at: 0 });
acceso.flush();
acceso.close();          // si no cerrás, el archivo queda bloqueado para el resto
No confundas OPFS con la File System Access API. Son parientes pero distintas: showOpenFilePicker() / showSaveFilePicker() tocan archivos del usuario, y siguen siendo solo Chromium — no son Baseline. OPFS, en cambio, es interoperable hace años. Si tu feature depende de escribir en la carpeta del usuario, necesitás un fallback con <input type="file"> más una descarga.

⚠️ Las dos cosas que te van a arruinar el día. Primero: la expulsión es por origen y todo junto — si el navegador decide limpiar, se van IndexedDB, Cache API y OPFS al mismo tiempo, no el pedacito que menos usás. Segundo: en Safari, un usuario que no visita tu sitio durante siete días vuelve con todo vacío. La excepción es una PWA instalada en la pantalla de inicio, que queda exenta de ese plazo. 
async function prepararAlmacenamiento() {
  const { usage, quota } = await navigator.storage.estimate();
  const usadoMB = (usage / 1_048_576).toFixed(1);
  const cuotaMB = (quota / 1_048_576).toFixed(0);

  // persist() NO es una garantía: Firefox le pregunta al usuario, Chromium y Safari
  // deciden solos según cuánto interactuó con el sitio. Puede devolver false.
  const persistido = await navigator.storage.persist();

  return { usadoMB, cuotaMB, persistido };
}
📌 Tu almacenamiento local es una caché, no una base de datos. El criterio es simple y no admite excepciones: si el usuario perdería trabajo cuando el navegador expulse los datos, esos datos tienen que estar sincronizados con el servidor. Todo lo demás es reconstruible, y tu código tiene que poder reconstruirlo sin drama.

FS8.5 Offline de verdad

Hay una distancia enorme entre "mi app pasa el audit de PWA" y "mi app funciona sin red". La primera se logra en una tarde. La segunda es un proyecto.

💡 Offline-first no es un plugin: es una decisión de arquitectura de datos. Es la decisión de que la fuente de verdad de la UI es la base local y el servidor es un peer con el que sincronizás, en vez de que la red sea la fuente de verdad y el caché un consuelo. Todo lo demás —el service worker, el manifest, los íconos— es plomería alrededor de esa decisión.

La cola de salida y la idempotencia

// Toda mutación se escribe local PRIMERO y se encola después.
// La clave de idempotencia es lo que hace que reintentar sea seguro:
// si el POST llegó pero la respuesta se perdió, el servidor reconoce el id y no duplica.
async function guardarNota(db, texto) {
  const op = {
    id: crypto.randomUUID(),            // ← clave de idempotencia
    tipo: "crear_nota",
    payload: { texto },
    creadoEn: Date.now(),
    intentos: 0,
  };
  const tx = db.transaction(["notas", "outbox"], "readwrite");
  tx.objectStore("notas").put({ id: op.id, texto, estado: "pendiente" });
  tx.objectStore("outbox").put(op);
  await tx.done;
  drenarOutbox(db);                     // intenta ya; si falla, queda para después
  return op.id;                          // la UI ya puede mostrar la nota
}

async function drenarOutbox(db) {
  if (!navigator.onLine) return;        // onLine miente: dice "hay red", no "hay internet"
  for (const op of await db.getAll("outbox")) {
    try {
      const r = await fetch("/api/notas", {
        method: "POST",
        headers: { "Content-Type": "application/json", "Idempotency-Key": op.id },
        body: JSON.stringify(op.payload),
      });
      if (r.status >= 500) throw new Error("reintentable");
      if (r.status >= 400) { await marcarFallida(db, op, await r.text()); continue; }
      await confirmar(db, op, await r.json());
    } catch {
      // Backoff exponencial con tope. Sin tope, un servidor caído se convierte
      // en un ataque de denegación de servicio hecho por tus propios usuarios.
      op.intentos++;
      setTimeout(() => drenarOutbox(db), Math.min(2 ** op.intentos * 1000, 60_000));
      return;
    }
  }
}

// Reintentá también cuando la pestaña vuelve al frente: es el disparador
// más confiable que existe, y funciona en todos los navegadores.
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "visible") drenarOutbox(db);
});
addEventListener("online", () => drenarOutbox(db));
⚠️ No apoyes tu sincronización en Background Sync. La Background Sync API es solo Chromium (Chrome, Edge, Opera, Samsung): ni Firefox ni Safari la implementan. La Periodic Background Sync es todavía más restringida —Chromium, solo en PWA instaladas y sujeta al puntaje de engagement del sitio. Usalas como mejora, nunca como mecanismo principal. Tu red de seguridad son visibilitychange y el evento online.

Conflictos: elegí uno, escribilo, no improvises

EstrategiaCuándo sirveQué te cuesta
Last write winsDatos de un solo usuario en varios dispositivosPérdida silenciosa de ediciones. Necesitás relojes confiables (o versiones)
Versión / ETag y rechazoCuando el usuario puede resolver a manoHay que diseñar una UI de conflicto, que nadie quiere diseñar

El error clásico: no elegir. Un equipo implementa "offline" sin decidir la estrategia y termina con last-write-wins de hecho, porque el último PUT pisa. Nadie lo documentó, así que cuando un usuario reporta que perdió una edición, no hay a qué comparar el comportamiento. La estrategia de conflictos va escrita en un ADR antes de la primera línea de código de sincronización.

FS8.6 Streaming y renderizado en el servidor

HTTP transporta un stream de bytes y el parser del navegador es incremental: empieza a construir el DOM con el primer chunk, sin esperar el cierre de </html>. Eso, que es de 1993, es la base de todo el SSR moderno.

// SSR con streaming, sin framework. El shell sale en el primer chunk;
// los datos lentos salen cuando llegan, sin bloquear nada de lo anterior.
export default {
  async fetch(req) {
    const stream = new ReadableStream({
      async start(c) {
        const enc = new TextEncoder();
        // 1) Head + shell: el navegador ya puede pedir CSS y pintar
        c.enqueue(enc.encode(`<!DOCTYPE html><html lang="es"><head>
          <link rel="stylesheet" href="/app.css"></head><body>
          <header>Mi tienda</header>
          <main id="lista"><p class="cargando">Cargando productos…</p></main>`));

        // 2) La consulta lenta corre mientras el usuario YA ve algo
        const productos = await consultarProductos();

        // 3) Out-of-order: mandamos el contenido real al final y lo movemos
        //    a su lugar con un script inline. Así el orden de LLEGADA
        //    no tiene por qué ser el orden VISUAL de la página.
        c.enqueue(enc.encode(`<template id="datos-lista">${render(productos)}</template>
          <script>{
            const t = document.getElementById("datos-lista");
            document.getElementById("lista").replaceChildren(t.content);
            t.remove();
          }</script></body></html>`));
        c.close();
      },
    });
    return new Response(stream, { headers: { "Content-Type": "text/html; charset=utf-8" } });
  },
};
Eso es, en esencia, lo que hacen <Suspense> de React, <Await> de Remix y {#await} de Svelte. Saber que abajo hay un <template> y un script inline te cambia la relación con esas abstracciones: dejan de ser magia y pasan a ser una comodidad que también podés escribir vos.

Qué resuelve el SSR de verdad — y qué no

El SSR agrega un servidor a tu vida. Con render estático o SPA pura, tu frontend es un montón de archivos en una CDN: no se cae, no escala mal, no tiene incidentes a las 3 de la mañana. Con SSR tenés un servicio con latencia, con estado de conexiones, con despliegues, con memoria que se puede fugar y con una base de datos que se puede saturar. Eso no lo hace una mala decisión — lo hace una decisión, que se justifica con LCP y TTFB de campo (FS4), no con la sensación de que "se siente más rápido".

  const puede = document.startViewTransition
    && !matchMedia("(prefers-reduced-motion: reduce)").matches;

FS8.8 Progressive enhancement en 2026

El argumento contra el progressive enhancement siempre fue el mismo: "casi nadie navega sin JavaScript". Es cierto y es irrelevante, porque nunca se trató de eso.

💡 El punto no son los usuarios sin JS: es que el JS falla. Y falla por razones que no controlás. La red corta a mitad del bundle. El CDN está bloqueado por una red corporativa o por un país. Un navegador viejo no parsea una sintaxis nueva y todo el archivo muere en el parseo. Una extensión rompe un global. Un móvil con 2 GB de RAM mata la pestaña. El HTML y el CSS degradan —lo que no se entiende se ignora—, mientras que el JavaScript es binario: anda o no anda.
FallaSPA sin PECon progressive enhancement
El bundle no descarga (red, CDN, bloqueo)Página en blancoContenido legible, links que funcionan
Error de JS en el arranquePágina en blancoContenido legible, formularios que envían
Navegador viejo o exóticoPágina en blancoVersión sin adornos, usable
Bot / crawler / preview de linkDepende del renderizado del botHTML real, siempre
Red lentísimaSpinner durante 8 segundosContenido a los 800 ms, interactivo después

Qué significa cuando tu app es una SPA

No significa "hacé que todo funcione sin JS". Eso es imposible en un editor de video y absurdo en un IDE. Significa definir tu superficie mínima y garantizarla en capas:

Capa 1 — Estructura. La navegación principal son <a href> con URLs reales, no <div onclick>. Los formularios tienen action y method. El contenido crítico está en el HTML inicial.
Capa 2 — Presentación. El CSS hace la página usable aunque el JS nunca llegue. Nada crítico depende de una clase que agrega JavaScript.
Capa 3 — Comportamiento. El JS intercepta y mejora: en vez de un submit completo, un fetch y una actualización parcial. Si el JS no llegó, el submit normal funciona.
<!-- Sin JS: POST normal, el servidor responde con la página actualizada.
     Con JS: se intercepta, se manda en segundo plano y no parpadea nada. -->
<form id="suscribir" action="/api/suscribir" method="post">
  <label for="email">Tu email</label>
  <input id="email" name="email" type="email" required>
  <button>Suscribirme</button>
  <p class="resultado" aria-live="polite"></p>
</form>
document.getElementById("suscribir").addEventListener("submit", async (e) => {
  e.preventDefault();
  const form = e.currentTarget;
  const salida = form.querySelector(".resultado");
  const boton  = form.querySelector("button");

  boton.disabled = true;
  try {
    // action y method salen del HTML: una sola fuente de verdad para la URL
    const r = await fetch(form.action, { method: form.method, body: new FormData(form) });
    salida.textContent = r.ok ? "¡Listo! Revisá tu correo." : "No pudimos suscribirte.";
  } catch {
    // Si falla la red, dejamos que el navegador haga el envío clásico:
    // degradar hacia la capa de abajo también es progressive enhancement
    form.submit();
  } finally {
    boton.disabled = false;
  }
});
📌 La pregunta correcta no es "¿PE sí o no?". Es: ¿cuál es la parte de mi producto que tiene que funcionar aunque el JavaScript no llegue? En un e-commerce, esa parte es ver un producto y su precio. En un banco, ver el saldo. En un diario, leer la nota. Definila, escribila en la documentación del proyecto y ponele un test. Lo demás puede exigir JS con toda tranquilidad.

FS8.9 Detección de features y estrategia de soporte

La decisión de "qué navegadores soportamos" se toma casi siempre por opinión —"los últimos dos", "los que usa el equipo"— y casi nunca con datos. Desde 2023 hay una herramienta que convierte esa discusión en una consulta.

Baseline: el vocabulario común

NivelQué significaCómo se usa en una decisión
Limited availabilityFalta al menos un motor coreSolo como enhancement con fallback, o detrás de un flag
Newly availableYa está en Chrome, Edge, Firefox y Safari (escritorio y móvil)Usable, pero el parque de dispositivos viejos todavía no rotó
Widely available30 meses después de ser NewlyUsar sin ceremonia. Es el default sensato para producción
Los 30 meses no son arbitrarios: son el tiempo empírico que tarda el parque de dispositivos reales en rotar lo suficiente como para que la cola de versiones viejas deje de importar. Y hay una segunda señal, gratis: Interop. Los focus areas los eligen entre Apple, Google, Igalia, Microsoft y Mozilla, y en Interop 2026 son 20 áreas surgidas de más de 150 propuestas. Que algo esté en la lista significa que todavía no es interoperable — es una advertencia disfrazada de buena noticia.

⚠️ El costo real de un polyfill no son sus kilobytes. Son cuatro: (1) bytes y tiempo de parseo, muchas veces para el 100% de los usuarios cuando solo el 3% lo necesita; (2) sus propios bugs, que se comportan distinto de la implementación nativa; (3) el conflicto cuando la feature nativa llega y el polyfill la pisa; y (4) que nadie los borra. Todo polyfill que agregues lleva un comentario con fecha de revisión, o dentro de tres años sigue ahí.

📌 Una política se puede verificar; una opinión no. "Soportamos los navegadores que cubren el 98% de nuestras sesiones de los últimos 90 días, más Baseline Widely available, revisado cada trimestre" es una política: cualquiera puede consultarla y saber si una feature entra o no. "Soportamos los últimos dos navegadores" es una opinión, y una que cambia de significado sola cada seis semanas.

FS8.10 Cuándo NO necesitás un framework — y cuándo sí

Sin militancia y sin la trampa de comparar solamente el tamaño del bundle. El costo de un framework casi nunca son sus kilobytes: es el acoplamiento a su modelo mental y a su ciclo de versiones. Y el costo de no usarlo es que el sistema de componentes, el routing, el manejo de estado y las convenciones los escribís y los mantenés vos.

Una tercera opción que casi nadie menciona. Entre "todo React" y "todo a mano" existe una franja ancha y muy razonable: HTML servido más islas de interactividad (Astro), HTML sobre el cable (htmx), una capa fina de reactividad (Alpine, Lit), o tu propio código — porque 200 líneas tuyas que entendés completas suelen ser mejores que una dependencia de 40 KB que entendés a medias. Elegir una de esas no es cobardía: es dimensionar.
Los dos errores simétricos. El primero: meter un framework en un sitio de contenido de doce páginas, y terminar con hidratación, un servidor de render y un pipeline de build para mostrar texto. El segundo: construir una aplicación con cuarenta vistas y estado compartido sin framework, y a los dos años tener un framework propio —peor documentado, sin comunidad y con un solo mantenedor que se va a ir. El segundo error es más caro que el primero, aunque el primero se critique más en redes.

FS8.11 El futuro cercano y cómo no correr atrás de cada novedad

La plataforma se mueve más rápido que nunca y eso genera una ansiedad que no ayuda a nadie. La respuesta no es leer más: es tener un sistema.

1. Una sola fuente de verdad de soporte. Baseline y el dashboard de web status. Se consulta cuando hay una decisión que tomar, no todos los días.
2. Un pulso trimestral, no diario. Los digests mensuales de Baseline y las notas de versión de los cuatro motores. Una hora cada tres meses te deja mejor informado que scrollear todos los días.
3. Usá Interop como agenda. Los focus areas del año te dicen qué va a dejar de ser un problema. Los de 2026 —View Transitions, scoped custom element registries, Navigation API, JSPI, dialogs y popovers, container style queries, scroll-driven animations— son literalmente el índice de lo que vas a poder usar sin fallback en 2027.
4. Dos preguntas antes de adoptar cualquier cosa. ¿Qué problema medido resuelve? ¿Cuál es el plan si lo tengo que sacar? Si no podés responder las dos, no es una decisión técnica: es entusiasmo.
5. Un ADR de diez líneas por dependencia nueva. Fecha, problema, alternativas descartadas, criterio de salida. Es el único antídoto contra el "esto está acá porque siempre estuvo".
El antipatrón tiene nombre y es caro: adoptar por FOMO y descubrir el costo recién en la migración. Toda tecnología se ve barata mientras la estás agregando; el precio real se cobra el día que la querés sacar. Por eso el criterio de salida se escribe el día que entra, cuando todavía sos honesto.

class EstadoEnvio extends HTMLElement {
  static observedAttributes = ["codigo"];
  #root; #controlador;

  constructor() {
    super();
    // TRAMPA 3 (parte 1): delegatesFocus hace que enfocar el host lleve el foco
    // al primer elemento focuseable de adentro. Mejora el tabbing, pero cambia
    // dónde se dibuja el anillo de foco: hay que estilar :host(:focus-within).
    this.#root = this.attachShadow({ mode: "open", delegatesFocus: true });
    this.#root.adoptedStyleSheets = [estilos];
    this.#root.innerHTML = `
      <div role="status" aria-live="polite">
        <p class="estado">Consultando…</p>
        <button type="button" part="boton-detalle">Ver detalle</button>
      </div>`;

    this.#root.querySelector("button")
      .addEventListener("click", () => this.#emitir("detalle-solicitado", { codigo: this.codigo }));
  }

  connectedCallback() {
    // AbortController: un solo abort limpia TODOS los listeners al desconectar.
    // connectedCallback puede correr más de una vez si el host mueve el elemento.
    this.#controlador?.abort();
    this.#controlador = new AbortController();
    this.#consultar();
  }

  disconnectedCallback() { this.#controlador?.abort(); }

  attributeChangedCallback(n, viejo, nuevo) { if (viejo !== nuevo) this.#consultar(); }

  get codigo() { return this.getAttribute("codigo"); }

  #emitir(nombre, detail) {
    // TRAMPA 2: sin composed:true el evento MUERE en el shadow boundary
    // y el host nunca se entera. bubbles:true solo no alcanza.
    this.dispatchEvent(new CustomEvent(nombre, { detail, bubbles: true, composed: true }));
  }

  async #consultar() {
    if (!this.codigo) return;
    try {
      const r = await fetch(`https://api.ejemplo.com/envios/${this.codigo}`,
                            { signal: this.#controlador.signal });
      const { estado } = await r.json();
      this.#root.querySelector(".estado").textContent = estado;
      this.#emitir("estado-cambiado", { codigo: this.codigo, estado });
    } catch (e) {
      if (e.name === "AbortError") return;                  // desconexión, no es un error
      this.#root.querySelector(".estado").textContent = "No pudimos consultar el envío.";
    }
  }
}

// Registro defensivo: dos versiones del widget en la misma página no deben tirar

if (!customElements.get("envio-estado")) customElements.define("envio-estado", EstadoEnvio);

Paso 3 — Las tres trampas que aparecieron en la integración real.

Trampa 1 — Los estilos que sí se heredan. El shadow DOM bloquea los selectores del host, pero las propiedades heredables pasan igual: font-family, font-size, color, line-height, letter-spacing, text-transform, visibility. En el cliente de WordPress, un body { letter-spacing: .05em } hacía que el widget se viera distinto de los otros dos. Solución: all: initial en :host y volver a declarar lo que sí querés. Y aprovechar que las custom properties también cruzan —eso no es un bug, es tu API de theming: --envio-bg, --envio-color, --envio-radio.
Trampa 2 — Eventos que no salen, y un target que miente. Un CustomEvent con solo bubbles: true sube hasta el shadow root y ahí se detiene: el host nunca lo escucha. Hace falta composed: true. Y hay una segunda mitad: cuando el evento cruza, el navegador hace retargeting y event.target pasa a ser el <envio-estado>, no el botón interno. Si necesitás el elemento real, es event.composedPath()[0]. En Angular esto se manifestó como un handler que "no recibía nada"; en realidad recibía el host y el código buscaba un dataset que ahí no existía.
Trampa 3 — El foco. document.activeElement devuelve el host, no el elemento enfocado adentro: para llegar al real hay que bajar por host.shadowRoot.activeElement. Eso rompió la trampa de foco del modal del cliente de Next.js, que recorría document.querySelectorAll y no veía nada adentro del widget. Además, delegatesFocus: true mejora el tabbing pero mueve el anillo de foco al host, así que hay que estilar :host(:focus-within). Y recordá que aria-labelledby no cruza el boundary: la etiqueta accesible se resuelve adentro, o con ElementInternals.
Y la cuarta, que apareció después del deploy. Sin JavaScript, <envio-estado> es una caja vacía: el navegador la renderiza como un elemento desconocido y no muestra absolutamente nada. El fallback es progressive enhancement puro: poner contenido en el light DOM —un link al seguimiento en la web del correo— dentro de un <slot>, para que si el script nunca llega, el usuario igual tenga a dónde ir.
📌 Lo que hay que llevarse del ejercicio no es "usá custom elements". Es que la decisión se tomó por una propiedad concreta —"la integración tiene que ser una etiqueta HTML porque no controlo los tres hosts"— y no por preferencia de tecnología. Y que las tres trampas no eran obvias desde la documentación: aparecieron probando en los tres entornos reales. Ningún componente distribuible está listo hasta que se probó en un host que no controlás.

Checkpoint — ¿lo tenés claro?

¿Por qué un componente en WebAssembly que pinta DOM suele ser más lento que el mismo en JavaScript?

Porque Wasm no tiene acceso al DOM: cada operación sobre la página es una llamada que cruza la frontera hacia JavaScript, y ese cruce tiene overhead. Encima, los strings y objetos no viven en el heap de JS sino en la memoria lineal de Wasm, así que hay que copiarlos en cada dirección. Un componente de UI hace muchísimas operaciones chicas sobre el DOM: es el peor perfil posible: mucho marshalling y poco cómputo por llamada. Wasm gana en lo contrario —pocas llamadas que hacen mucho trabajo sobre datos contiguos: códecs, criptografía, físicas, imágenes, inferencia. Es una optimización de cómputo, no una arquitectura de UI.

Tu app guarda el borrador del usuario en IndexedDB y funciona perfecto. Un usuario de Safari vuelve a los diez días y perdió todo. ¿Qué pasó y qué se hace?

La política de Intelligent Tracking Prevention de Safari borra los datos creados por script cuando un origen pasa siete días sin interacción del usuario. No es un bug tuyo ni de IndexedDB, y no se arregla desde el código: la expulsión es por origen y se lleva IndexedDB, Cache API y OPFS al mismo tiempo. Las mitigaciones reales son tres, en orden: (1) sincronizar el borrador con el servidor —si perder el dato le cuesta trabajo al usuario, el dato no puede vivir solo en el cliente; (2) pedir navigator.storage.persist(), sabiendo que puede devolver false y que no es una garantía; y (3) para el caso de una PWA, ofrecer la instalación en la pantalla de inicio, que queda exenta del plazo de siete días. Y en cualquier caso, la UI tiene que sobrevivir a encontrar la base vacía.

¿Por qué "cross-document view transitions" y "view transitions" no son la misma decisión de adopción?

Porque tienen estados de soporte distintos. Las transiciones dentro de un mismo documento (document.startViewTransition()) están en los tres motores —Chrome 111+, Safari 18+, Firefox 144+— y su pseudo-clase :active-view-transition es Baseline Newly available desde enero de 2026. Las cross-document (@view-transition, para sitios multipágina) funcionan en Chromium y en Safari 18.2+, pero Firefox todavía no las envía: MDN las marca como disponibilidad limitada y no son Baseline; de hecho View Transitions es un focus area de Interop 2026, que es precisamente la señal de que falta interoperabilidad. La consecuencia práctica es buena: donde no hay soporte, la navegación simplemente ocurre sin animación. Es un enhancement con degradación perfecta, así que se puede usar hoy — pero como adorno, nunca como algo de lo que dependa el funcionamiento.

Resumen ejecutivo

  • Web Components valen cuando la propiedad que necesitás es "ser una etiqueta HTML": design systems que cruzan frameworks y widgets embebibles. Sus límites reales son formularios (ElementInternals), accesibilidad entre raíces, el registro global de nombres y la DX.
  • WebAssembly gana en cómputo denso y en código portado; pierde por el cruce de frontera, por no tocar el DOM y por el costo de arranque. Wasm 3.0 es estándar W3C desde 2025 y WasmGC está en los tres motores desde fines de 2024; JSPI todavía le falta a Safari.
  • Almacenamiento: IndexedDB por defecto, Cache API para respuestas HTTP, OPFS para archivos y bases embebidas, localStorage solo para banderas diminutas porque es sincrónico y bloquea el hilo principal. La expulsión es por origen y todo junto; Safari borra a los 7 días sin interacción.
  • Offline-first es una decisión de arquitectura de datos: la base local como fuente de verdad, una outbox idempotente y una estrategia de conflictos elegida a propósito. Background Sync es Chromium-only: no apoyes la sincronización ahí.
  • SSR mejora el primer contenido y la indexabilidad; no mejora la app después del arranque, no elimina el waterfall de datos y te agrega un servidor a mantener.
  • Progressive enhancement no es por los usuarios sin JS: es porque el JS falla, y el HTML degrada mientras el JS es binario. Definí tu superficie mínima y ponele un test.
  • Baseline convierte "qué soportamos" en una consulta reproducible: Newly available (los cuatro motores) y Widely available (30 meses después). Browserslist ya trae esas queries. Interop marca lo que todavía no es interoperable.
  • La pregunta framework sí/no se responde con estado compartido, cantidad de vistas, tamaño y rotación del equipo, vida esperada y ecosistema. Construir una app grande sin framework sale más caro que meter un framework en un sitio chico.

🧠 Autoevaluación

1. Tu custom element emite un CustomEvent con bubbles: true, pero el host nunca lo recibe. ¿Cuál es la causa?

Un evento con solo bubbles: true sube por el árbol interno y muere en el shadow root. Para cruzar hacia el documento hace falta composed: true. Y hay una segunda mitad que suele confundir después: cuando el evento cruza, el navegador hace retargeting y event.target pasa a ser el host, no el elemento interno que lo originó — si necesitás ese elemento real, usá event.composedPath()[0].

2. Estás decidiendo si usar @view-transition (cross-document) en un sitio multipágina. ¿Cuál es el razonamiento correcto en 2026?

Es el caso de manual de una degradación perfecta. MDN marca @view-transition como disponibilidad limitada —no es Baseline— porque Firefox todavía no la envía, y View Transitions es justamente un focus area de Interop 2026, que es la señal de que falta interoperabilidad. Pero el fallback no es una página rota: es un corte seco entre páginas, o sea el comportamiento normal de la web. Ojo con no confundirla con las transiciones dentro del mismo documento (document.startViewTransition()), que sí están en los tres motores.

3. Una app de notas guarda todo en IndexedDB y funciona sin red. ¿Qué le falta para llamarse offline-first en serio?

Guardar local resuelve la lectura; lo difícil es la escritura. Sin una outbox con clave de idempotencia, un reintento después de una respuesta perdida duplica el dato; y sin una estrategia de conflictos elegida a propósito, terminás con last-write-wins de hecho y ediciones que se pierden sin que nadie lo pueda explicar. Background Sync tampoco es la respuesta: es solo Chromium —ni Firefox ni Safari la implementan—, así que sirve como mejora pero nunca como mecanismo principal; los disparadores confiables son visibilitychange y el evento online.
