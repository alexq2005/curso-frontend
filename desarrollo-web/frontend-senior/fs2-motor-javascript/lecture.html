FS2 — El motor de JavaScript: V8 por dentro y el costo real del código

FS2.0 Por qué este módulo

En el M05 y el M07 aprendiste JavaScript: sintaxis, closures, prototipos, ES6+, módulos. En el M11 le pusiste tipos con TypeScript. En todo eso, el intérprete fue una caja negra que "ejecuta lo que escribís". Este módulo abre la caja.

No para que escribas JavaScript raro. Para que puedas responder, con evidencia, las preguntas que aparecen cuando una app crece: por qué la misma función tarda 4 ms la primera vez y 0,3 ms la décima; por qué agregar un campo opcional a un objeto degradó un loop un 40 %; por qué la pestaña come 900 MB después de veinte minutos; por qué el microbenchmark decía que la versión nueva era 8× más rápida y en producción no cambió nada.

💡 La tesis del módulo. JavaScript es rápido cuando el motor puede predecir. V8 apuesta constantemente: "esta función siempre recibe objetos con la misma forma", "esta propiedad siempre está en el mismo offset", "esta suma siempre es entre enteros". Cuando acertás, ejecutás código máquina especializado que compite con C. Cuando le rompés la predicción, el motor tira el trabajo y vuelve a empezar. Casi todo el mal rendimiento de JavaScript no viene de "hacer demasiadas cosas": viene de hacerlas de formas que impiden predecir.

La contracara, que este módulo repite hasta el cansancio: el motor casi nunca es tu cuello de botella. En una app real, el tiempo se va en la red (FS3), en el render (FS4) o en un algoritmo cuadrático que escribiste sin darte cuenta. Saber internals sirve para reconocer el 5 % de los casos en que la culpa sí es del motor, y para no perder dos días optimizando el otro 95 %.

🎭 Analogía. V8 es un mozo con memoria fotográfica. Si sos habitué y siempre pedís lo mismo, te trae el pedido antes de que abras la boca: eso es una inline cache. Si un día cambiás el pedido, se adapta y recuerda dos variantes. Si cambiás cada vez, deja de intentar adivinar y vuelve a preguntarte todo desde cero, cada vez. El mozo no se volvió lento: vos volviste tu comportamiento impredecible.

FS2.1 El pipeline de V8: cuatro tiers, no dos

La descripción clásica —"V8 interpreta con Ignition y optimiza con TurboFan"— está desactualizada desde 2023. Hoy V8 tiene cuatro niveles de ejecución, y la mayor parte del código de una app nunca llega al último.

// El camino de UNA función a través del motor
//
//   fuente JS
//      │  parse (o pre-parse: FS2.2)
//      ▼
//     AST
//      │  compilación a bytecode
//      ▼
//   IGNITION      intérprete · arranque instantáneo · junta feedback
//      │  ~pocas invocaciones
//      ▼
//   SPARKPLUG     JIT baseline · compila casi sin pensar · sin optimizar
//      │  ~500 invocaciones con feedback estable
//      ▼
//   MAGLEV        JIT optimizador rápido · código "suficientemente bueno"
//      │  el código sigue caliente
//      ▼
//   TURBOFAN      JIT optimizador pesado · código máquina especializado
//      │
//      └─ si una suposición falla → DEOPT → volvés a Ignition
TierQué haceCosto de compilarCalidad del código
IgnitionInterpreta bytecode y recolecta feedback de tiposNulo (no compila a máquina)Base de comparación (1×)
SparkplugTraduce bytecode a máquina casi 1:1, sin análisisMuy bajo, lineal en el tamaño~5–15 % mejor que interpretar
MaglevOptimiza con el feedback, en un solo pase (SSA)~10× más barato que TurboFanMuy cerca de TurboFan en código típico
TurboFanOptimización agresiva: inlining, escape analysis, unboxingEl más caro; corre en un hilo aparteLa mejor; código especializado por tipo
Contexto histórico rápido. Sparkplug llegó en Chrome 91 (2021) para tapar el hueco entre "interpretar" y "optimizar de verdad". Maglev se activó por defecto en Chrome 117 (2023). Y desde 2024–2025 el backend de TurboFan (selección de instrucciones, asignación de registros, generación de código) migró a una infraestructura nueva llamada Turboshaft, que redujo a la mitad el tiempo de compilación con igual o mejor calidad de código. Turboshaft no es un tier: es la cañería interna del último tier.

Qué significa realmente "warm up"

Una función recién cargada corre interpretada. A medida que se la llama, V8 acumula feedback vectors: qué tipos recibió, qué formas tenían los objetos, qué ramas se tomaron. Recién cuando ese feedback se estabiliza, el motor invierte en compilarla. Ese es el "calentamiento", y tiene consecuencias que se ven todos los días:

1. La primera ejecución nunca es representativa. Medir una función una sola vez mide el intérprete, no tu código. Es el error número uno de los microbenchmarks (FS2.7).
2. El código que corre una vez nunca se optimiza — y está bien. El handler de un click que se dispara tres veces por sesión vive y muere en Ignition. Optimizarlo sería tirar CPU a la basura. Por eso el tiering es guiado por perfil: subir de tier cuesta.
3. Tiering guiado por perfil (2024+). V8 ya no promueve solo por contador de invocaciones: también mira si el feedback es estable. Una función llamada 5.000 veces con formas siempre cambiantes puede quedarse en Sparkplug, porque optimizarla produciría código que se deoptimiza al instante.
El costo que nadie cuenta: la compilación también consume CPU. En un dispositivo de gama media, el trabajo de compilar y recompilar durante el arranque compite con el render del primer frame. Por eso "más optimización" no es gratis, y por eso las estrategias de arranque (FS4, FS7) valen más que cualquier micro-optimización de una función.

Verlo con tus propios ojos

Node expone las flags de V8 directamente. No hace falta compilar nada:

# Qué se optimiza y qué se deoptimiza, con motivo
node --trace-opt --trace-deopt app.js

# Solo las deopts, que es lo que suele importar
node --trace-deopt app.js 2>&1 | grep -i "deoptimizing"

# Ver el estado exacto de una función (requiere abrir las "natives")
node --allow-natives-syntax script.js

# Con Deopt Explorer (extensión de VS Code) se lee el log en una UI
node --prof --log-deopt --log-ic --log-maps app.js
// script.js — correr con: node --allow-natives-syntax script.js
function sumar(a, b) { return a + b; }

console.log(%GetOptimizationStatus(sumar));   // recién nacida: interpretada

for (let i = 0; i < 100000; i++) sumar(i, i + 1);
%OptimizeFunctionOnNextCall(sumar);
sumar(1, 2);
console.log(%GetOptimizationStatus(sumar));   // ahora: optimizada

sumar("a", "b");                              // ← cambio de tipo
console.log(%GetOptimizationStatus(sumar));   // volvió atrás: deoptimizada
%GetOptimizationStatus devuelve un bitfield, no un texto legible. En la práctica se usa la librería v8-natives o se lee el log de --trace-deopt, que dice en castellano de máquina qué suposición falló y en qué línea. Eso último es lo que convierte una discusión de opiniones en un hecho.

FS2.2 Lazy parsing: el bundle cuesta antes de ejecutar nada

Antes de que se ejecute una sola línea, el navegador tiene que leer tu JavaScript. Y parsear no es gratis: en dispositivos móviles de gama media, el análisis y la compilación inicial suelen ser el mayor costo de arranque, por encima de la ejecución.

📌 Un byte de JavaScript es mucho más caro que un byte de imagen. Una imagen se decodifica en un hilo aparte y no bloquea nada. Un byte de JS hay que descargarlo, descomprimirlo, parsearlo, compilarlo y ejecutarlo — y las tres últimas etapas pelean por el hilo principal, el mismo que dibuja la pantalla.

El pre-parser: el truco que hace tolerable un bundle grande

V8 no parsea todo tu archivo en profundidad. Usa dos parsers: el completo, que construye AST y emite bytecode, y el pre-parser, una versión mínima que solo verifica que la sintaxis sea válida y anota lo indispensable (dónde empieza y termina la función, qué variables externas captura). Cuando esa función se llama por primera vez, recién ahí se parsea de verdad.

// Este archivo tiene 500 KB. V8 NO parsea las 400 funciones a fondo:
// pre-parsea, marca los límites, y sigue.

function nuncaSeLlama() {          // pre-parseada: costo mínimo
  /* 200 líneas */
}

export function usada(x) {         // pre-parseada al cargar,
  return x * 2;                    // parseada de verdad al primer llamado
}

usada(21);                         // ← acá se paga el parse completo
El clásico que rompe el lazy parsing: las IIFE y el código de nivel superior. Todo lo que está en el top level del módulo se parsea y ejecuta sí o sí. Un const TABLA = [ ...5000 entradas ] o un framework que se inicializa al importarse se pagan completos, aunque la pantalla que los necesita no se muestre nunca. La solución no es micro-optimizar el parser: es no cargar ese código (import dinámico, code splitting — FS7).

Los números que sirven para decidir

Code cache: la segunda visita es otra historia. Chrome guarda el bytecode compilado junto al script en el caché de disco. En la segunda carga, V8 deserializa metadata en lugar de compilar. Esto tiene una consecuencia práctica poco conocida: si cambiás el hash del archivo en cada deploy, tirás a la basura el code cache de todos tus usuarios. Es un argumento real a favor de separar el vendor bundle (estable) del código de aplicación (volátil).
El costo de la estrategia. Dividir en muchos chunks chicos reduce el parse inicial pero multiplica los round-trips y complica el cacheo. La guía histórica de V8 —evitar el bundle único y partirlo cuando pasa unos 50–100 KB— es un punto de partida, no una ley. Con HTTP/2 y HTTP/3 (FS3) el costo por request bajó mucho, pero no es cero. Se mide con el panel Coverage: cuánto del JS cargado se ejecutó realmente en el primer minuto.

FS2.3 Hidden classes e inline caches: por qué el orden importa

Esta es la sección que más cambia cómo escribís código, así que vale la pena entenderla bien.

En JavaScript los objetos son diccionarios: podés agregar y quitar propiedades cuando quieras. Si V8 los implementara literalmente como hash maps, cada obj.nombre sería una búsqueda con hash. Sería correcto y lentísimo. Lo que hace V8 en cambio es asumir que los objetos vienen en formas repetidas, y le asigna a cada forma una estructura interna: la hidden class, o shape (también map en la jerga de V8).

const a = { x: 1, y: 2 };   // shape S1: {x en offset 0, y en offset 1}
const b = { x: 5, y: 9 };   // MISMA shape S1 → el motor los trata igual

// Agregar una propiedad crea una shape nueva y la encadena
const c = { x: 1 };         // shape S0  {x}
c.y = 2;                    // transiciona a S1 {x,y}

// Pero el ORDEN de creación define la cadena de transiciones:
const d = { y: 2 };         // shape T0  {y}
d.x = 1;                    // transiciona a T1 {y,x}  ← ¡NO es S1!
📌 {x, y} y {y, x} tienen los mismos datos y shapes distintas. Para vos son el mismo objeto. Para el motor son dos tipos diferentes, y cualquier función que reciba ambos deja de ser monomórfica.

Inline caches: monomórfico, polimórfico, megamórfico

Cada lugar del código donde accedés a una propiedad (un call site) tiene una cachecita adosada. La primera vez que se ejecuta, V8 anota "cuando el objeto tiene la shape S1, la propiedad x está en el offset 0". Las siguientes veces compara la shape y salta directo al offset: dos instrucciones de máquina.

Estado del ICCuántas shapes vioQué hace el motorCosto relativo
Monomórfico1Compara shape y lee el offset directo1× — el caso ideal
Polimórfico2 a 4Compara contra una lista corta de shapes~2–5× según el caso
Megamórfico5 o másAbandona: consulta un caché global con hash~10–20×, y bloquea el inlining
⚠️ El umbral es 4. V8 admite hasta cuatro shapes por call site. La quinta lo vuelve megamórfico, y ahí no solo se pierde el acceso rápido: TurboFan deja de poder inlinear esa función, y con el inlining se pierde en cascada todo lo que dependía de él (escape analysis, unboxing de números, eliminación de chequeos). Un solo call site megamórfico en un loop caliente puede costar más que todo lo demás junto.

El ejemplo medible

// benchmark de shapes — correr en Node o en la consola del navegador
function crear(n, variantes) {
  const out = [];
  for (let i = 0; i < n; i++) {
    const o = { id: i, valor: i * 2 };
    // agregamos un campo distinto según la variante → shapes distintas
    if (variantes > 1) o["extra" + (i % variantes)] = 1;
    out.push(o);
  }
  return out;
}

function sumar(items) {          // ← el call site de items[i].valor
  let t = 0;
  for (let i = 0; i < items.length; i++) t += items[i].valor;
  return t;
}

function medir(variantes) {
  const datos = crear(200000, variantes);
  for (let i = 0; i < 20; i++) sumar(datos);        // warm-up (FS2.7)
  const t0 = performance.now();
  let acc = 0;
  for (let i = 0; i < 50; i++) acc += sumar(datos);
  const ms = performance.now() - t0;
  return { variantes, ms: +ms.toFixed(1), acc };    // acc se consume: sin DCE
}

for (const v of [1, 2, 4, 8, 16]) console.log(medir(v));
Qué vas a ver. Los números exactos dependen de tu máquina y de la versión de V8, pero la forma del resultado es siempre la misma: 1 y 2 variantes van parejas; 4 empieza a despegarse; de 5 en adelante hay un escalón claro y después se aplana, porque una vez megamórfico da lo mismo tener 8 shapes que 80. Ese escalón es el hallazgo: no es un continuo, es un acantilado.

Cómo se escribe código con shapes estables

1. Inicializá todos los campos en el constructor, siempre en el mismo orden, aunque el valor sea null o undefined. Un campo que a veces existe y a veces no es la fuente número uno de polimorfismo accidental.
2. No uses delete. Borrar una propiedad puede empujar al objeto a "modo diccionario" (propiedades lentas), del que no vuelve. Poné obj.campo = null, o usá un Map si de verdad necesitás quitar claves.
3. Preferí clases o factories con forma fija a construir objetos literales campo por campo en distintas ramas de un if. Es la misma disciplina que ya te impone TypeScript en el M11 — pero acá el motivo no es la seguridad de tipos, es el rendimiento.
4. Cuidado con las funciones "genéricas" del núcleo. Un function get(obj, key) { return obj[key]; } compartido por toda la app ve cientos de shapes: es megamórfico por diseño. Duplicar ese helper en dos módulos suena a mala práctica, y sin embargo, en un camino caliente, dos call sites monomórficos ganan por lejos a uno megamórfico.
// ❌ Shapes inestables: el campo opcional bifurca el tipo
function crearUsuario(datos) {
  const u = { id: datos.id, nombre: datos.nombre };
  if (datos.avatar) u.avatar = datos.avatar;      // ← dos shapes distintas
  if (datos.equipo) u.equipo = datos.equipo;      // ← cuatro combinaciones
  return u;
}

// ✅ Shape única: los campos siempre están, aunque valgan null
function crearUsuario(datos) {
  return {
    id: datos.id,
    nombre: datos.nombre,
    avatar: datos.avatar ?? null,
    equipo: datos.equipo ?? null,
  };
}
El costo de esta regla. Objetos con campos siempre presentes ocupan un poco más de memoria y ensucian el JSON si los serializás tal cual. Y más importante: esto solo importa en código caliente. Aplicar la disciplina de shapes a un formulario que se llena una vez es ruido que hace el código peor sin ganar nada. El criterio es simple: si la función corre miles de veces por segundo o sobre miles de elementos, importa; si no, escribí lo que se lea mejor.

Elements kinds: los arrays también tienen shape

Menos conocido, e igual de importante: V8 clasifica los arrays según lo que contienen, y las transiciones son de una sola dirección.

const a = [1, 2, 3];        // PACKED_SMI_ELEMENTS   — enteros chicos, el más rápido
a.push(4.5);                // → PACKED_DOUBLE_ELEMENTS — doubles sin "cajita"
a.push("hola");             // → PACKED_ELEMENTS       — punteros genéricos
a[10] = 1;                  // → HOLEY_ELEMENTS        — con agujeros: el más lento

// Una vez que un array es HOLEY, NUNCA vuelve a PACKED.
const b = new Array(1000);  // ← nace HOLEY: 1000 agujeros
const c = [];               // ← nace PACKED y crece bien
El malentendido caro: "prealoco con new Array(n) para evitar los realocs". En V8 eso te da un array con agujeros, y todo acceso a un array holey paga un chequeo extra por elemento y una consulta al prototipo cuando encuentra un hueco. Si de verdad necesitás preasignar, usá new Array(n).fill(0) (que lo empaqueta) o directamente un TypedArray. Y en la enorme mayoría de los casos, un [] con push es lo correcto.

FS2.4 Deoptimización: cuando el motor tira el trabajo

TurboFan genera código que solo es válido bajo suposiciones. "Este argumento es siempre un entero de 32 bits." "Este objeto siempre tiene la shape S1." "Este array nunca tiene agujeros." Cada suposición viene con un chequeo barato al principio del código optimizado. Si el chequeo falla, se dispara una deoptimización: V8 descarta el código máquina, reconstruye el estado del intérprete a mitad de camino y sigue ejecutando en Ignition.

🎭 Analogía. Es un cocinero que prepara mise en place para el menú del día. Si entra un pedido fuera del menú, tiene que guardar todo, cocinar a mano ese plato, y recién después decidir si vale la pena rearmar el mise en place. Una vez está bien. Si pasa en cada pedido, hubiera sido mejor no preparar nada.

La forma correcta de decidirlo hoy no es citar una regla de 2015: es correr --trace-deopt y ver qué dice el motor tuyo, en tu versión.

📌 Una deopt aislada no es un problema; un ciclo de deopts sí. Lo que hay que buscar en el log es la misma función deoptimizándose una y otra vez: eso significa que V8 la reoptimiza, ella se cae, la reoptimiza… y estás pagando la compilación repetidamente además de correr sin optimizar. V8 tiene un límite: después de varias deopts en el mismo punto marca el código como deopt loop y deja de intentar optimizarlo. Cuando eso pasa, esa función se quedó lenta para siempre en esa sesión.

FS2.5 Memoria y GC: la pausa que se ve en pantalla

V8 nunca te devuelve memoria cuando vos querés: la devuelve cuando el recolector decide. Entender cuándo decide es lo que separa "la app se pone lenta después de un rato" de un diagnóstico.

Generacional: la mayoría de los objetos mueren jóvenes

El heap se parte en dos. La generación joven es chica (del orden de decenas de MB) y se recolecta seguido con el Scavenger, un algoritmo de copia con dos semi-espacios: recorre solo los objetos vivos, los copia al otro semi-espacio y descarta el resto de un saque. Como la mayoría de los objetos mueren jóvenes, casi nunca hay mucho que copiar, y las pausas son de menos de un milisegundo a unos pocos.

El objeto que sobrevive dos scavenges se promueve a la generación vieja, que se recolecta con Mark-Sweep-Compact: mucho más caro, porque tiene que recorrer todo el grafo de objetos alcanzables. V8 hace la mayor parte del marcado concurrentemente, en hilos aparte mientras tu JavaScript sigue corriendo, y el barrido también. Lo que queda como pausa real ("stop-the-world") son pasos incrementales cortos y una pausa final de unos pocos milisegundos en un heap sano.

📌 Por qué las pausas importan tanto en el frontend. A 60 fps tenés 16,7 ms por frame para hacer todo: ejecutar JS, calcular estilos, layout, paint, composite (FS4). Un scavenge de 1 ms se pierde en el ruido. Un major GC de 40 ms se come dos frames y medio y el usuario lo ve como un tirón. En un servidor Node, esos mismos 40 ms son latencia p99 pura. 
// Ver la presión de GC en tiempo real, sin herramientas
// (memory.usedJSHeapSize requiere Chrome; es aproximado y está redondeado)
let anterior = performance.memory?.usedJSHeapSize ?? 0;
setInterval(() => {
  const actual = performance.memory?.usedJSHeapSize ?? 0;
  const deltaMB = ((actual - anterior) / 1048576).toFixed(2);
  console.log(`heap ${(actual / 1048576).toFixed(1)} MB · Δ ${deltaMB} MB`);
  anterior = actual;
}, 2000);

El costo del "no generes basura". Es un consejo real pero se aplica mal. Reusar objetos y armar object pools a mano complica el código, introduce bugs de estado compartido y, en la mayoría de las apps, no cambia nada medible: el Scavenger es muy bueno recogiendo objetos efímeros. La regla razonable es: en un loop que corre 60 veces por segundo o sobre cientos de miles de elementos, evitá alocar; en el resto del código, escribí normal.

Qué es una fuga real en JavaScript

En un lenguaje con GC no hay "olvidarse de liberar". Una fuga es siempre lo mismo: algo que ya no usás sigue siendo alcanzable desde una raíz. Las raíces son las globales, la pila y los closures activos. Estas cuatro cubren el 95 % de los casos reales:

1. Listeners no removidos. Un addEventListener sobre window o document desde un componente que se desmonta mantiene vivo el handler, su closure, y todo lo que ese closure captura — incluido, muchas veces, el árbol de estado del componente entero.
2. Closures que capturan más de lo que necesitan. Una función que solo usa datos.id pero cierra sobre datos mantiene vivo el objeto completo. Y si varias funciones comparten un mismo context, la que sobrevive mantiene vivas las capturas de todas.
3. DOM desprendido (detached). Guardás una referencia a un nodo en un array o un mapa, después removés el nodo del documento. El nodo sale de la pantalla pero no de la memoria: y con él viene todo su subárbol, que puede ser gigante.
4. Cachés sin límite. Un Map que crece con cada request y nunca se poda no es un caché: es una fuga con buena prensa. Un caché necesita una política de expulsión (LRU, TTL, tamaño máximo) o no es un caché.
// ❌ Fuga clásica: listener global + DOM detached
class Panel {
  constructor(root) {
    this.root = root;
    this.filas = [];
    window.addEventListener("resize", () => this.reajustar());  // nunca se quita
  }
  render(items) {
    this.filas = items.map(i => {                 // guarda nodos...
      const el = document.createElement("div");
      el.textContent = i.nombre;
      this.root.appendChild(el);
      return el;
    });
  }
  limpiar() { this.root.innerHTML = ""; }         // ...que quedan detached
}

// ✅ Con ciclo de vida explícito
class Panel {
  constructor(root) {
    this.root = root;
    this.filas = [];
    this.onResize = () => this.reajustar();
    window.addEventListener("resize", this.onResize);
  }
  limpiar() {
    this.root.replaceChildren();
    this.filas.length = 0;                        // soltar las referencias
  }
  destruir() {
    window.removeEventListener("resize", this.onResize);
    this.limpiar();
    this.root = null;
  }
}
AbortController resuelve esto de una. addEventListener(tipo, fn, { signal }) desregistra el listener cuando abortás la señal. Un controller.abort() en el desmontaje limpia todos los listeners del componente sin que tengas que guardar cada referencia. Y WeakMap/WeakRef sirven para asociar datos a un objeto sin impedir que se recolecte — pero son la excepción, no el patrón por defecto.

Cazarlas: la técnica de los tres snapshots

Esta es la herramienta que hay que saber usar de memoria, porque es la única que da una respuesta concluyente.

Snapshot 1 — línea de base. Abrí DevTools → Memory → Heap snapshot. Poné la app en el estado inicial de la acción que sospechás (por ejemplo: la lista cerrada). Tomá el snapshot.
Ejecutá la acción sospechosa varias veces. Abrí y cerrá el panel 10 o 20 veces. Repetir importa: distingue una fuga real del ruido de un caché que se llenó una sola vez.
Snapshot 2. Volvé al mismo estado inicial. Tomá el segundo snapshot.
Repetí y tomá el Snapshot 3. Ahora seleccioná el snapshot 3 y en el selector de arriba elegí "Comparison" contra el snapshot 2, o filtrá por Objects allocated between Snapshot 1 and Snapshot 2. Lo que sobrevivió a dos ciclos completos y sigue creciendo linealmente es tu fuga.
📌 La columna que importa es Retained Size, no Shallow Size. Shallow es lo que ocupa el objeto en sí (casi siempre irrelevante). Retained es cuánta memoria se liberaría si ese objeto desapareciera — es decir, todo lo que él mantiene vivo. Un objeto de 40 bytes con un retained size de 12 MB es exactamente lo que estás buscando. Después, el panel Retainers te muestra la cadena desde la raíz: ahí está el culpable, con nombre y apellido.
Para DOM detached hay un atajo: en el buscador del heap snapshot escribí Detached y vas a ver directamente los Detached HTMLDivElement y compañía. Chrome también tiene un panel Detached Elements dedicado. Y para diferenciar "fuga" de "el heap creció y se estabilizó", el Allocation instrumentation on timeline muestra barras por asignación: las que quedan azules al final son las que no se liberaron.

Array vs TypedArray

Acá hay un matiz que casi todo el mundo se saltea. Se suele decir "los arrays de JS guardan punteros y los typed arrays guardan valores crudos". Es cierto a medias: si un array de V8 contiene únicamente doubles y no tiene agujeros (PACKED_DOUBLE_ELEMENTS), V8 guarda los números sin caja, contiguos, a 8 bytes cada uno, igual que un Float64Array.

const a = [1.5, 2.5, 3.5];          // PACKED_DOUBLE: 8 bytes por valor, contiguo
const b = new Float64Array([1.5, 2.5, 3.5]);   // idem, pero con garantía

a.push("x");                         // ← se rompe: ahora son punteros a objetos
// b.push(...)                       // ← no existe: los TypedArray no crecen
ElegíCuándoQué pagás

Y es la moneda de cambio con Wasm (FS2.9), con WebGL/WebGPU y con los Workers. Si tu dato es intrínsecamente numérico y de tamaño conocido, empezá ahí.

Strings: el mito de la concatenación

"Nunca concatenes strings en un loop, usá array.join('')" es otro consejo heredado que en V8 ya casi nunca aplica. V8 no copia los bytes cuando hacés a + b: crea un ConsString (una rope), un nodo con dos punteros. La concatenación es O(1). El costo se paga después, una sola vez, cuando alguien necesita los caracteres de verdad (una comparación, un indexOf, insertarlo en el DOM): ahí V8 aplana el árbol en un string contiguo.

let s = "";
for (let i = 0; i < 100000; i++) s += "x";   // 100.000 ConsStrings encadenados
s.length;                                     // O(1): la rope conoce su longitud
s.charCodeAt(50000);                          // ← acá se aplana, UNA vez
Dónde sí duele. Si dentro del loop leés el string parcial (un .length está bien, pero un .includes(), un .slice() o un .replace() no), forzás un aplanado por iteración y ahí sí tenés el O(n²) que el consejo viejo intentaba evitar. La regla real no es "no concatenes": es construí sin leer, y leé al final.

FS2.7 Los microbenchmarks mienten

Si algo de este módulo te tenés que llevar por encima del resto, es esto. La mayoría de las "optimizaciones" que circulan en internet son artefactos de mediciones mal hechas.

⚠️ Las cuatro formas en que tu benchmark te miente.
1. Dead code elimination. Si no consumís el resultado, TurboFan puede probar que el cálculo no tiene efecto y borrarlo entero. Medís 0,001 ms y creés que descubriste algo.
2. El motor optimiza lo que medís, no lo que corre en producción. Un loop que llama siempre a la misma función con los mismos tipos se vuelve monomórfico y se inlinea. En tu app esa función ve seis tipos y es megamórfica. Medís el caso ideal y desplegás el caso real.
3. Falta de warm-up. Sin iteraciones previas medís Ignition o Sparkplug, no el código optimizado. Con demasiadas, medís un caso especializado que no existe fuera del banco.
4. Varianza. Frecuencia dinámica de la CPU, otras pestañas, GC en el medio, resolución limitada de performance.now() (del orden de microsegundos, y más grosera sin cross-origin isolation). Una diferencia del 10 % entre dos corridas es ruido, no un resultado. 
// ❌ Benchmark que no mide nada
console.time("a");
for (let i = 0; i < 1e7; i++) Math.sqrt(i);      // resultado descartado → DCE
console.timeEnd("a");

// ✅ Benchmark defendible
function bench(nombre, fn, { warmup = 5, corridas = 15, iter = 1e6 } = {}) {
  let sumidero = 0;
  for (let w = 0; w < warmup; w++) sumidero += fn(iter);   // calentar los 4 tiers
  const tiempos = [];
  for (let r = 0; r < corridas; r++) {
    const t0 = performance.now();
    sumidero += fn(iter);                                   // resultado consumido
    tiempos.push(performance.now() - t0);
  }
  tiempos.sort((x, y) => x - y);
  const mediana = tiempos[Math.floor(tiempos.length / 2)];
  const p10 = tiempos[Math.floor(tiempos.length * 0.1)];
  const p90 = tiempos[Math.floor(tiempos.length * 0.9)];
  console.log(
    `${nombre}: mediana ${mediana.toFixed(2)} ms · p10 ${p10.toFixed(2)} · ` +
    `p90 ${p90.toFixed(2)} · dispersión ${((p90 - p10) / mediana * 100).toFixed(0)}%`
  );
  if (sumidero === Infinity) console.log("");   // ancla: impide el DCE
}

bench("sqrt", (n) => {
  let acc = 0;
  for (let i = 0; i < n; i++) acc += Math.sqrt(i);
  return acc;
});
📌 Reportá mediana y dispersión, no el promedio ni el mejor tiempo. El promedio lo destroza un GC en el medio. El "mejor de N" mide condiciones ideales que el usuario no tiene. Y si la dispersión entre p10 y p90 es mayor que la diferencia entre las dos variantes que comparás, no medisté nada: repetí con más corridas o aceptá que son equivalentes.
El paso que casi nadie da: confirmarlo en la app real. Un microbenchmark, en el mejor caso, te dice qué hipótesis vale la pena probar. La única medición que cuenta es la de tu aplicación, con tus datos, en el perfil de CPU del panel Performance — y mejor todavía, en datos de campo con usuarios reales (RUM, FS4). Es habitual que un cambio con 3× en el banco mueva la aguja un 2 % en producción porque esa función era el 0,7 % del tiempo total. Ese 2 % puede seguir valiendo la pena; lo que no vale es haberlo asumido.

FS2.8 Async: await no es gratis

async/await es azúcar sintáctica sobre promesas, y las promesas son objetos. Cada llamada a una función async asigna, como mínimo, la promesa que devuelve y la estructura que guarda el estado suspendido de la función. Además, cada await agenda un microtask: el resto de la función se ejecuta más tarde, cuando la cola de microtasks corre (el detalle del event loop está en FS1).

// Estas dos NO son equivalentes en costo
function sync(x)        { return x * 2; }
async function asincro(x) { return x * 2; }   // aloca una promesa siempre

// En un loop de 100.000 elementos, la diferencia es medible:
// 100.000 promesas + 100.000 microtasks + presión sobre el Scavenger.
Justicia con V8: el costo de await bajó muchísimo. Hubo una época en que cada await gastaba tres ticks de microtask y varias promesas intermedias; V8 lo redujo a lo mínimo indispensable y además hizo gratis los stack traces asincrónicos. Hoy await es barato. Barato no es gratis, y "barato × 100.000 en un loop caliente" vuelve a ser caro.

Dónde "async everywhere" se vuelve contraproducente

1. Marcar async una función que no espera nada. Convertís un retorno directo en una promesa que hay que crear, resolver y agendar. Si la función es un helper llamado en un loop, es puro overhead. Si tiene que devolver una promesa por contrato, devolvela sin async: return Promise.resolve(x) o mejor, devolvé el valor y que el llamador decida.
2. await dentro de un for cuando las operaciones son independientes. Serializás lo que podría ir en paralelo. Promise.all (o allSettled) es la respuesta — con el matiz de que N peticiones simultáneas contra el mismo servidor puede ser peor que 8: ahí necesitás un pool con límite de concurrencia.
3. Cadenas largas de await para valores ya disponibles. Cada await sobre un valor que ya está resuelto igual cuesta un turno de microtask. Diez capas de abstracción asincrónicas retrasan el resultado diez microtasks, y en un camino que corre por cada fila de una tabla eso se nota.
// ❌ Serial sin necesidad: N × latencia
const resultados = [];
for (const id of ids) resultados.push(await traer(id));

// ⚠️ Paralelo sin límite: N peticiones simultáneas — puede tumbar al servidor
const resultados = await Promise.all(ids.map(traer));

// ✅ Paralelo con límite de concurrencia
async function mapConLimite(items, limite, fn) {
  const salida = new Array(items.length);
  let cursor = 0;
  async function obrero() {
    while (cursor < items.length) {
      const i = cursor++;
      salida[i] = await fn(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: limite }, obrero));
  return salida;
}
const resultados = await mapConLimite(ids, 8, traer);
📌 El criterio. async es para operaciones que de verdad esperan algo: red, disco, temporizadores, otro hilo. Para transformar datos que ya tenés en memoria, el código sincrónico es más simple, más rápido y más fácil de razonar. Y si esa transformación sincrónica bloquea el hilo principal demasiado tiempo, la solución no es async —que no libera nada— sino un Web Worker o partir el trabajo en fragmentos (FS4).

FS2.9 WebAssembly: cuándo vale la pena escaparse

Cuando el motor de JavaScript ya no alcanza, la salida es Wasm: un bytecode de bajo nivel, con tipos estáticos, que se compila a código máquina de forma predecible. Sin warm-up, sin deopts, sin GC en el camino caliente (salvo que uses WasmGC), sin sorpresas.

Wasm gana cuando…Wasm pierde cuando…
Cómputo denso y sostenido: códecs, criptografía, física, compresión, inferenciaLa función es corta y se llama muchísimas veces: el cruce de frontera domina
Ya existe una implementación probada en C/C++/Rust que querés portarEl trabajo real es manipular el DOM: Wasm no lo toca directo, va por JS
Necesitás rendimiento predecible, sin picos por JIT o GCEstás en el camino de arranque: descargar y compilar el módulo cuesta
Podés trabajar sobre buffers grandes de números (TypedArrays)Los datos son strings u objetos JS: hay que serializar en cada cruce
⚠️ El costo que hunde la mayoría de los intentos: el cruce de frontera. Llamar a una función Wasm no es gratis, y sobre todo pasar datos no triviales sí es caro: los strings y los objetos hay que copiarlos dentro de la memoria lineal del módulo y volver a leerlos del otro lado. Si tu función Wasm es un toLowerCase() llamado un millón de veces, vas a ser más lento que JavaScript puro, por mucho margen. La regla es: cruzá pocas veces, con mucho trabajo por cruce.
Estado en 2026, en corto. WasmGC está disponible en los tres motores desde fines de 2024, y permite que lenguajes con recolector (Java, Kotlin, Dart) reusen el GC del navegador en vez de empaquetar el suyo — lo que recortó binarios de megabytes. JSPI (llamar APIs asincrónicas de JS desde Wasm sincrónico sin bloquear) llegó a Fase 4 y está en Chrome y Firefox. Memory64 rompe la barrera de los 4 GB y viene detrás. Nada de esto cambia la regla del cruce de frontera. El tratamiento completo está en FS8; acá solo importa saber cuándo la respuesta correcta a "esto es lento" deja de ser "optimizá el JavaScript".

FS2.10 Cuándo NO micro-optimizar (o sea: casi siempre)

Todo lo anterior es cierto y casi nunca es tu problema. Vale la pena decirlo con números.

SíntomaCausa probableOrden de magnitudDónde se ataca

📌 El orden de ataque, y no es negociable. (1) ¿Se puede no hacer el trabajo? (cachear, paginar, virtualizar, hacerlo en el servidor). (2) ¿El algoritmo es el correcto? Pasar de O(n²) a O(n) con un Map le gana a cualquier truco de motor por varios órdenes de magnitud. (3) ¿Se puede sacar del hilo principal? (Worker, requestIdleCallback, fragmentar). (4) Recién ahora, micro-optimizar el motor. Si empezás por el 4, vas a escribir código feo para ganar un 15 % de algo que se podía eliminar por completo.
El costo real de micro-optimizar de más no es el tiempo que perdés: es el código que queda. Un helper duplicado "por las ICs", campos null que nadie entiende, un pool de objetos con bugs de estado. Todo eso lo va a leer alguien en dos años sin el contexto de la medición que lo justificó. Si micro-optimizás, dejá el número en un comentario: qué medías, con qué carga, cuánto ganaste. Sin eso, la próxima persona lo va a "limpiar" —con razón— y vas a volver al punto de partida.

🧑‍🎓 Worked Example — 50.000 registros en 2,3 segundos

Una vista de reportes procesa 50.000 registros que vienen de la API y arma un resumen por categoría. Tarda 2.310 ms y congela la pestaña. El equipo propone: "pasémoslo a un Worker" y "reescribámoslo en Rust con Wasm". Antes de nada, medimos.

Paso 0 — El código como está

function construirResumen(registros, categorias) {
  let filas = [];
  for (const r of registros) {
    const cat = categorias.find(c => c.id === r.categoriaId);   // (a)
    const fila = { id: r.id, monto: r.monto, categoria: cat.nombre };
    if (r.descuento) fila.descuento = r.descuento;              // (b)
    if (r.nota) fila.nota = r.nota;                             // (b)
    filas = filas.concat([fila]);                               // (c)
  }
  return filas.reduce((acc, f) => {
    acc[f.categoria] = (acc[f.categoria] ?? 0) + leer(f, "monto");  // (d)
    return acc;
  }, {});
}
function leer(obj, campo) { return obj[campo]; }                 // (d)

Paso 1 — Perfilar, no adivinar

# En el navegador: DevTools → Performance → grabar la acción → pestaña Bottom-Up
# En Node, para el mismo código:
node --cpu-prof --cpu-prof-dir=./perfiles reporte.js
# y se abre el .cpuprofile en DevTools → Performance → Load profile

# En paralelo, ver si el motor se está peleando consigo mismo:

📌 Antes de tocar una línea, el perfil ya destruyó las dos propuestas del equipo. Un Worker movería los 2,3 s a otro hilo pero seguirían siendo 2,3 s. Wasm no ayuda: acá no hay cómputo numérico denso, hay copias de arrays y accesos a propiedades. Lo que hay es un O(n²) y dos problemas de motor.

Paso 2 — El O(n²) obvio: concat (c)

filas = filas.concat([fila]) crea un array nuevo y copia todo lo anterior, en cada una de las 50.000 vueltas. Son ~1.250 millones de copias de puntero y 50.000 arrays descartados.

const filas = [];
// ...
filas.push(fila);        // O(1) amortizado, sin alocar un array por vuelta

Medición: 2.310 ms → 795 ms. Una línea, 2,9×. Y las pausas de GC bajaron a ~8 ms porque dejamos de generar 50.000 arrays basura.

Paso 3 — El otro O(n²): find (a)

Con 200 categorías, cada registro recorre en promedio 100 elementos: 5 millones de comparaciones. La solución no tiene nada que ver con el motor, es estructura de datos.

const porId = new Map(categorias.map(c => [c.id, c]));   // una vez, O(n)
// ...
const cat = porId.get(r.categoriaId);                     // O(1) por registro

Medición: 795 ms → 470 ms.

Paso 4 — Ahora sí el motor: el polimorfismo del campo opcional (b)

Con los dos algoritmos arreglados, el perfil cambia de forma: ahora el 60 % del tiempo está en el loop propio, y --trace-deopt muestra reason: wrong map repetido en la línea del reduce.

La causa son las dos líneas if (r.descuento) / if (r.nota). Producen cuatro shapes distintas según qué combinación de campos opcionales trae cada registro: {id,monto,categoria}, {...,descuento}, {...,nota}, {...,descuento,nota}. El call site que lee f.categoria en el reduce queda polimórfico al borde del umbral, y como el orden de los registros mezcla las cuatro variantes, TurboFan optimiza y se deoptimiza en ciclos.

// Shape ÚNICA para las 50.000 filas
const fila = {
  id: r.id,
  monto: r.monto,
  categoria: cat.nombre,
  descuento: r.descuento ?? null,
  nota: r.nota ?? null,
};

Medición: 470 ms → 210 ms. Y las deopts en esa línea pasaron de 340 a 0.

Por qué este paso vino cuarto y no primero. Si hubiéramos empezado por acá —que es lo que uno hace cuando acaba de leer sobre hidden classes— habríamos ganado unos 260 ms sobre 2.310: un 11 %, sobre un problema que en realidad era 90 % algorítmico. Habríamos declarado victoria y dejado el O(n²) intacto. El orden del FS2.10 no es una formalidad: es lo que evita optimizar la parte equivocada.

Paso 5 — El helper megamórfico (d)

leer(obj, campo) es un helper compartido: en la app entera lo llaman con veinte tipos de objeto distintos, así que su call site interno es megamórfico y TurboFan no puede inlinearlo. Acá no hace falta un helper genérico:

acc[f.categoria] = (acc[f.categoria] ?? 0) + f.monto;   // acceso directo

Medición: 210 ms → 155 ms. Y el código quedó más corto y más claro que antes, que es la única micro-optimización que uno querría siempre.

Ese reparto es lo típico, no la excepción. Y el siguiente paso obvio ya no es este módulo: es paginar la respuesta, o traer el resumen ya calculado del servidor — o sea, no hacer el trabajo (FS2.10, punto 1).
Cerralo con una prueba, no con un commit. Un test que falla si construirResumen tarda más de, digamos, 400 ms sobre un fixture de 50.000 filas convierte esta tarde de trabajo en una garantía. Sin eso, dentro de seis meses alguien agrega un campo opcional "porque es más limpio" y volvés a 470 ms sin que nadie se entere.

Checkpoint — ¿lo tenés claro?

Una función procesa objetos que vienen de cinco endpoints distintos, cada uno con su forma. Corre 200.000 veces. ¿Qué le está pasando y qué se hace?

El call site que lee propiedades vio cinco shapes distintas, así que pasó el umbral de cuatro y se volvió megamórfico: V8 abandona la inline cache y consulta un caché global con hash, y además TurboFan pierde la capacidad de inlinear esa función, lo que arrastra otras optimizaciones que dependían del inlining. Hay dos salidas. La primera y preferible es normalizar en el borde: convertir las cinco respuestas a una forma única apenas entran a la app, lo que además es mejor diseño porque el resto del código deja de conocer los formatos externos. La segunda, si por alguna razón no se pueden normalizar, es especializar el camino caliente con una función por forma, aunque duplique código: cinco call sites monomórficos ganan por lejos a uno megamórfico. Y en ambos casos se verifica con --trace-deopt o con el perfil de CPU, no por fe.

Tu benchmark dice que la versión nueva es 8× más rápida, pero en producción no cambió nada. Enumerá las causas posibles, en orden de probabilidad.

(1) Esa función no era el cuello de botella. Si representaba el 3 % del tiempo total, un 8× te da un 2,6 % de mejora global — indetectable. Es lo más frecuente y se descarta mirando el perfil antes de optimizar. (2) Dead code elimination: el benchmark no consumía el resultado y V8 borró el cálculo, así que medía la nada. (3) El banco creó condiciones que no existen en producción: tipos siempre iguales, shapes estables, todo monomórfico e inlineado; en la app real la función es polimórfica y no se inlinea. (4) Falta de warm-up o exceso de warm-up: mediste Ignition, o mediste un caso ultra-especializado. (5) Varianza no controlada: reportaste un promedio o un mejor-de-N en lugar de mediana y dispersión, y la "mejora" está dentro del ruido. La verificación honesta es siempre la misma: medir el flujo completo en la app, antes y después, con la misma carga.

Una SPA arranca en 180 MB y después de veinte minutos de navegación está en 900 MB. ¿Cómo lo diagnosticás?

Primero hay que distinguir crecimiento de fuga: un caché que se llena y se estabiliza no es una fuga. Se abre DevTools → Memory y se aplica la técnica de los tres snapshots: snapshot en el estado base, repetir la navegación sospechosa 10–20 veces volviendo siempre al mismo estado, snapshot, repetir, snapshot. Si el heap crece linealmente con las repeticiones, es una fuga. Después se compara el tercer snapshot contra el segundo y se ordena por Retained Size —no Shallow—, porque lo que importa es cuánta memoria mantiene vivo cada objeto, no cuánto pesa él. El panel Retainers da la cadena desde la raíz hasta el objeto, y ahí aparece el culpable. Los sospechosos habituales, en orden: listeners sobre window/document que no se removieron al desmontar, nodos del DOM guardados en arrays o mapas después de sacarlos del documento (buscar Detached en el filtro), closures que capturan objetos grandes, y cachés sin política de expulsión. La prevención estructural es AbortController con { signal } en todos los listeners de un componente y un destroy() explícito que suelte las referencias.

Resumen ejecutivo

  • V8 tiene cuatro tiers (Ignition → Sparkplug → Maglev → TurboFan), no dos, y promueve según estabilidad del feedback, no solo por contador. Turboshaft es el backend moderno del último tier, no un tier nuevo.
  • Parsear cuesta antes de ejecutar. El pre-parser hace tolerable un bundle grande, pero el top level y las IIFE se pagan completos. La optimización que gana no es escribir mejor JavaScript: es enviar menos.
  • Shapes e inline caches son el mecanismo central. Monomórfico → polimórfico (hasta 4) → megamórfico, que es un acantilado, no una pendiente: se pierde el acceso rápido y también el inlining.
  • Los arrays también tienen tipo (elements kinds) y las transiciones son de una sola dirección: de PACKED a HOLEY no se vuelve. new Array(n) sin fill nace holey.
  • Deopt = falló una suposición. Lo grave no es una deopt: es el ciclo optimizar–deoptimizar. Se lee con --trace-deopt. El "try/catch impide optimizar" es un mito de la era Crankshaft, muerto desde ~2017.
  • GC generacional: Scavenger sub-milisegundo en la generación joven, Mark-Sweep-Compact con marcado concurrente en la vieja. Con 16,7 ms por frame, una pausa mayor se ve. Una fuga en JS siempre es alcanzabilidad: listeners, closures, DOM detached, cachés sin límite. Se caza con tres snapshots y la columna Retained Size.
  • Estructuras: objeto para claves fijas, Map para claves dinámicas; TypedArray cuando el layout tiene que estar garantizado; y la concatenación de strings es O(1) en V8 gracias a las ropes — el problema es leer el string parcial dentro del loop.
  • Los microbenchmarks mienten por DCE, por crear condiciones que no existen en producción, por warm-up mal hecho y por varianza. Reportá mediana y dispersión, consumí el resultado, y confirmá en la app real.
  • await es barato, no gratis. Marcar async una función que no espera nada aloca una promesa y un microtask por llamada. Para trabajo sincrónico pesado la respuesta no es async, es un Worker.
  • Wasm gana con cómputo denso y pocos cruces de frontera; pierde con funciones cortas, mucho DOM o mucho string. Detalle completo en FS8.
  • El 95 % de las veces el cuello no es el motor. Orden de ataque: no hacer el trabajo → arreglar el algoritmo → sacarlo del hilo principal → recién ahí, micro-optimizar. Y si micro-optimizás, dejá el número medido en un comentario.

🧠 Autoevaluación

1. Una función que lee item.precio en un loop pasa de recibir objetos de 4 formas distintas a recibir objetos de 5 formas. El tiempo se dispara mucho más de lo que sugeriría "una forma más". ¿Por qué?

Es un acantilado, no una pendiente. Hasta 4 shapes V8 mantiene una lista corta y compara contra ella. Con la quinta abandona la IC y pasa a un caché global con hash — y lo caro no es solo ese acceso: al perder la inline cache se pierde el inlining, y con él caen en cascada el escape analysis, el unboxing de números y la eliminación de chequeos que dependían de tener la función inlineada. Por eso el salto de 4 a 5 cuesta mucho más que el de 3 a 4, y por eso de 5 en adelante se aplana: una vez megamórfico da igual tener 5 shapes que 50.

2. Tu microbenchmark reporta que la versión B es 8× más rápida que la A. ¿Cuál es la primera cosa que verificás antes de creerle?

Sin consumir el resultado, TurboFan puede eliminar el cálculo entero (dead code elimination) y estarías midiendo la nada. Sin warm-up medís Ignition o Sparkplug, no el código optimizado. Pero incluso con un banco impecable, el motivo más frecuente de que un 8× no se note en producción es que esa función era el 3 % del tiempo total: un 8× sobre el 3 % es un 2,6 % global, indetectable. Por eso el perfil de la app real va antes del benchmark, no después.

3. Una vista procesa 50.000 filas en 2,3 s. El perfil muestra 64 % en Array.prototype.concat y 13 % en Array.prototype.find. ¿Por dónde empezás?

El perfil ya dijo que el 77 % del tiempo está en dos algoritmos cuadráticos: concat copia el array completo en cada vuelta y find recorre la lista de categorías por registro. Arreglar eso da ~5× con dos líneas. Empezar por las shapes hubiera dado un 11 % y hubiera dejado el O(n²) intacto — el error clásico de aplicar lo último que uno leyó. Y el Worker no achica el trabajo: mueve 2,3 s a otro hilo y siguen siendo 2,3 s, con el costo extra de serializar los datos para cruzarlos.
